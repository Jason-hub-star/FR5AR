# 증거 — 마커 검출 실측 (2026-07-30)

분류: **증거**. 실제 ARToolKit 검출기로 측정했다. 카메라는 열지 않았다.

```bash
python3 scripts/assets/make-marker-test-images.py    # 합성 이미지 117장
bash scripts/dev/serve.sh 8123
# http://localhost:8123/test/marker-detect.html         (정본 마커 #5)
# http://localhost:8123/test/marker-detect.html?bc=2    (예비 마커 #2)
```

## 무엇을 닫았나

`DECISION-LOG` D10에서 마커를 바코드 3×3 Hamming으로 바꿀 때
**"시뮬레이션은 실제 검출기가 아니다"**를 미확정으로 남겼다. 그것을 닫았다.

`ArToolkitSource` 의 `sourceImage` 로 합성 이미지를 먹여, 사각형 검출 → 매트릭스 디코드 →
Hamming 오류정정을 거치는 **실제 경로**를 통과하는지 봤다.

## 결론 3개

### ① 크기가 아니라 **대비**가 결정한다

| 조건 | 검출되는 최소 변 |
|---|---|
| 흐림 0.5px (이상적) | **16px** |
| 흐림 1.5px | 16px |
| 흐림 3.0px | 24px |
| JPEG 품질 35 | 24px |
| **대비 낮음 (명도차 ~106)** | **전부 실패 — 120px도 실패** |
| 대비 낮음 + 흐림 3 + JPEG | 전부 실패 |

**필요한 최소 명도차 약 130** (0~255 척도). 명도차 137에서 통과, 127에서 실패.

| 크기 | 통과한 최저 명도차 |
|---|---|
| 120px | 153 |
| 60px | 142 |
| 32px | 137 |

→ **인쇄 시트의 "무광 용지 · 고른 조명"이 마커 크기보다 중요하다.**
광택지 반사광은 국부적으로 명도차를 무너뜨리고, 그건 마커를 키워도 해결되지 않는다.
검은 잉크가 인쇄에서 연해지는 것(토너 절약 모드 등)도 같은 실패다.

### ①-b 흰 여백은 **3%면 충분하다** — 내가 5배 크게 잡았다

마커 크기를 고정하고 흰 여백만 0~40%로 바꾸며, **여백 밖을 어두운 배경**으로 뒀다
(어두운 판·테이블에 붙이거나 종이 끝까지 마커가 가는 상황이 실제 위험이다).

| 여백 (마커 한 변 대비) | 120px 마커 | 80px 마커 |
|---|---|---|
| 0% | ✗ | ✗ |
| **3%** | **○** | **○** |
| 6 · 10 · 16 · 25 · 40% | ○ | ○ |

**0%만 실패한다.** 마커가 어두운 면에 바로 닿아 흰 경계가 없을 때다.

인쇄 시트의 여백을 처음 **16%로 잡은 것은 측정이 아니라 추정**이었고, 필요량의 5배였다.
8%(실측 최소의 2.7배)로 줄여 같은 용지에서 마커를 키웠다 — **A4 150→170mm, A3 200→240mm.**

A4 에서 마커 크기를 제한하는 것은 **세로가 아니라 가로 210mm** 다.
시트 아래 설명 글은 세로 공간만 쓰므로 **지워도 마커가 커지지 않는다** (깔끔해질 뿐).

### ② 검출기는 **첫 검출까지 수십 프레임을 먹는다**

`context.init` 콜백이 온 뒤에도 한동안 아무것도 못 잡는다.
첫 검출까지 필요한 프로브 수를 재보니 **실행마다 1~36회로 흔들렸다** (프로브당 2 update 호출).

→ 시연에서 **마커를 비추자마자 안 뜨는 것이 정상이다.** 2~3초 들고 기다려야 한다.
`web/ar.html` 의 HUD가 "마커를 찾는 중…"을 띄우는 이유다.

→ 이것이 내 첫 측정을 망친 원인이다. §틀린 측정 참조.

### ③ 마커 번호는 중요하지 않았다

| 마커 | 기본 케이스 | 오독 | 최소 검출 변 | 음성 대조군 |
|---|---|---|---|---|
| **#5** `110/110/110` (정본) | **18/18** | 0 | 16px | 9/9 거부 |
| **#2** `101/100/110` (예비) | **18/18** | 0 | 16px | 9/9 거부 |

기본 케이스 = 변 240·160·120·80·60·44·32·24·16px × 기울기 0°·12°.

D10에서 #5를 고른 근거는 "고립된 1칸 특징이 없어 흐려질 때 유리하다"였다.
**실제 검출기에서는 완전히 동등했다.** 시뮬레이션(PIL로 셀을 다시 읽기)이
Hamming 오류정정을 흉내내지 못해 셀 손실에 과민하게 나온 것이다.
**정교하게 고른 것은 과잉이었다.** #5를 유지한다 — 바꿀 이유가 없고 예비 인쇄본도 있다.

## 음성 대조군 — 9건 모두 정상 거부

| 이미지 | 결과 |
|---|---|
| 빈 흰 화면 | 거부 ✓ |
| 등록하지 않은 마커 #3 | 거부 ✓ |
| 검은 사각형만 (패턴 없음) | 거부 ✓ |
| 글자 있는 문서 | 거부 ✓ |
| **상대 마커 5건** (등록 안 한 번호, 60~240px) | 거부 ✓ |

**이 대조군이 없으면 "전부 검출됨"은 측정이 아니다.**
검출기가 아무 프레임에나 `visible` 을 켜는 것과 구별되지 않는다.
상대 마커를 대조군에 넣은 것이 핵심이다 — 번호를 실제로 **구별**한다는 증거다.

## 거리 환산 (참고, 낙관적)

640×480 · 수평 화각 약 60° 기준. 마커가 프레임 폭의 16/640 = 2.5%를 차지할 때까지 검출된다.

| 마커 | 이론상 검출 한계 | 목표 |
|---|---|---|
| A3 240mm | 약 8.3 m | 2 m |
| A4 170mm | 약 5.9 m | 2 m |

**이 숫자를 그대로 믿지 않는다.** 합성 이미지는 손떨림·역광·인쇄 번짐·실제 폰 해상도를
반영하지 않는다. 다만 여유가 크다는 것은 말할 수 있고, 그래서
**A4 170mm로도 2m는 된다.** A3는 여유일 뿐 필수가 아니다.

## 틀린 측정 — 세 번 고쳤다

처음 얻은 "36/36 검출, 최소 16px"은 **재현되지 않았다.** 같은 이미지가 다시 돌리면
`#2 17/18 → 0/18`, `#5 18/18 → 7/18` 로 바뀌었다. 원인을 셋 잡았다.

| 원인 | 증상 | 해결 |
|---|---|---|
| **검출기 워밍업** | 앞쪽 프로브가 크기와 무관하게 전부 실패. 실패했던 240px 이미지가 나중에 다시 재면 1프레임에 검출됨 | 큰 마커로 첫 검출이 날 때까지 돌린 뒤 측정 시작. 60회 안에 못 잡으면 **결과를 믿지 말라고 표시** |
| **바코드 2개 동시 등록** | 실행마다 결과가 바뀜. 마커 하나만 쓰는 구간은 세 번 모두 같은 숫자 | 한 번에 하나만 등록. 다른 번호는 `?bc=2` 로 따로. 상대 마커는 **대조군으로** 넣어 구별 능력을 본다 |
| **이미지 픽셀 미확정** | `<img>` 를 그대로 넘기면 결과가 흔들림 | `fetch → createImageBitmap → drawImage` 로 캔버스에 그려 넘긴다. `onload` 는 디코드를 보장하지 않고 `img.decode()` 는 백그라운드 탭에서 resolve 되지 않는다 |

## 밟은 함정 — 헤드리스 검증 일반

| 함정 | 증상 | 원인·해결 |
|---|---|---|
| 컨텍스트를 이미지마다 생성 | **렌더러가 얼어붙음** | `ArToolkitContext` 하나마다 1.2MB 프레임 버퍼 + WASM 컨트롤러. **하나만 만들고 이미지를 갈아 끼운다** |
| `requestAnimationFrame` 대기 | 검사가 영원히 멈춤 | MCP 탭은 `visibilityState === 'hidden'` 이라 rAF 가 **아예 안 불린다** |
| `setTimeout(0)` 대기 | 100건이 10분을 넘김 | 백그라운드 탭에서 1초로 묶인다. `context.update` 는 동기 함수라 대기가 애초에 불필요 |
| `maxDetectionRate` 스로틀 | 연속 호출이 검출 없이 무시됨 | `context._updatedAt = null` 로 매번 우회 |
| 적용 안 되는 구간을 "전부 실패"로 보고 | 예비 마커가 나쁜 것으로 오해됨 | 스트레스·대비 이미지는 정본 마커용이다. 대상이 다르면 **건너뛴다고 적는다** |

**헤드리스 검증 코드는 프레임 타이밍과 요소 렌더에 의존해선 안 된다.**

## 시트에서 뺀 것

처음에는 인쇄·부착 지침 6줄을 시트 아래에 넣었다. **시트에 있을 이유가 없다** —
인쇄하기 전에 읽는 내용이고, 그건 화면(`web/index.html`)과 이 문서에 있다.
지금은 한 줄만 남겼다 — **어느 마커이고 몇 mm인지**. 종이만 보고는 `barcodeValue` 를
알 방법이 없고, 코드 설정이 어긋나면 아무것도 뜨지 않는다.

## 남은 미확정

- **인쇄물 실측이 아니다.** 합성 이미지다. 실제 인쇄·촬영의 명도차는 인쇄 후 재야 안다
- 폰 실기 검출률 — A트랙 2단계에서 확정한다
- 정합 오차(±5~15mm 문헌값) — B트랙에서 실측한다.
  이 측정은 **검출 여부만** 봤고 위치 정확도는 보지 않았다
