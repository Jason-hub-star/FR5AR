# 겹치기 정합 — 벽 법선·훑기·준비도 HUD (2026-08-07)

## 무엇을 물었나

> 최초 AR 시작 때 캘리브레이션 기준은 모드마다 다른가? 시간이 길수록 정확해지나?
> 답사에서 벽이 기준이 될 수 있나? 캘리브레이션을 쉽게 하는 HUD 는?

## 답 — 네 가지, 전부 근거와 함께

**① 모드별 기준은 셋 다 같았다.** 갈리는 건 `scale0` 한 줄과 탭 횟수뿐이었다. 문제는
**오차에 가장 약한 답사(1:1)가 보정을 가장 안 받는다**는 것.

**② 시간을 늘려도 안 좋아진다.** ARCore 는 VIO 라 수렴시키는 건 **시차**다 — 가만히 서서
기다리면 얻는 게 없고 IMU 드리프트만 쌓인다. `WARMUP_MS` 는 틀린 것을 재고 있었다.

**③ 벽은 기준이 된다 — 새 API 없이.** `xr.js:550` 이 히트 포즈의 `position` 만 쓰고
`orientation`(= 그 면의 법선)을 **받아 놓고 버리고 있었다.**

**④ 정합 오차의 최대 항은 캘리브레이션이 아니라 `↺↻` 였다.** ±15° 스테퍼로는 최선을
다해도 ±7.5° 가 남고, 12m 지점에서 그건 **157cm** — 축척 오차(24cm)의 6배다.

## 손계산이 먼저, 실행은 확인용

점 N개 최소제곱의 기울기 오차 `σ√12/(L√N)` vs 탭 2회 `σ√2/L` → 갈리는 지점 **N=6**.

| 방법 | 기저 | 예측 | 12m 지점 |
|---|---|---|---|
| 15° 스테퍼 | — | ±7.5° | 157cm |
| 촬영 2탭 | 14.4m 대각 | 0.56° | 12cm |
| **3m 훑기 120표본** | 3m | **0.24°** | **5.5cm** |

**실측 0.240°** (`xr-web-verify.mjs`). 예측과 일치 — 3m 훑기가 14m 대각 2탭을 이긴다.

P1 다섯 건. **F1 은 플랜과 무관하게 배포본에 있던 버그다.**

| | 발견 | 처리 |

| **F4** | 타이머를 조건으로 바꾸다 **도달 불가 상태**를 만들 뻔했다 — "0.3m 이동" 은 삼각대에서 영영 충족 안 되는데, 그 고정 카메라 시연이 `xr.js` 머리말에 적힌 용도다 | 6초 유예 뒤 무조건 통과 + 회귀 검사 |

## 덤으로 잡힌 근본 원인 — 로봇이 누워있던 이유

`Dashboard/…/LayoutView.jsx` `holder` · `AR/…/xr.js` `holder` · `AR/…/robot.js` `zUpToYUp`

`Shared/view3d/robot.js:41-43` 이 **규칙을 산문으로 이미 적어 뒀는데 구현만 없었다.**
`mountRobotYUp` 하나로 흡수 — **5 → 1**. 한 벌이 빠지면 눕는다.

## 어떻게 확인했나

```
node scripts/check/xr-web-verify.mjs --pure   37/37   (브라우저 없음 · 1초)
node scripts/check/xr-web-verify.mjs          67/67   (헤드리스 `화면` 모드 실렌더 포함)
bash scripts/check/all.sh                     전체 통과
```

새 순수 검사 — **전부 답을 손으로 아는 것들**:
- 벽 법선 → yaw **왕복** (three 로 실제 회전시켜 대조). 법선을 뒤집으면 180° 반대가 나온다
- 히트 분류에서 **수직이 수평으로 새지 않는다** (F3 회귀)
- 훑기 0.240° · 잔차가 손 떨림 22.7mm 를 읽는다 · 포물선은 잔차가 크다 · 세로 벽(90°)에서 발산 안 함
- 준비도 **216가지 전수** — 상태와 문구가 어긋나는 조합 0
- **삼각대는 유예 뒤 반드시 통과** (F4 회귀)

### 검사를 한 번 고쳤다

훑기 각도 검사가 처음에 `89.98°` 로 실패했다. 원인은 코드가 아니라 **검사에 박은 손유도**
였다 — `yaw = 선각 + 90°` 로 기대했는데 `layout-view` 의 Z 가 거울이라 실제로는 `π − 선각`
이다. 검사를 **성질**로 바꿨다: "맵을 이 yaw 로 돌리면 로컬 +Z 가 훑은 선과 수직인가".
유도를 검사에 박으면 이렇게 거짓 실패를 낸다.

## 확인하지 않은 것 — 여기부터 폰이 필요하다

게이트가 **절대 못 보는** 것들이다. `immersive-ar` 은 폰에서만 열린다.

- **훑기 제스처 자체** — `selectstart`/`selectend` 가 실제로 오는지, `beforexrselect` 가
  조작바 위에서 `selectstart` 까지 막는지 (막지 않아도 짧은 훑기는 span 검사가 걸러낸다)
- **진동** — `navigator.vibrate` 가 XR 세션 중에 먹는지
- **자동 놓기** — `평소` 에서 0.8초 초록 유지가 실제로 안정적인지
- **벽 평면 검출 여부** — 무늬 없는 흰 벽이면 ARCore 가 수직 평면을 못 잡는다. 그러면
  벽 법선 경로가 실패하고 **훑기가 주력**이 된다. 이게 우선순위를 정한다
- 앵커·유령벽·바닥 잠금·바텀시트 — **2026-08-06 부터 계속 미확인**

## 폰이 잡은 것 — 게이트가 원리상 못 보던 셋

`startAR` 은 어떤 테스트도 실행하지 않는다 (헤드리스가 도는 것은 `화면` 모드다).
아래 셋은 **사람이 폰을 들어서** 나왔다.

**① 탭하기도 전에 맵이 서 있었다.** `anchor` 가 만들어지자마자 씬에 붙는데 `position` 이
`(0,0,0)` — `local-floor` 원점, 즉 **세션을 열 때 서 있던 자리**다. 겨냥한 곳과 아무 상관없는
데라 "이미 놓였나?" 로 읽히고 탭하면 거기서 점프한다. → 놓기 전에는 링만 그린다.

**② 링이 맵의 어디인가를 모드마다 안 갈랐다.** `layout-view.js:102` 의 root 원점은 맵의
**모서리**라 셋 다 구석에 섰다. 그런데 모드가 시키는 일이 다르다:

| 모드 | 링이 오는 자리 | 왜 |
|---|---|---|
| 평소 | **가운데** | "책상 위에 얹는다" 는 *여기 놔라* 지 *여기가 모서리다* 가 아니다 |
| **답사** | **들어가는 변의 가운데** | 구석에 서면 **대각선으로** 들어가야 한다 — "걸어 들어간다" 가 성립하지 않는다 |
| 촬영 | 모서리 (그대로) | `solveCorners` 가 첫 모서리를 원점으로 쓴다. 바꾸면 축척 보정이 깨진다 |

이동은 **`apply()` 에서** 한다. 탭할 때 좌표를 옮겨 두면 확대할 때마다 기준점이 모서리
쪽으로 밀린다 — 배율이 바뀔 때 같이 잡아야 제자리에 머문다.

**③ 각도가 사람과 무관했다.** `yaw = 0` 은 서 있는 쪽과 아무 상관이 없다. 이걸 고치면서
남겨 뒀던 **4지선다가 저절로 풀렸다** — 벽 법선은 yaw 를 90° 네 자리까지만 좁히는데,
그 마지막 한 칸을 `↺↻` 로 미루지 않고 **사람이 서서 보는 쪽**이 고른다 (`snapQuadrant`).
**벽이 정밀함을, 사람이 방향을 낸다.** 게이트가 전수로 확인한다 — 90° 배수로만 돌려
벽이 낸 정밀함을 안 깎고(오차 0), 그중 사람 쪽에 45° 안으로 붙는다.

## 남은 판단

`plane-detection` 모듈(벽 폴리곤을 통째로 주는 것)은 안 썼다. 안드로이드 크롬에서 플래그
뒤에 있을 수 있어 확인이 필요하고, **히트 포즈의 법선만으로 대부분 된다.** 폰에서 벽이
안 잡히는 것이 확인되면 그때 다시 판단한다.
