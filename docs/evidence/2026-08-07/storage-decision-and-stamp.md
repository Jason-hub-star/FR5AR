# 저장소를 SQLite 로 되돌리고, 궤적에 그리퍼 정체를 실었다 (D81)

날짜 2026-08-07 · 게이트 `bash scripts/check/all.sh` **exit 0**

## 1. D81 — Supabase 를 보류로 되돌렸다

**바꾼 이유는 D46 의 이유를 그대로 밀어붙인 것이다.** D46 은 "인터넷이나 클라우드가 끊겼다고
티칭·실행이 멈추면 안 된다" 로 두 층을 세웠는데, 그 이유를 **열람까지** 확장하면 클라우드가
상위 층일 근거가 없다 — 작업이 안 멈춰도 기록을 못 보면 반쪽이다.

**D46 의 기각 하나를 철회했다** — "SQLite 단독: 팀 공유가 안 된다" 는 SQLite 를 **각자 PC 에
두는** 경우다. 상주 기계 하나가 들고 HTTP 로 서빙하면 공유도 집계도 된다. 팀은 이미 랩 안에서
브리지 주소 하나로 들어온다 (`TB-CONTRACT.md`).

전파한 곳 — `DECISION-LOG.md`(D46 행에 개정 표시 · 본문 보존) · `Database/AGENTS.md` ·
`ARCHITECTURE.md` · `USER-REQUIREMENTS.md` · `GAP-MATRIX.md`(BLOCKED→CLOSED) ·
`.env.example`(Supabase 키를 **지우지 않고** 보류 표시).

**살려 둔 것** — D46 의 스키마 조항 전부. 저장소가 바뀌어도 "소급해 못 채운다" 는 이유가 안 변한다.

### 확인하지 않은 것

- **보존 기간은 여전히 미정이다.** 저장 방식만 정했고 이건 팀 회의 몫이라 GAP 에 남겼다
- 호스트(라즈베리파이 4/5)를 **정하지 않았다.** D61 과 같은 태도로 계약이 호스트를 모르게 뒀다

## 2. 궤적 `stamp` 에 그리퍼 정체를 실었다

**착수 전 판단이 틀렸다.** "정체 4개가 빠졌다" 고 봤으나 `session.stamp()` 이 `robotId` ·
`toolId` · `userId` · `firmware` · `speedCapPct` · `gripperForcePct` · `workspaceRev` 를 이미
싣고 있었다. 궤적 레코드의 최상위 키만 보고 `stamp` 안을 안 열은 탓이다.

**실제로 빠져 있던 것은 그리퍼 정체 하나**였고, 값은 이미 오고 있었다 —
`gripper_activate()` 가 `GetGripperConfig` 를 읽어 반환하는데 `commands.py` 가 **로그로만
흘려보내고 버렸다.**

| 파일 | 무엇 |
|---|---|
| `API-CONTRACT.md` | `stamp.gripperConfig` 추가 + "해석하지 않고 원본을 싣는다" 규약 (하드 룰 1 — 계약 먼저) |
| `session.py` | `clear()` 에 필드 신설("빈 세션의 유일한 정의" 자리) · `open()` 에서 초기화 · `stamp()` 에 실음 |
| `commands.py` | 활성화가 읽어 온 `diag` 를 세션에 보관 |

**파싱하지 않는다.** `GetGripperConfig` 는 `company`·`device` 에 +1 보정이 섞여 있고 우리
실측(`4·0`)과 유니티 기록(`2·4`)이 갈렸다. 해석해 저장하면 그 해석이 틀렸을 때 원본이 안 남는다.

**로봇이 바뀌면 물려주지 않는다** — `open()` 에서 비운다. 이전 연결의 그리퍼 정체가 다음
궤적에 붙으면 조용히 거짓말이 된다.

### 검증 — 기존 게이트는 새 필드를 보지 않는다

단위 141 · 브리지 왕복 93 · 웹 실렌더 66 은 전부 통과하지만 **새 필드를 검사하지 않는다.**
그래서 따로 확인했다.

```
① 활성화 전 — gripperConfig: null
② 활성화 후 — {"config": [0, [1, 4, 0, 0]]}     ← 계약 예시와 일치
③ clear·open 둘 다 초기화됨
4/4 통과
```

### 확인하지 않은 것

- **실기 미검증이다.** mock 어댑터로만 확인했다. 실물에서 `GetGripperConfig` 가 무엇을
  돌려주고 그것이 궤적 파일에 실제로 실리는지는 **다음 실기 세션에서 본다** —
  활성화 → 궤적 녹화 → `~/fr5-data/trajectories/` 의 JSON 을 열어 `stamp.gripperConfig` 확인
- 옛 궤적 파일에는 이 필드가 없다. 읽는 쪽이 `null` 을 견디는지는 화면에서 확인하지 않았다

## 3. 실렌더 게이트에 포트 방어선을 넣었다

**증상** — `fr5-web-verify` 66건 중 2건이 화면 탓처럼 실패했다
(`미연결 phase 표시 DISCONNECTED` · `null (reading 'click')`).

**근본 원인은 화면이 아니었다.** 게이트는 자기 브리지를 띄운 뒤 `/robots` 가 200 이면 "떴다"
로 보는데 **남의 브리지도 200 을 준다.** 별도 터미널이 띄운 프로세스가 5157·5176 을 쥐고
있어 게이트가 **이미 로봇에 연결된 화면**에 붙었고, "아직 연결 안 됨" 을 전제한 검사 둘만 깨졌다.

고아를 정리하고 단독 재실행하니 **66/66 PASS** — 원인 확정.

`fr5-render.sh` 진입점에서 실행 전 포트 점유를 검사해 **멈춘다.** 자동으로 죽이지는 않는다 —
게이트 둘이 동시에 돌면 서로 죽인다. 양방향 확인: 포트가 비면 159/159 통과, 점유되면 exit 1.

**게이트 자체는 고아를 남기지 않는다.** 연속 실행 직후의 "Address already in use" 는 커널
TIME_WAIT 잔여였다. 처음 발견된 고아는 별도 터미널이 띄운 것이다.

## 4. 개발 기록물 파이프라인

발표 자료에 넣을 사진을 매번 찾아 헤매던 것을 없앴다.

- `scripts/dev/shot.sh` — 화면 캡처 · 폰 사진(HEIC→jpg) · 영상(→gif 2MB 상한 + 대표 프레임)
  을 오늘 날짜 폴더에 떨구고 **캡션을 그 자리에서 `SHOTS.md` 에 쌓는다**
- `scripts/build/album.mjs` — 전 날짜 사진을 `docs/evidence/ALBUM.md` 한 장으로 색인

**캡션은 나중에 받으면 못 받는다** — 실측으로 기존 사진 42장 중 마크다운 이미지 문법에 캡션이
붙은 것은 9장뿐이었다. `album.mjs` 가 산문에서 28장을 건져 88% 까지 올리지만 건진 문장은
캡션으로 어색하다. 그래서 `SHOTS.md` 를 캡션의 단일 출처로 둔다.

영상 원본(`.mov`/`.mp4`/`.webm`)은 `.gitignore` — 커밋되는 것은 gif 와 png 뿐이다.
