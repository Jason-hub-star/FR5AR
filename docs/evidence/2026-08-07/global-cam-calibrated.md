# 글로벌 카메라 캘리브레이션 — 닫힘

분류: 증거 · 2026-08-07 · 대상 `Shared/data/config/global-cam.json`

## 결론 먼저

**게이트 넷을 다 통과했고 설정 파일이 교체됐다.** 눈으로도 확인했다.
이전 값이 왜 틀렸는지는 `../2026-08-06/global-cam-intrinsics-invalid.md`.

```
내부  2560x1440 · HFOV 73.05° · RMS 0.469px · 사진 25장 · 앞뒤 fx 차이 0.7%
외부  카메라 (343, -1782, 672) mm · 상판에서 0.67m · 하향 10.8° · RMS 1.51px
거치  폰 **가로(16:9)** — CSS 90° 회전 없앰 · 팔 작업 전 범위 담김 · 0.95 mm/px
```

| | 옛 값 | 지금 |
|---|---|---|
| fx / fy | 2106.36 / 2059.07 | **1728.17 / 1724.40** (이방성 2.2% → 0.2%) |
| 주점 | (1292.9, 722.5) | (1270.9, 735.6) — 화면 중앙에서 18px |
| HFOV / VFOV | 62.57° / — | **73.05° / 45.32°** |
| 왜곡 | `[0.361, −3.424, −0.0051, 0.0068, 16.622]` | **`[0.112, −0.257, 0.003, 0.0, 0.339]`** |

**왜곡 계수가 가장 강한 방증이다.** 옛 `k3 = 16.62` 는 물리적으로 성립하지 않는 값 —
초점거리를 맞추려 왜곡이 억지로 부풀려진 흔적이다. 새 값은 평범한 폰 렌즈 범위다.

## 무엇이 달랐나 — 장수가 아니라 기울기다

52장까지 찍었을 때도 앞/뒤 fx 차이는 **8.5%** 로 안 닫혔다 (상한 5%). 원인:

```
무작위로 절반 가르기 40회 → 앞뒤차 중앙값 2.8%  (범위 0.2~8.4)
시간순으로 절반 가르기     → 8.5%               ← 게이트가 쓰는 방식
기울기 낮은 절반 fx 1811  |  높은 절반 fx 1736
```

**정면에 가까운 사진은 초점거리 정보를 담지 않고 왜곡과 맞바꾼다.** 촬영 초반에 정면
사진이 몰려 있어 시간순 분할에서만 크게 벌어졌다. 기울기 15° 미만 9장을 빼자 닫혔다:

| 버린 문턱 | 장수 | RMS | fx | 앞뒤차 |
|---|---|---|---|---|
| 0° (전부) | 33 | 0.488 | 1752 | 8.5% |
| **15°** | **25** | **0.469** | **1728** | **0.7%** |
| 20° | 17 | 0.515 | 1736 | 2.6% |
| 25° | 10 | 0.625 | 1715 | 0.5% |

**이 걸러내기가 게이트 봐주기가 아닌 근거 셋:**

1. 기준이 **기하(기울기)** 라 게이트가 재는 값(RMS·fx)과 독립이다. 게이트가 재는 값으로
   골라내면 자기 답을 자기가 채점하는 것이라 검증이 아니다
2. **촬영 전에 정한 기준이다.** "40~60° 로 기울여라" 를 결과를 보기 전에 지시했다
3. **fx 가 사방에서 같은 값으로 모인다** — 모델을 바꿔도 1735~1756, 문턱을 바꿔도
   1715~1736, 상판 태그 자유최적합은 1829. 이전 20장에서는 같은 조작이 1351~2351 이었다

## 배율의 주인은 `tagSizeMm` 하나다

태그 배치를 사진에서 풀었더니 모양은 완벽한 직사각형인데(z 편차 3mm, yaw 편차 1°)
크기만 줄자보다 7% 컸다. 두 축이 **같은 비율**로 어긋난 건 기준자가 틀렸다는 뜻이다.

| | `tagSizeMm=155` | `tagSizeMm=145` | 줄자 |
|---|---|---|---|
| 0↔2 | 644 | **599.4** | 600 |
| 0↔1 | 327 | **303.4** | 300 |

실측 145mm 로 확정. `extrinsics.py` 주석의 2026-08-03 실측값과도 일치한다.
**이 하나가 모든 거리의 척도라 7% 틀리면 카메라 높이도 7% 틀린다.**

## 렌즈 왜곡 재측정 — HUD 설계에 직접 걸린다

핀홀 투영과의 어긋남 (`2560×1440` 격자 65×37):

| 위치 | 새 계수 | (옛 계수였다면) |
|---|---|---|
| 정중앙 | 0.0 px | 0.0 |
| 가로 1/4 | 6.8 px | 7.6 |
| 좌변 중앙 | 42.3 px | 680 |
| 좌상 모서리 | **74.8 px** | **2064** |
| 화면 최대 | **82 px** | 2064 |

**최대 어긋남이 25배 줄었다.** 다만 "1px 이내" 반경은 344px 로 화면 대각 반경의 **23%**
— 이전과 비슷하다. 결론이 정성적으로는 같고 **정량적으로는 완전히 다르다**:

| 허용 오차 | 덮는 화소 | 최대 반경 |
|---|---|---|
| ≤1px | 7.8% | 344px |
| ≤2px | 13.0% | 442px |
| ≤5px | 25.9% | 612px |
| ≤10px | 44.7% | 810px |

→ three.js `PerspectiveCamera` 만으로 화면 전체를 덮으면 **모서리에서 82px** 어긋난다.
폰 화면 폭 338px 로 축소하면 약 11px 이다. **못 쓸 정도는 아니지만 안전구역 표시에는
크다.** 영상을 먼저 왜곡 보정해 핀홀로 만든 뒤 겹치는 쪽이 맞다.

## 거치 방향을 세로에서 가로로 바꿨다 (같은 날)

세로(9:16)로 달았을 때 **팔이 옆으로 뻗으면 화면 밖으로 나갔다.** 재보니 원인이 분명했다 —
세로로 달면 넓은 화각(73°)이 **세로로** 가고 가로에는 좁은 45.3° 만 남는다.

| 거치 | 팔 높이(+922mm)에서 보이는 가로 폭 | 팔 지름 1844mm |
|---|---|---|
| 세로 (9:16) | 1.32 ~ 1.55m | ❌ |
| **가로 (16:9)** | **2.19 ~ 2.45m** | ✅ |

세로로 맞추려면 66cm 를 더 물려야 했고 그러고도 해상도가 34% 나빴다. 가로로 돌리자
같은 자리에서 **0.95 mm/px** (오늘 최고)로 전 범위가 들어왔다.

**덤이 더 크다 — CSS 90° 회전이 사라졌다.** 돌아간 이미지 위에 오버레이를 얹으면
가운데만 맞고 모서리가 338~587px 어긋난다(`../2026-08-06/hud-brief-verify.md` §3).
겹치기의 선행 조건이 거치 방향 하나로 닫혔다. `main.css` `.cambody img` 에서 제거.

> 함정: 처음 가로로 돌렸을 때 **위아래가 뒤집혀 있었다**(실세계 수직이 화면 아래로 −89.8°).
> 앱 설정으로 돌리면 주점 `cx·cy` 가 바뀌어 내부 파라미터를 손봐야 한다 —
> **거치대에서 폰을 물리적으로 180° 돌리는 쪽**이 맞다. 그러면 내부 파라미터가 그대로다.

## 남은 것

- `AR/` 빌드 산출물에 옛 `fx 2106` 이 박혀 있어 지웠다 — **재빌드·재배포가 필요하다**
- `capture.py --auto` 에 기울기 문턱을 넣을지 (지금은 사람이 지켜야 한다)
- **로봇 베이스 위치를 태그 좌표계에서 재는 것** — 안전구역은 "로봇 기준 어디" 라서
  이게 없으면 구역을 그릴 수 없다. 지금 원점은 상판 태그 id0 다
- **팔이 화면 밖으로 나가면 경고** — 카메라 쪽으로 뻗으면 가까워져 프레임을 벗어난다.
  구역이 안 그려지는데 화면은 멀쩡해 보이는 게 제일 나쁜 실패 모양이다
