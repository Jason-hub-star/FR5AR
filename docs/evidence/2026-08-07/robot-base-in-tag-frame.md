# 로봇 베이스가 태그 좌표계 어디인가 — 밑판으로 풀었다

분류: 증거 · 2026-08-07 · 선행 `global-cam-calibrated.md`

## 결론 먼저

```
로봇 베이스   x 285   y -179   z 1.5 mm   yaw 177.1° (±1.2°)
              좌표계: 상판 태그 id0 중심 · z=0 은 태그 종이면
파생          TCP 방위(태그 좌표계) = j1 + 7.8°   ← 관절각에서 바로 쓴다
```

**서로 독립인 두 경로가 맞았다** — 밑판 기하 177.1° / 로봇 관절 분석 176.3~178.3°.
로봇 분석의 기여는 각도 자체가 아니라 **밑판이 못 정한 90° 배수를 확정한 것**이다
(정사각형은 yaw 가 90° 주기로 같아 보인다).

## 왜 사진만으로는 안 됐나 — 깊이가 안 잡힌다

카메라가 **하향 10.8°** 로 얕게 보고 있어 각도는 정확한데 거리가 약하다.
베이스 밑면 중심 픽셀을 여러 높이로 되쏘아 보면:

| 가정한 높이 | x | y |
|---|---|---|
| 0mm | 286 | -197 |
| 10mm | 286 | -220 |
| 30mm | 288 | -268 |

**x 는 높이와 무관하게 안정적이고(카메라가 y 방향에 있다) y 만 흔들린다** —
높이 10mm 오차가 위치 24mm 오차다. 실측값 하나가 반드시 필요했다.

## 두 번 실패한 것 — 흰 것 위의 흰 것

1. **베이스 지름으로 깊이 풀기 (149.0mm, URDF `base_link.STL` 에서 확인).**
   화면상 폭을 재려 했으나 흰 베이스가 흰 판 위에 있고 케이블이 가로질러
   스캔라인마다 106~220px 로 튀었다. 눈으로 읽은 값으로 역산하니 거리가 2.0m —
   실제 1.66m 와 20% 차이. **캘리브레이션이 아니라 픽셀 읽기가 틀린 것이었다**
   (같은 카메라 자세로 229mm 판을 되쏘니 실물에 정확히 겹쳤다)
2. **네 변을 다 쓰기.** 윗변이 로봇 몸통에 가려 검출 실패

## 된 방법 — 밑판 세 변 + 실측 두 개

주인님 실측: **밑판 한 변 229mm · 태그 종이보다 1.5mm 높음.**

판이 수평(볼트 고정 평판)이라는 조건을 넣고 미지수를 `x·y·yaw` 셋으로 줄인 뒤,
보이는 세 변에서 밝기 경계를 따라 표본 53점을 뽑아 최소제곱으로 맞췄다.

```
잔차 중앙값 2.32 px (≈ 2.2mm) · 90 백분위 9.45 px
```

**높이를 자유롭게 풀어도 z = -2mm 가 나와 실측 1.5mm 와 맞는다** — 서로 독립인 확인이다.

## 눈으로 확인

`calib-shots/tags/tags-20260807d.png` 에 229mm 정사각형을 되쏘았다.
왼쪽·아래·오른쪽 변이 실물 판 모서리에 붙는다 (윗변은 로봇 뒤라 확인 불가).

## 검산 — 줄자 **통과** (3.5mm · 1.0%)

**실측: 태그 id0 중심 → 밑판 모서리 = 335mm.** 로봇 몸통이 가운데를 막아 중심은 못 재고
모서리를 쟀다. 모델이 내는 네 모서리 (밑판 229mm · 중심 (285,-179) · yaw 177.1°):

| 모서리 | 태그 좌표 | ← id0 | ← id1 | ← id2 |
|---|---|---|---|---|
| **A** (id1 쪽) | (164.9, -287.6) | **331.5** ← 실측 335 | 163.9 | 525.8 |
| B (id0 쪽) | (176.4, -58.9) | 186.0 | 300.6 | 428.2 |
| C | (405.1, -70.4) | 411.2 | 465.9 | 209.7 |
| D | (393.6, -299.1) | 494.3 | 391.9 | 370.3 |
| (중심 · 못 잼) | (285, -179) | 336.6 | 309.4 | 366.1 |

**모서리 이름을 안 물어도 갈린다** — 335 를 낼 수 있는 모서리가 A 뿐이다. B 는 186mm 라
줄자 시작점을 태그 종이 안 어디에 놓든(중심에서 최대 182mm) 335 가 안 나온다. C·D 는
76~159mm 어긋난다. **A 로 읽고 331.5 vs 335 — 잔차 중앙값 2.2mm 인 맞춤에 걸맞은 차이다.**

### 이 검산이 실제로 잰 것 — yaw 가 아니라 **축척**이다

yaw 는 이미 서로 독립인 둘이 맞았지만(밑판 177.1° · 관절 176.3~178.3°) **둘 다 위치를
`밑판 한 변 229mm` 라는 주인님 실측 하나에 얹고 있었다.** 229 가 틀리면 x·y 가 비례해서
같이 틀리고, 두 경로가 사이좋게 같은 값으로 틀린다 — 교차검증이 못 잡는 종류의 오차다.
줄자가 이걸 밖에서 쟀고, 통과했다.

> 중심값 336.6 과 A 값 331.5 가 5mm 밖에 안 떨어져 있어 **"335 가 중심과 맞았다" 로 읽으면
> 안 된다** — 중심은 로봇이 올라앉아 있어 물리적으로 잴 수 없는 지점이다.

## yaw — 로봇을 안 움직이고 풀었다

`/connect` 는 observe-only 로만 열리고(움직임은 별도 `POST /arm`), 서보 OFF ·
조종권 없음 상태에서 읽기만 했다.

### 막힌 것 둘

1. **URDF 정기구학이 컨트롤러와 안 맞는다.** 같은 관절각으로 플랜지가
   URDF `[-49, 522, 565]` vs 컨트롤러 `[357, 11, -12]` — **871mm 차이.**
   영자세 정의가 다르다 (흔한 일). 링크 길이는 맞다 (152·425·395·102.1·102)
2. **`tcpMmDeg` 가 베이스 좌표계가 아니다.** 저장된 티치 지점이 `toolId: 1, userId: 1` —
   사용자 좌표계 1 기준이다. z 가 −11.6mm 로 베이스 면보다 아래로 나온 게 이 때문이다

### 뚫은 방법 — 저장된 티치 지점 두 개

`home` 과 `1` 은 **j1 만 20.80° 다르고 나머지 다섯 관절이 같다.** j1 은 베이스 z 축
회전이므로, 두 TCP 를 잇는 회전의 **중심이 곧 베이스 원점**이다.

```
회전 중심(사용자 좌표계)  (401.0, -497.2)
home 반지름 510.0mm · 방위 +94.91°   (j1 -95.83°)
1    반지름 510.0mm · 방위 +74.10°   (j1 -116.63°)
두 반지름 차 0.00mm          ← 모델이 맞다는 확인
```

### 사진 한 장으로 마무리 — 손목 지름이 갈랐다

관절각 `[-95.828, -87.677, 88.552, -87.652, -91.465, 20.147]` 자세를 찍고 광선을
**반지름 510mm 원기둥**과 교차시키니 교점이 둘 나왔다:

| 해 | 위치 | 상판 위 높이 | 카메라까지 | 손목(80mm)의 화면 크기 |
|---|---|---|---|---|
| **A** | (295, -689, 336) | **335mm** | 1152mm | **120px** ← 실측 113px |
| B | (221, 327, 30) | 29mm | 2215mm | 62px |

**`wrist3_link.STL` 의 지름 80mm 가 갈랐다.** 화면 손목 링이 113px 인데 해 B 라면
145mm 여야 한다 — 두 배 가까이 틀리다. **해 A 다.**

TCP 를 그리퍼 끝·몸통·어댑터·플랜지 어디로 잡아도 `C` 는 +6.8~+9.1° 안이다 —
**공구 원점을 몰라도 결과가 안 흔들린다.**

> 함정: 사진 직전 폰 IP Webcam 이 꺼졌고(ping 은 되고 8080 만 닫힘), 다시 켜니
> **해상도가 1920x1080 으로 되돌아가 있었다** (D64, 오늘 세 번째). 되잠그고 다시 찍었다.
> 그 사이 폰이 33mm 움직여 `extrinsics.py` 도 다시 돌렸다 (RMS 1.57px).
