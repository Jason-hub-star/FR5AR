# AMR 을 GLB 로 바꿀 값을 재다가, 발자국이 3.4배인 걸 찾았다

분류: 증거 · 2026-08-07 · 등재 `STACK.md` §TurtleBot3 겉치수 · 정본 `catalog.js` §AMR_MM

## 결론 먼저

```
질문   AMR 을 실물 터틀봇 GLB 로 바꾸면 폰이 감당하나
답     성능은 제약이 아니다 — 막장(2대에 800k삼각·300메시)까지 60fps
발견   그런데 지금 그리는 발자국이 실물의 3.4배였다.  이게 더 급했다
       화면 280 × 300 × 190mm  ←  Waffle Pi 발자국 + Burger 높이 + 라이다 덧높이
       실물 Burger  178 × 138 × 192mm  (사양서)
```

**GLB 로 바꿔도 발자국이 틀린 채면 여전히 거짓말이다.** 그래서 치수를 먼저 고쳤다.

## 1. 성능 — 감당된다 (측정)

AMR 2대의 내용물을 무게 있는 더미로 갈아 끼워 GLB 부하를 흉내냈다.
메시 수 = 드로우콜, 삼각형 수 = GPU. 그림자 패스까지 값을 물렸다.

폰 뷰포트 390×844 · **재생 중**(매 프레임 관절 얹기 + 컷어웨이) · **CPU 4배 스로틀**:

| AMR 무게 | 드로우콜 | 삼각형 | 프레임 |
|---|---|---|---|
| 지금 (상자+원통) | 865 | 416k | 16.6ms · 60fps |
| 줄인 GLB 12메시/15k | 913 | 483k | 16.7ms · 60fps |
| 보통 GLB 40메시/60k | 1025 | 675k | 16.7ms · 60fps |
| 안 줄인 STL 유래 120메시/250k | 1345 | 1.46M | 16.6ms · 60fps |
| 막장 300메시/800k | 2065 | 3.97M | 16.6ms · 60fps |

**착수 전 예측이 틀렸다** — "+80콜이면 +1~2ms" 로 적었으나 실제 **0ms** 였다.
이 규모에서 CPU 는 병목이 전혀 아니다.

⚠ **이 표가 증명하지 못하는 것** — CPU 스로틀은 GPU 를 느리게 하지 않는다. 헤드리스
Chrome 이 쓰는 맥 GPU 는 폰 GPU 보다 훨씬 세다. 따라서 위 숫자는 **드로우콜·JS 쪽 여유**를
증명하고, 4M 삼각형이 실제 폰에서 60fps 라는 뜻이 **아니다.** 보통 GLB(675k) 선까지가 안전선.

⚠ **AR 로 옮겨가지 않는다.** AR 은 같은 `layout-view` 를 쓰지만 폰에서 카메라·마커 추적을
동시에 돌린다. AR 까지 갈 거면 폰에서 따로 재야 한다.

### 성능 아닌 비용 셋 (GLB 를 실제로 붙일 때)

- `GLTFLoader` 가 지금 저장소 어디에도 없다 — 번들에 새로 들어간다 (`BUILD-VITE.md` 관할)
- `Shared/assets/` 는 `dist` 에 통째 복사된다 (기존 GAP OPEN) — GLB 무게가 그대로 실린다
- **D62 와 충돌한다** — 실물 GLB 는 자기 색·텍스처·로고를 들고 온다. 우회는 하나뿐:
  **형태만 쓰고 재질을 `mat.amr` 로 덮는다**

## 2. 발견 — 발자국이 Waffle 이었다

`TB-CONTRACT.md:15` 는 실물이 **Burger ×2** 라고 못박는데, `layout-view.js:395` 는
`BoxGeometry(0.28, 0.19, 0.3)` 였다.

| | 폭 | 깊이 | 높이 | 바닥 면적 |
|---|---|---|---|---|
| 화면 (전) | 280 | 300 | **280** (몸통 190 + 라이다 90) | 84,000mm² |
| Burger 사양 | 178 | 138 | 192 | 24,564mm² |
| 배수 | 1.57× | 2.17× | 1.46× | **3.42×** |

280 × 300 은 Waffle Pi 발자국(281 × 306)이다. 높이 190 은 Burger(192)에서 왔다 —
**두 기종을 섞은 값**이고, 거기에 라이다를 몸통 위에 얹어 전체가 280mm 가 됐다.

**이게 측정값인 이유** — 도킹 간격·통로 폭·간섭 판정이 전부 이 상자에서 나온다.
발자국이 3.4배면 "안 닿는다" 가 "닿는다" 로 뒤집힌다. 스타일 문제가 아니다.

## 4. 실물 GLB 로 교체했다 (같은 날 후속)

성능 판정이 났으니 붙였다. 자산은 `Shared/assets/turtlebot3_burger/burger.glb`,
출처·라이선스·다시 굽는 법은 같은 폴더의 `ATTRIBUTION.md`, 굽는 스크립트는
`scripts/build/burger-glb.py` (Blender 5.1).

```
원본 STL 4장 7.72MB · 154,434 삼각  →  GLB 1장 750KB · 9,879 삼각 · 메시 1개
```

**드로우콜이 오히려 줄었다 (2 → 1).** 부품 4개를 굽는 단계에서 합쳤기 때문이다.
런타임에 4장을 받아 URDF 관절 원점으로 자리를 잡으면 그 일이 매번 화면에 들어온다.

### 규약을 지키려고 한 것

- **재질을 안 실었다** (`export_materials='NONE'`) + 화면에서 `mat.amr` 로 한 번 더 덮는다.
  GLB 가 자기 색을 들고 오면 D62(화이트 모형)가 깨진다. 두 겹으로 막아 자산이 바뀌어도 안 흔들린다
- **원점 = 바닥 중앙 · 정면 = +Z** (`parts.js` 머리 규약). ROS 는 Z-up·X-forward 라 Z −90° 를 구웠다
- **대체 상자를 안 지웠다.** GLB 는 네트워크를 타니 늦게 오거나 안 올 수 있고, 그때 AMR 이
  사라지면 배치 판단 근거(발자국·도달 링)가 같이 사라진다 — 팔이 실패하면 도달 링만 그리는
  그 규약과 같다 (D15·D18)
- **Draco 를 안 썼다** — 144KB 로 줄지만 WASM 디코더(~200KB)를 또 받아야 해 합계로 손해다

### 검증 9/9

```
겉치수        178 × 140 × 191mm · 바닥 접지 0     (사양 178×138×192 · 감량 오차 ±2mm)
방향          깊이 140 < 폭 178 — 축을 안 뒤집었다
메시·삼각형   2대 모두 메시 1개 · 9,879 삼각
반복 편집 5회  삼각 9,879 유지 — 빈 껍데기가 안 된다
자산 차단     대체 상자 복귀 (178×138×192) + 콘솔 경고 "터틀봇 메시를 못 불러왔다"
게이트        all.sh 21/21 · exit 0
```

`clone()` 이 지오메트리를 **공유**하는데 `dispose()` 가 root 를 훑어 전부 지운다 —
그대로 두면 두 번째 편집부터 터틀봇이 빈 껍데기가 됐다. FR5 팔이 밟은 그 함정이라
지오메트리를 복사한다. 위 "반복 편집 5회" 가 그걸 지키는 검증이다.

### 두 번 밟은 함정 (다음 사람 몫)

1. **STL 은 밀리미터, URDF 원점은 미터다.** 안 맞추면 바퀴가 0.08mm 만 벌어져 몸통에
   파묻히고 폭이 178 대신 147.8 이 된다. 첫 판이 그랬다
2. **`layout-view.js` 는 Node 에서도 돌아간다.** `xr-place`·`ar-render` 게이트가 겹치기 기하만
   계산하려고 이 모듈을 불러서, `GLTFLoader.load` 가 기준 URL 없이 던지고 **미처리 거부로
   게이트가 죽었다.** 이 파일 머리 규약이 이미 "자산 로딩은 이 모듈이 하지 않는다" 고 적어 뒀었다.
   `typeof document === 'undefined'` 로 막고 동기 throw 까지 한 자리로 모았다
3. ⚠ **게이트가 죽으면 헤드리스 Chrome 이 고아로 남는다.** `p.close()` 를 못 부르고 죽으므로
   CDP 포트(9353 등)를 계속 쥐고, **다음 판이 그 낡은 탭에 붙어** `__xr` 을 영영 못 본다.
   증상이 코드 결함처럼 보인다 (`WebXR 겹치기` 69건이 통째로 빨간불). 처방:
   `pkill -f "remote-debugging-port=9" && rm -rf /tmp/cdp-profile-9*`

## 5. "터틀봇 드래그가 어떨 땐 되고 어떨 땐 안 된다" — 원인은 축척이다

**증상은 사실이고, 원인은 메시가 아니라 화면 크기였다.** 가설을 셋 세웠고 **셋 다 측정이 부정했다.**

### 측정 — 기본 시점의 축척

```
1000mm  =  35.8 px      →  1 px ≈ 28mm   (캔버스 1068×529)
AMR 폭  178mm =  6.1 px
AMR 깊이 138mm =  7.6 px
도달 링 반경 380mm = 13.1 px
interaction.js §SNAP_PX 근접 보조 = 20 px
```

**보조 원(20px)이 로봇(6~8px)보다, 심지어 도달 링(13px)보다 크다.** 그래서 픽은 실루엣이
아니라 보조 원이 전부 담당한다. 격자로 눌러 본 지도가 그대로다 — 잡히는 모양이 로봇
모양이 아니라 원이다:

```
amr1 중심 기준 ±30px · 10px 간격        ● amr1  · 아무것도  d 문  f 격벽  p 팔레트
dy=-30   d  ·  ·  ·  ·  ·  ·
dy=-20   d  ·  ●  ●  ●  ·  ·
dy=-10   d  ●  ●  ●  ●  ●  ·
dy=  0   d  ●  ●  ●  ●  ●  ·
dy= 10   d  ●  ●  ●  ●  ●  ·
dy= 20   f  ·  ●  ●  ●  ·  ·
dy= 30   f  p  ·  ·  ·  ·  ·
```

**빗나가면 뒤에 있는 큰 것이 가져간다.** amr1 도킹 자리(700, 2500)가 서쪽 벽 근처라 문이
바로 뒤에 있고, 문은 `fixed: true` 라 끌리지도 않는다 — 그래서 "가끔 아무 일도 안 난다"
로 보인다. 발자국을 실물로 줄이며(280×300 → 178×138) 과녁이 10px → 6~8px 로 더 작아졌다.

### 폐기한 가설 셋 — 남겨 두는 게 값지다

| 가설 | 어떻게 부정됐나 |
|---|---|
| 놓기(pointerup)와 렌더 틱의 경합 | 놓기 지연 0·1·8·20·100ms 전부 실패 (5/5). 지연과 무관 |
| 실물 메시 플레이트 틈으로 광선이 빠진다 | 투명 히트박스를 넣었는데 **픽 지도가 한 칸도 안 변했다.** 당겨서 A/B 해도 동일 — GLB 가 같은 부피를 채우니 넓어질 게 없다. **넣은 코드를 지웠다** |
| 커밋 경로가 AMR 을 안 받는다 | `LayoutEditor.jsx:443` 이 `dockPosMm` 을 쓴다. 코드로 확인 |

### 판정 못 한 것 — 도구가 못 닿았다

드래그가 **커밋까지 되는지**는 헤드리스로 판정하지 못했다. 두 방식을 썼는데 둘 다
**대조 실험에서 소품(convA)조차 안 움직였다** — 즉 앱이 아니라 주입이 문제다:

- CDP `Input.dispatchMouseEvent` — 픽은 도달(`pickedId` 가 바뀐다), 드래그는 안 됨
- JS `PointerEvent` 를 캔버스에 디스패치 — 픽조차 안 됨

**대조 실험을 먼저 했어야 했다.** 그걸 안 해서 앱 결함으로 오독한 가설 두 개를 세웠다.
`dash-web-verify.mjs` 의 마커 끌기는 `PointerEvent` 로 되는데 3D 캔버스 끌기는 안 되므로,
**3D 끌기를 게이트로 잠글 방법이 아직 없다** — 그게 이 증상이 오래 산 이유이기도 하다.

### 처방 (미적용 — 결정 필요)

1. **당겨서 고른다.** 코드 변경 0. 1.4m 까지 당기면 로봇이 45px 가 되어 쉽게 잡힌다
2. **아주 작은 것만 보조 반경을 키운다** — `SNAP_PX` 를 크기에 따라 20 → 30px 로.
   `SMALL_M` 게이트가 이미 있으니 큰 가구끼리 클릭을 훔치는 문제는 안 돌아온다.
   단 작은 것끼리는 서로 훔칠 수 있어 실렌더 재측정이 필요하다
3. **3D 끌기 게이트를 만든다** — 위 "판정 못 한 것" 이 닫히지 않으면 같은 증상이 또 온다

## 확인하지 않은 것

- **줄자 실측을 안 했다.** 사양서 값이다. 실물이 랩에 있으면 실측이 정본이다
- **LDS-01 자체 치수 미확인.** 몸통/라이다 쪼개는 비율 `LIDAR_H = 40mm` 는 근거 없는 편의값이라
  `ponytail:` 주석으로 천장을 적어 뒀다. 실측이 오면 그 한 줄만 바꾸면 겉면은 유지된다
- **`reachMm 380` 은 손대지 않았다** — 사양이 아니라 우리가 정한 작업 반경이다. 발자국이
  1/3.4 로 줄었으니 이 값이 여전히 타당한지는 **따로 볼 일**이다 (도달 판정의 입력)
- **폰에서 안 재봤다.** 감당 판정은 CPU 4배 스로틀이고, 그건 GPU 를 안 느리게 한다.
  AR 은 카메라·마커 추적을 같이 돌리므로 **AR 판정은 폰이다** (`AR-DEBUG.md` §6)
- **감량 하한을 넘겨 보지 않았다.** 10,000 아래로 내리면 겉치수가 깎인다(7,948 에서 높이 −5mm).
  더 줄여야 하면 겉치수를 다시 재고 `AMR_MM` 과 대조해야 한다
