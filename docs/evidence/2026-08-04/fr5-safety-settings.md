주인님이 화면에서 ARM(조종권 `admin`). 브리지가 서보 ON 직후 설정을 넣고 되읽었다.

|---|---|---|---|
| `payloadKg` | 0.6 (그리퍼 사양) | **0.6000000000000001** | 일치 (허용 오차 0.05) |
| `cogMm` | [0, 0, 60] | **[0.0, 0.0, 60.0]** | 일치 |

| `toolCoord` (참고 읽기) | — | **[0, 0, 135, 0, 0, 0]** | 아래 §예상 밖 |

`mismatch: []` — 되읽을 수 있는 항목은 전부 일치했다. **실기가 우리 설정을 받아들인다**는
것이 확인됐고, 이제 조건 4·5(충돌)가 판정할 값이 만들어지는 상태다.

## 예상 밖 둘 — 참고로 읽은 값에서 나왔다

### ① `GetJointSoftLimitDeg` 의 단위는 도(°)다 — 그리고 j3 는 우리가 더 넓었다

SDK 주석은 단위를 **mm** 로 적어 놨다(함수명은 Deg). 모순이라 신뢰도가 낮다고 문서에
적어 뒀는데, 실측값이 답을 줬다:

```
[-175,175, -265,85, -160,160, -265,85, -175,175, -175,175]
```

우리 `JOINT_LIMITS_DEG` 와 **j3 만 빼고 전부 정확히 일치**한다 — 우연일 수 없으므로 도(°)다.
그리고 **j3 는 컨트롤러가 ±160 으로 우리(±162)보다 좁다.** 우리가 더 넓으면 컨트롤러가
거부할 목표를 게이트가 통과시킨다 → **좁은 쪽으로 맞췄다** (`safety.py`).

브리지 로그에도 남았다: `soft-limit-diff j3 컨트롤러 [-160.0, 160.0] vs 우리 [-162.0, 162.0]`.
**대조를 코드에 넣은 그날 바로 걸렸다.**

### ② 툴 좌표계 0 번에 이미 Z 135mm 가 들어 있다

`toolCoordId: 0` 인데 `GetCurToolCoord` 가 `[0, 0, 135, 0, 0, 0]` 을 준다.
매뉴얼상 툴 0 은 "툴 없음(플랜지 중심)" 인데, 이 개체는 **누군가 그리퍼 길이로 보이는
오프셋을 넣어 둔 상태**다.

- 계약에 "화면 TCP 는 플랜지 기준" 이라고 적어 뒀는데 **그 서술이 이 개체에서는 틀렸다** —
  TCP 값은 이미 135mm 오프셋이 적용된 값이다
- **누가 어떤 근거로 넣었는지 모른다.** 그리퍼 실측과 일치하는지 미검증 → GAP OPEN
- 지금 동작에는 영향이 없다 (관절값 저장 + `MoveJ` 재생 조합)
