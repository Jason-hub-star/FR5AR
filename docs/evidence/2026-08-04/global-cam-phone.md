# 글로벌 카메라 — 갤럭시를 카메라로 붙이고, 수동 초점이 거짓말인 것을 잡았다 (2026-08-04)

분류: 증거 · 게이트: `scripts/map/cam-lock.sh` · 대상: Galaxy S24+ (SM-S926N) · IP Webcam

**하드웨어 블로커가 풀렸다.** 640×480 USB 웹캠 대신 갤럭시가 2560×1440 을 준다.
그리고 하루의 대부분을 잡아먹은 "검출 0" 의 범인은 인쇄물도 높이도 아니라
**이 폰의 수동 초점이 실제 렌즈를 안 움직인다는 것**이었다.

## 붙이는 경로

| | 값 |
|---|---|
| 앱 | IP Webcam (`com.pas.webcam`) — MJPEG + HTTP 설정 API |
| 유선 | `adb forward tcp:8080 tcp:8080` → `http://localhost:8080/video` |
| 무선 | `http://<폰IP>:8080/video` — 같은 값이 그대로 돈다 |
| 처리량 | 유선 57.4 fps · 무선 56.8 fps (1080p · 90프레임 · 실패 0) |

**무선이 유선과 같다.** 케이블 길이가 설치를 제한하지 않는다.
유선의 남는 이점은 충전 동시(발열 시 폰이 스스로 화질·프레임을 깎는다)와
캠퍼스 망 정책 무관 둘이다. `localhost` 는 보안 출처라 https 배포본에서도
혼합 콘텐츠로 안 막히지만, 무선(`192.168.x.x`)은 막히므로 로컬 dev 로 열어야 한다.

## 범인 — `focusmode=off` + `focus_distance` 는 **되읽어도 참이 아니다**

| 상태 | 되읽은 `focus_distance` | 선명도 | ChArUco 코너 |
|---|---|---|---|
| 자동초점이 맞춘 직후 | 0.30 | **954** | **35/35** |
| 거기서 `focusmode=off` 로 "고정" | 0.30 (같다) | **36** | **0/35** |

**숫자는 요청한 대로 돌아오는데 렌즈는 거기 없다.** 되읽기 확인이라는 원칙은 맞았지만
확인한 대상이 기기가 말하는 값이었다 — 그건 검증이 아니라 메아리였다.
이 하나 때문에 보드 크기·카메라 높이·인쇄 품질을 차례로 의심하며 판을 여러 번 버렸다.

**고친 절차** — 자동초점을 **측정 도구로 한 번만** 쓴다.

```
focusmode=auto  →  /focus 트리거  →  약 8초 수렴  →  그대로 둔다
```

`/nofocus` 를 걸어도 950대를 유지했다. 고정 카메라는 장면이 안 변하니 다시 헤매지 않는다.
**판정은 되읽은 다이옵터가 아니라 실제 프레임의 라플라시안 분산 수렴**으로 한다
(`cam-lock.sh` 가 `397 → 394 → 394 → 395` 처럼 찍는다).

## 해상도 — 1440p 가 최적점

같은 A4 ChArUco(6×8 · 28mm) · 같은 자리 · 초점 맞춘 상태:

| 해상도 | fps | 코너 | 마커 |
|---|---|---|---|
| 1920×1080 | 48.6 | 28/35 | 21 |
| **2560×1440** | **35.3** | **35/35** | **24** |
| 3840×2160 | 12.3 | 35/35 | 24 |

4K 는 검출이 같은데 fps 만 3분의 1이다. **A3 재인쇄는 필요 없다** — 검토했다가 접었다.

부수 실측 — 마커가 20px 아래로 내려가면 확대해도 안 살아난다(4배 확대에 24장 중 6장).
36h11 해독에는 **마커 한 변 32~40px** 이 필요하다. 대비(명도차 129)나 검출 파라미터
문제가 아니라 정보량 문제다 — CLAHE·정규화 스트레치 모두 0장이었다.

## `cam-lock.sh` — 찍기 전 매번 돌린다

해상도·화질·화이트밸런스·줌·초점을 잠그고 **되읽어 확인**한다.
실측으로 잡아낸 것들:

- 세션 도중 IP Webcam 이 재시작해 `quality 90→49` · `focusmode→continuous-video` ·
  `whitebalance→auto` 가 **조용히 되돌아가 있었다.** 화면에는 아무 표시가 없다
- 케이블을 다시 꽂으면 `adb forward` 가 사라진다 → localhost 경로면 자동으로 다시 건다
- 먼 초점은 다이옵터 0.1 눈금이라 3400mm 요청이 5000mm 로 잘린다 (게이트가 FAIL 로 잡음)
- 같은 값을 다시 넣으면 카메라가 재시작하므로 **다른 것만** 바꾼다
- 해상도를 바꾼 직후 `status.json` 은 **키가 빠진 채** 돌아온다 → 돌아올 때까지 기다린다

## 겹치기 화면이 **대시보드 배치안**을 받는다 (`AR/cam.html`)

전에는 `cam.js` 안에 배치안이 하드코딩돼 있었다 — 고정물 전용 화면이었다.
셋을 밖에서 받게 바꿨다. **전부 URL 로 넘어가 링크 하나로 재현된다.**

| 파라미터 | 무엇 |
|---|---|
| `?feed=<MJPEG URL>` | 카메라 영상. 없으면 합성 고정물 |
| `?scene=<JSON URL>` | 대시보드 **내보내기** 산출물 그대로. 파일 선택·`localStorage` 도 된다 |
| `?fit=WxD&anchor=x,y` | 태그 사각형(mm)에 맵을 **맞춰 줄인다** |

**배율이 필요한 이유** — 배치안은 12m 방인데 강의실은 3m 다. 1:1 로 겹치면 벽이 방을
뚫고 나간다. 태그를 놓은 사각형에 맵을 넣으면 **태그 배치가 곧 맵 크기**가 된다.
`min(W/floorW, D/floorD)` 로 **균일 스케일만** 쓴다 — 가로·세로를 따로 맞추면 로봇이
찌그러지고, 그 화면으로 도달 범위를 판단하면 틀린 판단을 한다.

**배율을 화면에 늘 적는다** (`1:2.5 축소 — 실물 크기 아님`). 줄어든 것은 도달 범위 링도
마찬가지인데, 표시가 없으면 "저 링 안이면 안전하다"로 읽힌다.

캘리브레이션 파일은 `import.meta.glob` 으로 읽는다. `intrinsics.py` 의 산출물이라
**캘리브레이션 전에는 정상적으로 없고**, 정적 import(D18)로 두면 그때까지 빌드가 깨진다.
없으면 고정물로 떨어지고 **화면이 노란 글씨로 "합성 고정물"이라고 말한다.**

![배율 겹치기](cam-scene-fit.png)

### 판정 — `node scripts/check/cam-web-verify.mjs` · **12/12**

눈으로 보지 않는다. 합성 사진에서 태그를 **cv2 로 다시 검출**해 얻은 중심과, 화면이
실제로 쓰는 카메라로 실험실 좌표를 투영한 픽셀을 대조한다.

| | 결과 |
|---|---|
| **정합 (스테이션 좌표 ↔ 사진 속 태그 중심)** | **최대 0.80px** — S4 실측 0.83px 재현 |
| 배치안이 파일에서 올라온다 | 하드코딩 제거 확인 |
| fit 배율 · 균일성 · 앵커 | 3000×1600 → `fit=1200x800` = **0.40** · x=y=z · `planToScene` 규약대로 |
| 슬래브 숨김 · 배경 투명 · 캔버스 | 영상이 비친다 |
| 합성 고정물 경고 | 노란 상태 표시 |

고정물의 배치안도 이제 `make-fixture.py` 가 사진과 **같이** 낸다 — 태그 자리를 화면 쪽에
다시 적으면 사진과 배치안이 조용히 어긋나고, 그러면 겹침이 틀린 건지 코드가 틀린 건지 못 가른다.

## 확인하지 않은 것

- **`intrinsics.py` 를 아직 안 돌렸다.** 코너 35/35 는 한 장 기준이고, 15~20장의
  재투영 RMS(≤0.5px)는 미측정이다. 자동초점이라 **장마다 렌즈 상태가 다를 위험**이 남는다 —
  보드 거리를 크게 바꾸지 말고 각도·화면 위치 위주로 찍어야 한다. 이 위험은 게이트가 잡는다
- **화각을 안 쟀다.** 검출 코너 간격으로 역산한 수평 44° 는 추정이고, 1080p 와 1440p 의
  화각이 같은지도 미확인이다. 다르면 해상도를 바꿀 때 내부 파라미터를 그냥 스케일할 수 없다
- **카메라 높이·설치 거리 미측정.** 줄자가 없었다. `extrinsics.py` 의 출력이지 입력이 아니라
  진행에는 지장이 없다
- **태그(AprilTag) 실기 검출은 아직 안 했다.** ChArUco 픽셀 대응에서 환산하면
  1440p 에서 약 17 px/칸(안전선 5.0)이지만 **환산이지 실측이 아니다**
- 렌즈 왜곡 · 라이브 MJPEG 겹치기 · 지연 보정 — 전부 그대로 열려 있다
- **겹치기 화면을 실측 캘리브레이션으로 돌린 적이 없다.** 12/12 는 전부 합성 고정물이다.
  `?feed=` 로 라이브 MJPEG 을 꽂아 본 적도 없다 (스트림 주인 계약이 먼저다 — 하드 룰 1)

# 다른 길 — WebXR 로 마커 없이 정합

화면 `AR/xr.html` · 기기 Galaxy S24+ (Android 16) · Chrome + ARCore 1.54

**된다.** 준비 0으로 20초 만에 실제 크기가 나왔다. 오차는 **보통 ±2%, 가끔 8%**.
같은 날 마커 방식은 하루를 쓰고도 축척을 확정하지 못했다.

## 왜 열려 있었나 — 제약을 잘못 물려 뒀다

마커를 고른 이유는 `AR-MARKER.md` 의 **"iOS 사파리가 `immersive-ar` 을 안 열어준다"** 였다.
팀원이 각자 폰으로 보는 화면이라 그게 맞았다.

그런데 **고정 카메라는 기기가 하나다 — 우리가 정한 갤럭시.** 남의 아이폰을 신경 쓸 이유가
없는데, "AR" 이라는 같은 이름 때문에 두 개의 다른 문제가 한 제약으로 묶여 있었다.

| | 폰을 들고 보기 | 고정 카메라 |
|---|---|---|
| 기기 | 아무 폰 (iOS 포함) | **우리 폰 하나** |
| 그래서 | 마커 | **WebXR** |

## 잰 방법

줄자 **1000mm** 를 평면에 펴고, 조준선을 양 끝에 맞춰 탭해 두 점 사이 거리를 읽었다.
정답이 있는 길이를 재야 채점이 된다 — 아무 데나 두 번 찍으면 나온 숫자를 판정할 수 없다.

- 길이를 **1m 로** 잡은 이유: 탭 정확도가 ±10mm 쯤이라 300mm 를 재면 오차가 3~7% 로
  잡음에 묻힌다. 1m 면 1~2% 다
- 평면은 **바닥이 아니어도 된다.** 축척 시험은 어느 평면에서도 성립한다 (책상 위 1m 도 1m).
  실제로 바닥 평면이 잘 안 만들어져 책상에서 쟀다

## 결과

| 회차 | 잰 값 | 오차 | 두 점 높이차 |
|---|---|---|---|
| 1 | 987 mm | −1.3% | 4mm |
| 2 | 1019 mm | +1.9% | 0mm |
| 3 | 1012 mm | +1.2% | 0mm |
| 4 | **918 mm** | **−8.2%** | 6mm |

평균 984mm · 표준편차 40mm. **넷 중 셋이 ±2% 안.**

부수 실측 — `immersive-ar` 지원 true · 평면 검출 3.5~19.7초 · 앱 설치 불필요
(Chrome 웹페이지) · HTTPS 필수.

### 튄 판은 **미리 알 수 있었다**

4회차 세션만 평면 높이가 흘렀다 — `345 → 351 → 241mm`. 앞의 세 판은 0~6mm 로 붙어 있었다.
**추적 품질이 화면에 드러나 있었던 것**이라, 구현에서는 세 번 찍어 중앙값을 쓰고
평면이 흔들리면 다시 찍게 한다. 오늘 마커 쪽에서 없어서 하루를 태운 바로 그 장치다.

## 이 정확도로 되는 것 / 안 되는 것

| | |
|---|---|
| ✅ 맵을 방에 겹쳐 보기 · 배치 감각 · 시연 | 3m 에서 60mm — 눈에 안 거슬린다 |
| ✅ AMR 경로 · 스테이션 위치 | 충분 |
| ⚠ "이 링 안이면 닿는다" 판정 | 안전 여유를 그만큼 크게 잡아야 한다 |
| ❌ mm 단위 정렬 | 마커가 필요하다 |

**마커와 배타적이지 않다.** 정합은 WebXR 이 하고, 원점을 매번 같은 자리에 두거나 로봇
좌표계와 이어야 할 때 **마커 한 장**을 더한다. 그때 그 한 장은 축척을 안 맡으므로
**크기를 잴 필요가 없다** — 오늘 145/155/160mm 로 하루를 태운 그 문제가 사라진다.

## 만들면서 밟은 함정 둘 (코드에 주석으로 박음)

- **dom-overlay 루트가 화면을 덮으면 탭을 DOM 이 먹는다.** `select` 가 한 번도 안 왔다.
  루트를 크기 0 짜리 껍데기로 두고 조준선만 `position:fixed` 로 띄워 해결
- **점은 폰이 겨누는 방향에 찍힌다** (`space: viewer`). 손가락으로 화면을 짚는 게 아니다 —
  조준선이 없으면 반드시 헷갈린다. 실제로 같은 자리를 두 번 찍어 4mm 가 나왔다

그리고 **막지 말고 알려야 한다.** 바닥이 아니면 탭을 거부하게 했더니 바닥 평면이 안
만들어지는 상황에서 아무것도 못 하게 됐다. 지금은 높이를 적고 경고만 한다.

## 맵을 얹고 팔을 켰다 — **폰 성능은 문제가 아니었다**

`AR/xr.html` 에 배치안(프리셋)·팔 대수·애니메이션을 폰에서 고르게 하고 fps 를 로그에 남겼다.
팔은 `createLayoutView` 가 자리만 만들고 화면이 얹는 구조라 대수를 그냥 고르면 된다.

| 설정 | fps 중앙값 | 최저 |
|---|---|---|
| 팔 1대 | 90 | 74 |
| 팔 1대 + 애니메이션 | 90 | 85 |
| 팔 2대 | 90 | 76 |
| **팔 2대 + 애니메이션** | **90** | **78** |

**전부 90fps(화면 상한)에 붙어 있고 최저도 74 아래로 안 내려갔다.** 삼각형 128,808 × 2 에
팔마다 다른 관절 재생까지 얹은 상태다 — `GAP-MATRIX` 의 "URDF 두 벌의 비용 미측정"은
**여유 있게 닫힌다.** 두 번째 팔을 저해상도로 대체할 이유가 없다.

부수 실측 — URDF 첫 로딩 **3.4초**, 이후 캐시로 0.1~0.2초. 평면 검출이 **1.3초**로 빨라졌다
(같은 방을 이미 훑은 뒤라 그렇다 — 첫 세션의 18~19초와 대비된다).
맵을 놓은 높이가 −26 ~ −68mm 로 모여 **바닥에 일관되게 얹혔다.**

**애니메이션은 팔마다 다르게 준다** — 1번 `home↔grip`(3.2초), 2번 `lowIdle↔lowBelt`(4.6초).
같은 동작을 두 대가 하면 "두 대가 도는가"는 알아도 "각자 다른 동작이 되는가"는 모른다.

### 잡은 버그 — 팔이 바닥에 누웠다

`loadRobot()` 이 준 URDF 를 팔 자리에 **그대로** 붙였더니 팔이 누웠다.
**URDF 는 Z-up, three.js 는 Y-up** 이라 −90° X 회전을 감싸야 한다 —
`ar.js` 의 `stage`, `Dashboard/…/LayoutView.jsx` 의 `holder` 가 이미 같은 규약인데
새 화면에서만 빠뜨렸다. 같은 규약을 **세 곳이 각자 적고 있는 것**이 진짜 원인이다.

수학은 확인했다 — 감싼 뒤 URDF 의 `+Z` 가 월드 `(0, 1, 0)` 이 된다.
**눈으로는 아직 못 봤다** (배포본을 폰에서 다시 열어야 한다).

## 촬영·평소 두 모드로 갈랐다 (2026-08-05)

포트폴리오 영상은 실물 3250×3250 맵에서, 평소 테스트는 아무 바닥에서 — 역할을 나눴다.
**두 모드의 차이는 배율 숫자 하나뿐이다.** 렌더 경로를 가르면 평소 테스트가 촬영본을
검증해 주지 못하고, 갈라진 쪽이 정작 촬영 날 깨진다 (D17 의 실패 모양).

| | 촬영 | 평소 |
|---|---|---|
| 배율 | `1.0` → 두 모서리가 보정 | `2500 / 가장긴변` |
| 놓는 법 | 마주보는 두 모서리 탭 | 한 번 탭 + 버튼 |
| 계기 | 놓는 순간 끈다 (로그엔 남는다) | 켠 채로 |

**두 모서리가 위치·회전·배율을 한 번에 낸다.** `layout-view.js` 가 root 원점을 평면도
원점에 두므로 첫 탭에 anchor 를 놓으면 그대로 맞는다. 배율은 **잰 대각 ÷ 참값 대각**이다
— 실물 대각선을 우리가 아니까 **맵 자체가 자(尺)**가 되고, WebXR 축척 오차가 그 자리에서 지워진다.

폰에 올리기 전에 계산으로 검증했다 (회전 0·30·−110·180° × 축척 0.987·1.019·1.0):
**복원 yaw 오차 0.0000° · 배율 오차 0.0000% · 모서리② 어긋남 0.000mm.**
이 검증이 부호 오류를 잡았다 — three.js 의 Y 회전은 `atan2(z,x)` 를 **깎기** 때문에
`yawLocal − atan2` 여야 한다. 폰에서 봤으면 "맵이 반대로 돌았다"로 보였을 것이다.

**지나가다 잡은 것** — 다른 세션이 `poses.js` 의 `POSES` 를 `PRESET_POSES` 로 바꿔
`xr.js` 가 이미 빌드 불가 상태였다. 배포본이 리팩터 전 빌드라 살아 있었을 뿐이다.

### 배포가 원격 빌드로는 안 된다

Vercel 이 `AR/` 만 올려 받아 `npm install` 이 형제 워크스페이스 `@fr5/shared` 를
npm 레지스트리에서 찾다가 404 로 죽는다. **로컬 빌드 + prebuilt 업로드**가 이 저장소의 절차다.

```bash
cd AR && vercel build --prod && vercel deploy --prebuilt --prod --yes
vercel alias set <새 배포 URL> fr5ar.vercel.app     # 별칭은 따로 걸어야 한다
```

`vercel.json` 의 `Permissions-Policy: camera=(self)` 는 이 경로에서도 실린다 — 응답 헤더로 확인했다.
**별칭을 안 걸면 새 배포가 Ready 여도 `fr5ar.vercel.app` 은 옛것을 준다** (이번에 실제로 그랬다).

### 화면 기록이 XR 화면을 담는다

포트폴리오 계획의 관문이었다 — `immersive-ar` 의 카메라 영상은 우리 캔버스가 아니라
**시스템이 바깥에서 합성**하므로 앱 안에서 `canvas.captureStream()` 으로는 배경이 안 담긴다.
기기에 따라 OS 화면 기록도 보호된 표면으로 처리해 검게 나올 수 있었다.

**갤럭시 빠른 설정의 `화면 기록`으로 기록됐다.** 외부 카메라로 폰째 찍는 대안은 안 써도 된다.

## 확인하지 않은 것

- **팔이 선 것을 눈으로 확인하지 않았다** — 축 계산만 맞췄다
- **터틀봇 모델이 저장소에 없다** — ROBOTIS URDF 에서 변환해야 한다. 팔 2대가 90fps 이니
  예산은 충분하다
- 배치안을 **씬 파일로** AR 에 넣어 보지 않았다 (프리셋만 굴렸다)
- 평면 검출이 3.5~19.7초로 편차가 크다. 현장에서 이 대기가 어떻게 느껴지는지 미확인
- 걸어다니며 오래 쓸 때의 **드리프트** 미측정 (한 자리에서만 쟀다)
- iOS 미확인 — 될 리 없지만 화면이 그 사실을 어떻게 말하는지 안 봤다
