# 관제화면이 저작 도구가 됐다 — 시점 · 시나리오 · 자세 · 경로 (2026-08-04)

무대(조립 라인)를 짓는 이야기는 `assembly-line.md`. 이 문서는 **사람이 무엇을 고칠 수
있게 됐나**만 다룬다. 순서대로 시점 → 시나리오 저장 → 자세 저작 → AMR 경로다.

전부 헤드리스 CDP 로 **실제로 눌러서** 확인했고, 게이트마다 **결함을 주입해 빨개지는 것**까지
봤다 — 통과만 본 것은 게이트가 아니다.

## 시점이 화면을 안 채우고 있었다 (2026-08-04 추가)

방이 좁아서가 아니었다. **놓인 것이 방의 95%(가로)·86%(세로)를 이미 채우고 있다.**
좁았던 것은 방이 아니라 **화면 속 방**이다.

`stage.js frame()` 이 `dist = r / tan(fov/2)` 로 **세로 화각만** 봤다. three.js 의 `fov` 는
세로라서 **한 코드가 정반대 두 방향으로 틀렸다.**

| | 가로 1600×900 | 세로 900×1600 |
|---|---|---|
| 전 | 가로 0.307 · 세로 0.443 — **화면의 13.6%** | 가로 **1.403 — 양옆 40% 잘림** |
| 후 | 가로 0.664 · 세로 0.901 — **59.8%** | 가로 0.935 · 세로 0.283 |

원인이 셋이었다.

1. **종횡비를 안 봤다** — 가로 화면에선 남고 세로 화면에선 넘쳤다
2. **`max(size.x, size.z)` 를 세로 화각에 예약했다** — 45° 대각에서 그 축은 화면에서
   대각선으로 눕는다. 세로로 필요한 건 절반도 안 되는데 통째로 비웠다. **낭비의 대부분**
3. **방향 벡터 `(0.75, pitch, 0.75)` 를 정규화하지 않았다** — 길이가 1.141 이라 늘 14% 뒤

지금은 AABB 8모서리를 카메라 축으로 분해해 **두 화각을 동시에** 만족하는 최소 거리를 낸다.
짐작이 없어져 `pad` 는 1.35 → **1.06**(순수 여유분)이 됐다.

**한 겹을 더 얹었다.** 첫 판에서 위 27% · 아래 3% 로 여백이 한쪽에 쏠렸다 — 비스듬히 본
상자는 화면에서 대칭이 아니라 **상자 중심을 겨누면 한쪽만 화면 끝에 닿는다.** 투영된 상자의
가운데를 다시 겨누자(2회 반복) 세로 점유가 0.698 → **0.901** 이 됐다.

그리고 시점을 **배치안마다 한 번만** 잡고 있었다(`framedRef`). 창을 키워도 방은 그대로
작았다. `ResizeObserver` 에서 비율이 바뀌면 다시 잡는다.

### 게이트를 깨뜨려 봤다

`dash-web-verify.mjs` §13. 원래 버그(종횡비 무시)를 그대로 주입하니

```
세로 화면 — 화면 밖으로 안 잘린다   FAIL  여백 -0.447 / -0.45 / 0.237 / 0.233
가로 화면 — 빡빡한 축이 85% 이상    FAIL  가로 0.454 · 세로 0.53
```

**잘림 0 이 먼저고, 그 다음이 빡빡한 축의 하한(85%)이다.** 반대 축에는 하한을 안 건다 —
방 모양과 창 비율이 정하는 값이라 걸면 거짓 실패가 난다.

### 게이트가 자기 크래시를 삼키고 있었다

이 절을 붙이자 **31/31 초록이던 것이 45개 중 44개**로 바뀌었다. §9 의 거리 함수 `d` 를
선언보다 먼저 써서 TDZ 로 터졌고, `finally` 안의 `process.exit` 이 예외보다 먼저 돌아
**11·12 절이 안 도는데 "전부 통과"** 였다. 잡아서 FAIL 로 적는 `catch` 를 넣었다.

드러난 FAIL 하나는 **게이트가 틀린 것**이었다 — 26·29·31·35초를 쟀는데 그 넷은 전부 팔이
신관 트레이로 간 구간(`fetch`)이라 리프터까지 445~487mm 가 정상이다. 잰 값이 아니라
**잰 시각**이 틀렸다. 접촉 시각(17·19·24·32·36초)으로 바꾸니 **98·32·24·24·24mm** 다.

**한 시각 목록으로 두 질문을 재고 있었다.** 시각을 옮기자 이번엔 `j6` 가 전부 0 이 됐다 —
j6 는 신관 트레이를 왕복하는 구간에서 돌고, 그리퍼가 붙는 것은 그 사이의 접촉 순간이다.
어느 한쪽은 반드시 거짓 실패한다. 목록을 둘로 나눴다.

### 연속 스크럽으로 잰 값에는 누적 지연이 섞인다

1초 간격 전수를 돌렸더니 24초·32초 결합이 **445~712mm** 로 나왔고, 하마터면
"중간 두 결합은 안 붙는다" 를 GAP 으로 적을 뻔했다. **아니었다.**

관절에 각속도 제한(70°/s)이 걸려 있어 화면의 자세는 **직전 자세에서 출발해 목표로 수렴**한다.
0→49초를 260ms 간격으로 훑으면 매 칸이 조금씩 덜 따라잡고, 그 지연이 **누적**된다.
직전 시각을 가장 불리하게(팔이 신관 트레이에 가 있는 23·31초) 주고 다시 쟀다.

```
대기  300ms   23→24 25mm   31→32  5mm   35→36 24mm   16→17 98mm
대기 3000ms   23→24 24mm   31→32 24mm   35→36 24mm   16→17 98mm
```

**모든 결합 순간이 24~98mm 로 수렴한다.** 팔은 실제로 닿는다.
읽는 방법이 만든 숫자를 하마터면 로봇의 결함으로 적을 뻔했다.

### 시나리오가 코드였다 — 데이터로 내렸다 (사다리 1)

`series` 는 `datasource/mock.js` 안 `DEMO_CYCLE` **상수**였고, `getSeries(layoutId)` 는
**`layoutId` 를 무시하고** 늘 같은 배열을 냈다. 고칠 방법도, 배치안마다 다르게 줄 방법도 없었다.

```
Shared/data/scenario/schema.js    validateScenario · migrateScenario
Shared/data/scenario/presets.js   assembly49 (49초 · 사건 13개)
datasource                        getScenarios/getScenario/putScenario/deleteScenario
                                  getSeries 는 scenarioId → 저장분 → 프리셋 **해결기**가 됐다
배치안                             scenarioId 한 칸 (가리키기만 한다)
```

**계약이 저장 구조를 이미 정해 놨다** — `LAYOUT-METRICS-CONTRACT.md` "`series` 는 배치안 안에
넣지 않는다". 그래서 시나리오는 자기 id 를 가진 최상위 객체이고, **배치안 A·B 가 같은
`scenarioId` 를 가리킬 수 있다.** 그게 F8 이 성립하는 조건이다.

### 타임라인 — 소품과 같은 문법

`[편집]` 을 누를 때만 아래로 펼친다(3D 84px 양보). 평소엔 지금 막대 그대로라 방금 올린
프레이밍을 안 깎는다. 마커를 **끌어** 시각을 바꾸고 **우클릭**하면 사건·자리·팔·단계를 고른다 —
**자리와 팔은 배치안에서 뽑은 목록**이라 오타가 불가능하다.

### 문턱을 지웠다 — **관측되지 않아서**

소품처럼 끌기 문턱(`SLOP_PX = 4`)을 뒀다가, 게이트를 깨뜨려 보니 **0 으로 낮춰도 53/53 이
그대로 통과**했다. 이유는 계산해 보면 명백하다 — 0.5초 격자 한 칸이 화면에서 약 12px 라
**3px 끌기는 어차피 같은 값으로 붙는다.** 막고 있던 것은 문턱이 아니라 격자였다.

지우고 검사 문구를 사실로 바꾼 뒤, **격자를 0.5 → 0.01초로 주입**했더니

```
FAIL  반 칸을 못 넘는 흔들림은 편집을 안 만든다  — … 24 → 24.11
FAIL  시각이 0.5초에 붙는다                     — 24초 → 26.56초
```

이제 검사가 **실제로 막는 것**을 가리킨다. 통과하던 검사가 통과 이유를 틀리게 알고 있었다.

### 보관함에 필드를 더하면 밟는 자리

시나리오를 store 에 넣자 **새 배치안을 만드는 순간 시나리오가 통째로 사라졌다.** 보관함을
갈아 끼우는 자리 네 곳이 `{ current, scenes }` 만 돌려주고 `...prev` 를 안 펼쳤고, 저장
리컨실러가 그걸 "없어졌으니 지운다" 로 읽어 **저장소까지 비웠다.**

화면은 안 죽었다 — 재생 막대만 조용히 사라졌다. 네 곳을 다 고치고 검사를 붙였다:
`새 배치안을 만들어도 시나리오가 남는다`.

### 자세를 사람이 만든다 (사다리 2)

#### 자세표가 실기가 못 하는 각을 들고 있었다

`unscrew.j6 = 300°` 인데 **URDF 한계는 ±175°** 다. `urdf-loader` 는 `ignoreLimits` 가 아니면
**말없이 자른다** — 표에는 300 이 적혀 있고 화면에는 175 가 서 있었고, **위 §실렌더 39/39 의
`j6 … 175°` 는 자세표 값이 아니라 한계에 붙은 값**이었다.

```
URDF 한계   j1 ±175 · j2 -265~85 · j3 ±162 · j4 -265~85 · j5 ±175 · j6 ±175
얹은 결과   넣은 값 300 → 실제 175
```

`limits.js` 를 URDF **사본**으로 두되(게이트는 브라우저 로딩을 못 기다린다), **게이트가
URDF 원본을 파싱해 사본과 대조**한다. 사본을 두면서 사본이 거짓말하지 않게 하는 방법이다.
`unscrew.j6` 은 175 로 고쳤다 — 화면은 줄곧 175 였으므로 **보이는 동작은 안 바뀐다.**

#### 링이 겹쳐 엉뚱한 관절이 잡혔다

처음엔 j1 을 작게 j6 를 크게 뒀는데 **j6 를 겨눴더니 j4 가 잡혔다.** j4·j5·j6 는 원점이
서로 몇 cm 안이라 큰 링이 서로를 덮는다. **팔 모양대로 뒤집어** j1 190mm → j6 70mm 로,
굵기도 반지름에 비례시켰다.

포인터는 **호스트 div 에 캡처로** 건다 — DOM 캡처는 바깥→안 순서라 캔버스의 `interaction.js`
보다 반드시 먼저 돌고, 링을 잡았을 때만 `stopPropagation()` 으로 삼킨다. 배치 편집은 그대로 돈다.

#### 사건이 자기 성격을 든다 — 그리고 계획의 전제가 틀렸다

계획은 "사건이 자세 **하나**를 드는 키프레임은 지금 표와 수학적으로 같다" 고 적었다.
**아니었다.** 표의 `from` 이 앞 사건의 `to` 와 **4곳에서 다르다**(`join` ×3 · `hoist`) —
`fetch` 처럼 표에 칸이 없는 사건이 사이에 끼면 끊긴다.

그래서 **사건이 자세 두 벌을 든다**로 갔다. 동작이 그대로면서 표현력은 더 크다.

```
{ tSec: 24, event: '신관 결합', station: 'lift',
  pose: { process: ['grip', 'unscrew'] }, carry: 'feed' }
```

옛 경로와 새 경로를 0.5초 간격 **198판 전수 비교 — 다른 것 0개.**

**`fetch` 의 자세가 `home` 인 것은 지금 그렇게 돈다는 뜻이지 옳다는 뜻이 아니다.** 옛 표에
`fetch` 칸이 없어 팔이 대기 자세로 서 있었고, 그 사실을 **그대로 적었다.** 화면 글자는
"신관을 가지러 간다" 인데 팔은 안 간다 — 이제 프리셋의 두 줄만 고치면 된다.

#### 통과할 수밖에 없던 검사 둘을 고쳤다

**① 슬라이더가 자기 값을 자른다.** `<input type=range>` 는 `min`/`max` 로 값을 스스로 자르므로
슬라이더를 읽으면 한계 검사가 **언제나 통과한다** — 클램프를 지워도 61/61 이 그대로였다.
`__fr5giz.pose()` 로 **저장될 값**을 읽게 바꾸니 59/61 로 즉시 빨개진다.

**② FK 검사가 접촉 순간만 쟀다.** `fetch` 자세를 `home`→`grip` 으로 잘못 옮겨도 접촉만 재면
65/65 가 그대로다. 구간 안(22·30초)을 넣으니 `22s 261mm` 로 잡힌다.

**정확값이 아니라 대역으로 본다** — 각속도 제한 때문에 접촉 거리가 스크럽 순서에 따라
18~24mm 로 흔들린다. 정확값을 박으면 게이트가 이유 없이 빨개진다.

## AMR 경로 — 재고 있는데 안 보고 안 따라갔다 (사다리 3)

### 화면이 적는 숫자가 다른 것을 재고 있었다

```
화면 하단   amr1 0.8m · amr2 6.1m      ← waypointsMm 폴리라인 길이
실제 재생   amr1 1.9m · amr2 0.0m      ← 스테이션 직선 (0.1초 적분)
```

`amr1` 은 **2.4배** 차이고, `amr2` 는 시나리오에 사건이 없어 **한 발짝도 안 움직이는데 6.1m**
라고 적었다. 재생은 `waypointsMm` 를 한 번도 안 봤다 (`layout-view.js` — `stationAt[from]→
stationAt[to]` 직선). 라벨을 **`AMR 경로`** 로 고쳤다 — 그건 이동거리가 아니라 그려 둔 길의 길이다.

### 교차 검사가 교차를 못 잡았다

```js
for (const p of a.waypointsMm) for (const q of b.waypointsMm)
  if (거리(p,q) <= 600) → 교차          // **꼭짓점끼리만**
```

가운데서 대각으로 완전히 엇갈리는 두 경로도 **검출 0건**이었다 (꼭짓점 사이가 5657mm).
교착이 날 자리를 미리 보여주는 것이 이 함수의 목적인데 정작 교차를 못 잡았다.
선분 교차로 바꿨고, 나란한 선분에서 표시가 10개 쏟아지던 것도 묶었다.

```
대각 교차  1건 틈0   ·  T 자 접촉 1건 틈0
가까이 나란 1건 틈300 ·  멀리 나란 0건
```

### 경로가 목적지를 안 지나고 있었다

`amr1` 경로가 정작 목적지 `pile` 에서 **1664mm 빗나가** 있었다. 재생이 경로를 안 봐서
아무도 몰랐다. 경로를 시나리오에 맞추고 재생이 그 경로를 따라가게 했다.

```
전   화면 0.8m 적음 → 실제 1.9m 감
후   화면 1.8m 적음 → 실제 1.8m 감 · 경로에서 벗어남 0mm
```

**빗나가면 직선으로 떨어지는 안전판**을 뒀다 — 경로가 목적지를 안 지나면 따라갈수록
멀어져 로봇이 엉뚱한 데서 멈춘다. 그건 직선보다 나쁘다. 문턱은 그 AMR 의 도달거리다.

### 판정을 "꺾이나" 에서 "경로 위에 있나" 로 바꿨다

처음엔 출발·도착 직선에서 얼마나 부풀었나로 쟀는데 **176mm** 밖에 안 나왔다 —
그 구간엔 막는 것이 없어 **경로 자체가 거의 직선**이기 때문이다. 없는 장애물을 피하는 척
경로를 구부리는 것은 거짓말이므로 **재는 것을 바꿨다.** 직선으로 질러가면 경로에서 최대
370mm 벗어나므로 60mm 문턱이면 갈린다.

### 경로 편집 — 선은 여전히 평소엔 안 그린다

`layout-view.js` 에 **"경로 선을 안 그린다 (주인님 요청)"** 이 적혀 있다. 그 결정은 **배치를
정하는 화면**에 대한 것이었으므로, 타임라인·자세와 같은 문법으로 `[경로]` 를 켤 때만 그린다.

점을 끌어 옮기고(100mm 격자 — 소품과 같다) 우클릭하면 추가·삭제한다. 화면→바닥 변환은
`interaction.js` 의 `floorAtMm()` 를 **그대로 쓴다** — 또 만들면 놓는 자리와 끄는 자리가
미묘하게 어긋난다 (하드 룰 5).

패널이 **목적지까지 빗나감을 계속 보여준다** (`탄체 팔레트 까지 370mm ✓`). 그 값이 도달거리를
넘으면 재생이 경로를 버린다는 것을 화면이 그 자리에서 말한다.

### 끌기가 시작조차 못 했다

`setPointerCapture` 를 **상태를 세우기 전에** 불렀다. 합성 이벤트에서는 그게 던지고, 그러면
끌기 상태가 안 잡힌 채 조용히 사라진다. 순서를 뒤집고 `try` 로 감쌌다 — 관절 기즈모가
멀쩡했던 이유는 거기서는 상태를 먼저 세우고 있었기 때문이다.

그 다음엔 **어느 AMR 인지 안 넘겨서** 편집기가 `find(x => x.id === undefined)` 로 아무것도
못 찾았다. 화면이 고른 id 를 같이 넘긴다 — 편집기가 선택 상태를 되물으면 정본이 둘이 된다.

## 경로를 읽을 수 있게 · 시나리오로 넣는 길 (사다리 3 마무리)

**기능은 다 됐는데 아무도 못 썼다.** 주인님이 실제로 눌러 보고 넷을 못 했다 —
AMR 을 새로 놓을 수 없다 · 어느 점이 몇 번인지 모른다 · 어디가 출발인지 모른다 ·
언제 어디로 가는지 한눈에 안 보인다. 넷 다 **만든 것을 보이게** 하는 일이었다
(`GOAL-amr-route-legible.md` · 4 phase 전부 PASS).

```
P1 카드   팔레트 [로봇] → 터틀봇 (AMR) · **경로 2점을 갖고 태어난다**
P2 번호   점마다 ①②③④ · 출발점만 초록·1.45배
P3 방향   선분 가운데 원뿔 — **선분 벡터와 대조**해 판정한다
P4 띠     타임라인에 AMR 별 이동 구간 · 목적지 이름
```

### 같은 질문을 세 번 받았다

*"경로 끝난 걸 시나리오에 어떻게 추가하나"* — 답은 **"사건에 AMR 을 붙인다"** 인데,
`[경로 끝]` 을 눌러도 화면이 한 마디도 안 했다. **설명이 부족한 게 아니라 화면이 그 순간에
안 알려준 것이다.** 그래서 말만 하지 않고 **대신 해 준다** — `[시나리오에 넣기]` 한 번이면
그 AMR 이 붙은 사건이 생기고, 좌측이 시나리오 탭으로 바뀌고, 그 줄이 강조된다.
목적지는 **경로 끝점에 가장 가까운 자리**다 — 사람이 그린 길의 끝이 곧 가려던 곳이다.

### 좌측 패널을 부품/시나리오로 갈랐다

`작업 지점 ①~⑥` 은 부품이 아니라 **시나리오가 이름으로 부르는 어휘**인데 소품 옆에 있었다.
시나리오 탭에는 **사건 목록**을 뒀다 — 시각·이름·자리·AMR 을 그 자리에서 고치고, `▶` 로 그
시각으로 감고, `✕` 로 지운다. **타임라인 우클릭과 같은 문**(`onSetEvent`)이라 정본은 하나다.

### 손으로 눌러 보고 나온 결함 셋

**① 빈 방에 조립 라인 사건 13개가 딸려 왔다.** 자리가 하나도 없어 재생이
*"load, lift, fuze, ship, exit 스테이션이 없어서 못 돌려요"* 만 반복했다 — 빈 방에서 짓기
시작하면 **자리 6개를 다 놓기 전엔 한 발짝도 못 간다.** 원인이 둘이었다: `getScenarios()` 가
프리셋을 **하나만** 냈고, 해결기가 **저장분만** 보고 프리셋 id 를 못 알아봤다.
이제 빈 방은 `blank`(사건 0개)를 가리킨다.

**② `+ 사건 추가` 가 늘 같은 시각에 쌓였다.** 빈 시나리오에서 두 번 누르면 `0, 0` —
마지막 사건과 같은 시각이라 **눌러도 아무 일 없는 것처럼** 보였다. 이제 `5, 10`.

**③ 배치안을 바꿔도 그 시나리오로 안 따라갔다.** ①을 고치자 드러났다 — 빈 방에서 조립
라인을 새로 만들면 `blank` 에 머물러 **사건 0개**였다. 배치안의 `scenarioId` 를 따라가게 했다.

### 자원 누수와 NaN 물건

**번호 라벨이 GPU 에 쌓였다.** `CanvasTexture` 는 지오메트리 정리로 안 없어져, 배치안을
고칠 때마다 뷰가 새로 만들어지므로 **점을 한 번 끌 때마다 텍스처가 점 개수만큼** 쌓였다 —
실측 10번 끌자 **10 → 50**. `createLayoutView.dispose()` 가 `pathGiz.dispose()` 를 부르게 고쳐 **10 → 10**.

**모르는 카드 종류가 NaN 지오메트리를 만들었다.** `place()` 가 마지막 분기로 흘러가 치수
없는 창을 만들었고, 화면은 안 죽고 **보이지 않는 깨진 물건**만 남았다. 결함 주입 중에 드러났다.

### "통과할 수밖에 없는 검사" — 이번 세션 여섯 번

슬라이더가 자기 값을 자름 · FK 가 접촉만 잼 · 문턱보다 격자가 먼저 막음 · 재는 시각이 틀림 ·
슬라이더를 읽고 로봇을 안 봄 · AMR 구간이 하나뿐.

**공통 원인이 하나로 모인다 — 검사가 대상이 아니라 그 대상을 보여주는 것을 읽었다.**
슬라이더·패널·화면 상자는 전부 *표시*지 *값*이 아니다. 다음 검사를 쓸 때 첫 질문은
"이게 값을 읽나, 값을 보여주는 것을 읽나" 다.
