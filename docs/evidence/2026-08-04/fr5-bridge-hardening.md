## 실측 — ARM 한 번에 무엇이 들어갔나

주인님이 화면에서 ARM(조종권 `admin`). 브리지가 서보 ON 직후 설정을 넣고 되읽었다.

| 항목 | 넣은 값 | 되읽은 값 | 판정 |
|---|---|---|---|
| `payloadKg` | 0.6 (그리퍼 사양) | **0.6000000000000001** | 일치 (허용 오차 0.05) |
| `cogMm` | [0, 0, 60] | **[0.0, 0.0, 60.0]** | 일치 |

| `toolCoord` (참고 읽기) | — | **[0, 0, 135, 0, 0, 0]** | 아래 §예상 밖 |

## 예상 밖 둘 — 참고로 읽은 값에서 나왔다

### ① `GetJointSoftLimitDeg` 의 단위는 도(°)다 — 그리고 j3 는 우리가 더 넓었다

SDK 주석은 단위를 **mm** 로 적어 놨다(함수명은 Deg). 모순이라 신뢰도가 낮다고 문서에
적어 뒀는데, 실측값이 답을 줬다:

```
[-175,175, -265,85, -160,160, -265,85, -175,175, -175,175]
```

우리 `JOINT_LIMITS_DEG` 와 **j3 만 빼고 전부 정확히 일치**한다 — 우연일 수 없으므로 도(°)다.
그리고 **j3 는 컨트롤러가 ±160 으로 우리(±162)보다 좁다.** 우리가 더 넓으면 컨트롤러가
거부할 목표를 게이트가 통과시킨다 → **좁은 쪽으로 맞췄다** (`safety.py`).

브리지 로그에도 남았다: `soft-limit-diff j3 컨트롤러 [-160.0, 160.0] vs 우리 [-162.0, 162.0]`.
**대조를 코드에 넣은 그날 바로 걸렸다.**

### ② 툴 좌표계 0 번에 이미 Z 135mm 가 들어 있다

`toolCoordId: 0` 인데 `GetCurToolCoord` 가 `[0, 0, 135, 0, 0, 0]` 을 준다.
매뉴얼상 툴 0 은 "툴 없음(플랜지 중심)" 인데, 이 개체는 **누군가 그리퍼 길이로 보이는
오프셋을 넣어 둔 상태**다.

- 계약에 "화면 TCP 는 플랜지 기준" 이라고 적어 뒀는데 **그 서술이 이 개체에서는 틀렸다** —
  TCP 값은 이미 135mm 오프셋이 적용된 값이다
- **누가 어떤 근거로 넣었는지 모른다.** 그리퍼 실측과 일치하는지 미검증 → GAP OPEN
- 지금 동작에는 영향이 없다 (관절값 저장 + `MoveJ` 재생 조합)

## 확인하지 않은 범위

- **충돌 감지가 실제로 반응하는지** — 등급 5 를 넣었을 뿐, 사람이 밀었을 때 서는지는 안 봤다.
  이게 다음 실측이고 **이번 변경의 진짜 완료 판정**이다
- 되읽기 없는 항목(충돌 등급·전략·설치 방향)이 컨트롤러에 실제로 반영됐는지 — 확인 수단이 없다
- `powerLimitW` 미설정 · 툴 좌표계 135mm 의 정확도
- mock 은 38/38 · 실렌더 21/21 통과 (`fr5-mock-setfail` 로 조건 26 arm 거부까지 회귀 확인)

## 2부 — 유지보수 정비 4건 (P3 라우트가 붙기 전에)

## 왜 지금이었나

P3~P6 이 붙으면 브리지 라우트가 12개 → 25개가 된다. **지금 12개를 손보는 게 나중보다 싸다.**
통증은 추측이 아니라 같은 날 오전에 겪었다 — `appliedSettings` 를 추가하면서 그것을 지워야
하는 곳이 셋이라 각각 따로 고쳤다. 하나라도 빠뜨렸으면 연결이 끊긴 뒤에도 옛 기록이 남아
**조건 26 이 그냥 통과**했을 것이다.

지도를 떠 확인한 구조: 세션 11개 키가 init·`fail_closed`·`/disconnect` 세 곳에서 **서로 다른
부분집합만** 리셋되고 있었고, `observedAt`·`lastStateAt` 은 재연결해도 안 지워지는 stale 값이었다.

## 검증이 먼저 잡아 준 것

**재claim 뒤 옛 토큰으로는 반납이 안 된다** — 토큰을 넣고 검증을 돌리자 마지막 반납이
409 로 실패했다. 코드가 틀린 게 아니라 **토큰 수명주기가 원래 그런 것**이었고, 그 동작을
그대로 검증 항목으로 굳혔다(`옛 토큰으로는 반납도 안 된다`). 검증을 먼저 고치지 않고
사실을 확인한 뒤 항목으로 만든 사례다.

## 판단이 갈렸던 것 — `DECISION-LOG` 줄수 하드 상한을 없앴다

`DECISION-LOG.md` 가 900줄 상한을 넘겨 게이트가 막혔다. **상한을 없앤 근거는 게이트 자신의
주석**이다 — "이 문서는 자르지 않는다(결정의 역사가 정본)" 이고 "조치할 수 없는 경고는
소음" 이라고 적혀 있었다. 처방("최신 N건을 CURRENT 로 분리")은 이미 적용돼 있어, 하드 실패를
푸는 유일한 방법이 **역사를 지우는 것**뿐이었다. 줄수는 경고(1200)로 낮추고 하드 판정은
**목차 대조**(그 문서의 진짜 불변식)에 맡겼다. `scripts/README.md` 기준값 표도 갱신했다.

계약이 상한을 넘어 배치안·생산성 지표를 `LAYOUT-METRICS-CONTRACT.md` 로 **내용 그대로**
이관했다 — 로봇 명령과 소비자도 수명주기도 다르다.

## 3부 — 실기 재연결 — 로봇이 아니라 우분투 랜 설정이 범인이었다

분류: **증거**. 2026-08-04 오후. 주소 셋이 한 세션에 바뀌었고, 그 과정에서 얻은 실측 넷.

### 무엇이 문제였나

`/우분투` 가 0단계에서 멈췄다. 처음 판정은 "우분투가 꺼졌다" 였는데 **틀렸다** — 맥과
우분투가 서로 다른 `/24` 에 있었을 뿐이다. 그 뒤로도 판정이 두 번 더 뒤집혔다.

| 시점 | 관측 | 그때 내린 판정 | 실제 |
|---|---|---|---|
| 시작 | `192.168.10.49` 무응답 | "PC 가 꺼졌다" | 맥 `30.9` · 우분투 `40.4` — **망이 갈렸다** |
| 중간 | 로봇 포트 전부 닫힘 · `GetSoftwareVersion=-4` | "펜던트가 막았다" | **아무도 안 듣고 있었다** (랜 IP 소실) |
| 중간 | 10초간 수신 0패킷 | "선 반대편에 로봇이 없다" | **조용한 구간만 봤다** — 688KB 를 받던 연결이 있었다 |
| 끝 | — | — | **`enp3s0` 이 DHCP 라 주소를 반납했다** |

**근본 원인** — 로봇 쪽 랜 프로필이 `ipv4.method: auto` 였다. 로봇은 DHCP 서버가 아니므로
주소를 못 받고, NetworkManager 가 **가지고 있던 주소까지 반납한 뒤 장치를 내려놨다.**
그러면 `192.168.57.0/24` 로 가는 경로가 사라지고 모든 패킷이 **와이파이 게이트웨이로 샌다**:

```
192.168.58.2 via 192.168.30.1 dev wlx…   ← 로봇 반대 방향
```

### 판정을 뒤집은 계측

추측을 세 번 접게 만든 것은 전부 커널이 들고 있던 숫자다.

- `ss -tni` 의 **`bytes_received:688024` · `lastrcv:282465`** — "죽었다" 가 아니라
  **"4분 45초 전까지 살아 있었다"**. 좀비 소켓과 진짜 단절을 가른다
- `minrtt:0.149ms` 가 앞서 잰 ping 값과 일치 — **같은 상대**임을 증명
- `carrier_up_count/down_count = 6/6` — 선이 여러 번 뽑혔다 꽂혔다
- `statistics/rx_packets` 증가량 — 링크(1000Mb/s)는 살아도 **말은 안 한다**를 구분

**교훈** — `ping` 실패는 "장치 없음" 이 아니다. ICMP·ARP·TCP·링크·수신량을 따로 봐야
"꺼짐 / 다른 망 / 경로 없음 / 조용함" 이 갈린다.

### 확정된 값

| 항목 | 값 | 근거 |
|---|---|---|
| 우분투 | **`192.168.30.240`** (와이파이 고정) | 인터넷 정상 확인 |
| 로봇 | **`192.168.57.2`** | `20003`·`20004`·`8080` 전부 열림 + 연결 성공 |
| ⚠ 랜선 자리 | **컨트롤러 1번 포트** | **비상정지 박스 쪽 포트에 꽂으면 로봇이 `192.168.58.2` 로 보인다** |
| 우분투 유선 | `192.168.57.10/24` + `192.168.58.10/24` | 두 자리 모두 대비 |

`58.2` 는 FAIRINO 공장 기본값이다. 같은 로봇이 **꽂는 포트에 따라 다른 주소로 보인다** —
`config.yaml` 에 경고로 적었다.

### 실기로 닫힌 것 둘

**① 조종권 토큰이 실기에서 왕복했다** (D55 · 어제는 mock 뿐이었다) —
`claim` → 토큰 발급 → 그 토큰으로 `release` 성공.

**② "읽기는 공존한다" 가 실측이 됐다.** 로봇은 **서보 ON · 모드 1(수동)** 상태였다 —
펜던트 세션이 남긴 상태다. 그 위에 우리가 `OBSERVE_ONLY` 로 붙어 관절값을 읽었고
아무것도 깨지지 않았다. 포트가 갈리는 것도 확인했다:

```
펜던트 웹앱 → 로봇 :80 · :9999
우리 브리지 → 로봇 :20003(명령) · :20004(상태)
```

읽은 값 — 관절 `[-58.86, -94.08, 90.89, -84.97, -92.90, 16.51]` ·
TCP `[87.5, -151.1, 18.1]` mm · 안전 플래그 전부 정상.
2초 간격 3회에서 J4 가 `-84.97 → -84.98` 로 미세하게 떨린다 — **캐시가 아니라 실시간**이다.

**그리고 20분 뒤, 로봇이 실제로 움직인 것이 읽혔다.**

```
15:14  [ -58.9, -94.1,  90.9,  -85.0, -92.9, 16.5]
15:37  [-154.7, -80.0, 126.8, -133.6, -89.7, 23.4]   ← J1 이 96° 움직였다
```

**우리는 그 사이 어떤 명령도 보내지 않았다** (`OBSERVE_ONLY` 는 구조적으로 못 보낸다).
사람이 펜던트로 움직인 것이다. 즉 **펜던트가 로봇을 조작하는 동안 우리 읽기가 계속
살아 있었고, 그 움직임이 우리 화면 값에 그대로 들어왔다.**

정지 상태 공존이 아니라 **조작 중 공존**이 확인된 것이다 — 이게 오늘 얻은 가장 강한 값이다.

### NBSP — 네 번 실패한 진짜 이유 (같은 날 저녁)

`99-robot-lan.yaml` 을 만들어도 `ipv4.method` 가 계속 `auto` 였다. netplan·NetworkManager·
프로필 충돌을 차례로 의심했지만 전부 아니었다. `cat -A` 가 범인을 찍어냈다:

```
M-BM- M-BM- version: 2$        ← 고치기 전 (M-BM- = NBSP · U+00A0)
  version: 2$                  ← scp 로 보낸 뒤
```

**답변의 코드블록을 터미널에 붙여넣는 경로에서 들여쓰기 공백이 NBSP 로 바뀌었다.** 눈에는
공백과 똑같지만 YAML 파서에겐 다른 글자라 `version`·`ethernets` 키를 아무도 못 알아본다.
파일이 **읽히기는 하는데 내용이 통째로 무시되는** 상태 — 에러도 안 난다.

산술이 맞아떨어진다: 의도한 147바이트 + NBSP 22개 × 2바이트 = **실제 169바이트**.

고친 방법 — 스크립트를 `scp` 로 바이트 그대로 보내고 `sudo sh` 로 실행. 결과:

```
enp3s0  UP  192.168.57.10/24  192.168.58.10/24    ipv4.method: manual
ping 192.168.57.2 → 2/2, rtt 0.273ms
```

**교훈 두 개.**
① 여러 줄 설정 파일은 붙여넣기로 넘기지 않는다 — `scp`.
② `sudo nmcli connection up "Wired connection 1"` 은 **틀린 처방**이었다. 그 프로필은
`enx701988736cea`(다른 USB 랜)에 매치돼 있다. 런북·`/우분투` 스킬에서 제거했다.

### 확인하지 않은 범위

- **쓰기가 배타인가는 못 쟀다.** 동료가 웹앱을 닫아 경쟁 상대가 없었다.
  펜던트가 **작업 중일 때** 우리가 `20003` 을 잡으면 어떻게 되는지가 진짜 질문이고,
  그건 동료 동의를 받고 재야 한다 (GAP OPEN)
- ~~유선 고정이 아직 안 굳었다~~ → **같은 날 저녁 CLOSED.** 아래 §NBSP 참조
- ARM 하지 않았다 — 서보를 올리는 것은 사람이 옆에 있을 때 화면에서 (하드 룰 3)
- 충돌 감지가 실제로 반응하는지는 여전히 미검증 (D53 의 진짜 완료 판정)

## 4부 — 그리퍼를 화면에서 열고 닫았다 — 그리고 가정 넷이 깨졌다

분류: **증거**. 2026-08-04 저녁. 사다리 1칸(`GOAL-live-gripper.md`) 실기 완결.

### 무엇을 확인했나

`http://192.168.30.240:5055` 화면에서 조종권 → ARM → 활성화 → 개폐. **손가락이 누른 대로
움직이는 것을 눈으로 확인**했고(주인님 입회), 3D 쌍둥이도 같은 값으로 함께 움직였다.

```
지령 30 → 읽기 30        지령 70 → 읽기 70        오류 0/0
```

**변환이 없다.** 계약에 3개월 가까이 적혀 있던 "지령과 읽기는 방향이 반대"는 사실이 아니었다.

### 깨진 가정 넷 — 전부 "안 재고 믿은 것"이다

| 증상 | 내가 믿었던 것 | 실제 |
|---|---|---|
| 활성화해도 슬라이더가 안 열림 | `ActGripper(1,…)` 로 부르니 상태도 **bit1** 일 것이다 | **bit0** 이었다. 명령 번호와 상태 비트 자리는 별개다 |
| 완전 닫기 뒤 모든 명령 거부 | 속도와 시간 상한은 **따로** 정해도 된다 | `vel 30%` 로 낮추면 이동이 3초가 되고, `maxtime 3000ms` 와 겹쳐 **정상 이동이 타임아웃**한다 |
| 3D 손가락이 비현실적으로 벌어짐 | STL 은 **닫힌 자세**로 구워져 있을 것이다 | 이미 **벌어진 자세**였다 (`gripper-mount.json` 이 그렇게 적어뒀는데 안 읽었다) |
| 새로고침하면 자기 조종권에 갇힘 | 토큰은 메모리에 두면 된다 | 새로고침 한 번에 사라진다. 화면은 이름만 보고 "내 것"이라 판단해 **반납도 DISARM 도 거부**됐다 |

### 가장 비쌌던 것 — `8/1 Gripper Movement timeout`

완전 닫기 직후 컨트롤러가 오류를 **래치**했다. 브리지 재시작·재연결·`disconnect` 로 안 풀렸고
**전원 재투입으로만** 해소됐다. 펜던트 문구를 읽고서야 원인이 확정됐다.

**그 과정에서 구조적 함정도 드러났다** — `ResetAllError` 는 ARM 시퀀스 안에만 있는데
`check_arm` 이 오류가 있으면 ARM 을 거부한다. **오류를 풀려면 ARM 해야 하고 ARM 하려면
오류가 없어야 한다.** 화면에서 풀 길이 없다 (GAP OPEN).

### 유니티 기록이 이미 알고 있었다

오늘 헤맨 것의 절반이 `docs/ref/unity/unity-bridge-protocol.md` 에 적혀 있었다.

- `before auto mode: 0% → 96 · after auto mode: 0% → 0` — **"방향 반대"의 정체.**
  8/3 스모크는 브리지를 끄고 수동 모드에서 쟀다. 우리 ARM 은 `Mode(0)` 자동이라 곧다
- `그리퍼 readback 이 약 5초 늦다` — 이동 중 값으로 결론 내린 것이 8/3 의 실수였다

**교훈** — 새 함정을 만나면 SDK 소스보다 **우리가 옮겨 적어둔 실기 기록**을 먼저 연다.

### 지운 것 (표를 만드는 대신)

변환이 없다는 것이 확인되자 `pctRaw` · `calibrated` · `activeRaw` · `faultRaw` 네 필드가
불필요해졌다. 지우고 나니 **계약이 원래 적어둔 모양** `{pct, fault, motionDone, active}` 로
정확히 돌아왔다. 골이 요구한 3점 대응표는 **만들지 않았다** — 그 표의 목적(방향 확정)이
화면 조작으로 직접 증명됐기 때문이다 (`GOAL-live-gripper.md` §7).

### 확인하지 않은 범위

- **물건 파지를 안 해봤다.** `force` 30% 가 충분한지 모른다. 올리려면 `SAFETY-RULES.md`
  §그리퍼 힘 상한대로 **실물로 최소값을 재서 등재**해야 한다 (잡을 물건 미정)
- **3D 벌어짐 20mm 은 근사다** — 모델명 `PGE A-100-40` 에서 딴 값이고 데이터시트 대조를 안 했다
- **활성 비트 자리를 확정하지 않았다** — 실측은 bit0 이었지만 코드는 `!= 0`(하나뿐이라 성립).
  두 번째 그리퍼가 붙으면 자리를 정해야 한다
- **연속 개폐의 상한을 안 쟀다** — 몇 번을 얼마나 빠르게 눌러도 되는지 모른다
- 충돌 감지가 실제로 반응하는지는 여전히 미검증 (D53 의 진짜 완료 판정)
