# 글로벌 카메라 HUD 브리프 — 테스트로 판정 6건

분류: 증거 · 2026-08-06 · 대상 `docs/research/global-camera-hud-brief.md`

브리프의 전제 중 **테스트로 판정 가능한 것만** 골라 돌렸다. 산문 검토가 아니라 숫자다.
6건 중 **4건이 브리프를 반증했고, 1건은 통과, 1건은 회귀 확인**이다.

## 1. CORS — §10 브라우저 내 추론의 관문 (통과)

IP Webcam Server 0.4 가 `/shot.jpg`·`/video`·`OPTIONS` 셋 다에 `Access-Control-Allow-Origin: *`.

헤드리스 Chrome 에서 실제로 픽셀을 읽어 확인했다:

| | `/shot.jpg` | `/video` (스트림) |
|---|---|---|
| `crossOrigin` 없음 | `SecurityError: canvas has been tainted` | `SecurityError` |
| `crossOrigin="anonymous"` | **성공** 1920×1080 | **성공** 1920×1080 |

→ ONNX Runtime Web 을 브라우저에 붙이는 §10.4 안은 **성립한다.**
단 `CamView.jsx` 의 `<img>` 에 `crossOrigin="anonymous"` 가 **없다** — 추론을 붙일 때 같이 넣는다.

## 2. MJPEG `load` 이벤트 — 첫 프레임 1회뿐 (반증)

`multipart/x-mixed-replace` 를 `<img>` 로 받고 10초 관측:

```text
 2초 → load 1회   5초 → load 1회   10초 → load 1회
 load 시각(ms): [201]
```

영상은 계속 갱신됐는데 이벤트는 201ms 의 1회뿐이다.
→ §4.0 의 "`onLoad` 시각 − 현재 시각" 은 **살아 있는 스트림을 무한히 늙게 만든다.**

**이 성질 덕에 지금 `CamView` 의 첫 프레임 판정(`live`)은 정상이다.** 고칠 것은 나이 표시뿐이고,
`/status.json` 저주기 폴링으로 옮긴다.

## 3. CSS 90° 회전 — 중앙만 맞고 나머지는 다 틀린다 (반증)

배포본(`192.168.30.240:5055`)에서 `.cambody` `338×574` 기준 실측.
`<img>` 는 `matrix(0, 1, -1, 0, …)`. 형제 오버레이가 칸을 채운다고 가정하면(§5.1 그대로):

| 이미지 점 | 실제로 찍히는 자리 | 순진한 오버레이 | 어긋남 |
|---|---|---|---|
| 좌상 | (338, −13) | (0, 0) | **338 px** |
| 우상 | (338, 587) | (338, 0) | **587 px** |
| 중앙 | (169, 287) | (169, 287) | 1 px |
| 좌하 | (0, −13) | (0, 573) | **586 px** |
| 우하 | (0, 587) | (338, 573) | **338 px** |

**중앙만 맞는 게 가장 나쁜 모양이다** — 개발 중엔 화면 가운데를 보므로 "대충 맞네" 로 통과한다.

## 4. 렌즈 왜곡 — 핀홀이 쓸 수 있는 건 화면의 22% (반증) — **⚠ 2026-08-06 무효**

> **이 절의 숫자는 쓰지 마라.** 아래 계산은 저장된 `dist` 를 참으로 가정했는데, 같은 날
> 그 계수가 초점거리와 맞바꿔진 허상으로 판정됐다 (`fx` 1351~2351, 74% 흔들림).
> 실제 왜곡은 내부 파라미터 재측정 뒤에 다시 잰다 —
> `global-cam-intrinsics-invalid.md`. 방법(핀홀과의 차이를 격자에서 잰다)은 그대로 유효하다.

`dist = [0.361, −3.424, −0.00514, 0.00683, 16.622]` 를 실제로 적용해 핀홀 투영과의 차를 잰다
(`2560×1440` 격자 65×37):

| 위치 | 어긋남 |
|---|---|
| 정중앙 | 0.0 px |
| 가로 1/4 지점 | 7.6 px |
| 좌변 중앙 | **680 px** |
| 좌상 모서리 | **2064 px** |

**어긋남 ≤1px 인 최대 반경 321px** — 화면 대각 반경 1469px 의 **22%**.
→ three.js `PerspectiveCamera` 만으로는 화면 중앙 5분의 1 밖을 못 그린다. §8 의 "1px 이내" 는
그 반경 안에서만 성립한다.

곁가지: `fx 2106 / fy 2059` 로 이방성 **2.2%**. 폰 렌즈치고 크고, 사진 20장이 적었을 수 있다.

### 기존 게이트가 초록불인 이유 — 왜곡을 0 으로 두고 잰다

`scripts/map/check-overlay.sh:29` 와 `check-camera.sh:32` 는 둘 다 **`D = np.zeros(5)`** 로
투영한다. three.js 쪽에 넘기는 설정도 `"dist": [0] * 5` 다.

```text
카메라 변환 (OpenCV → three.js)   최대 오차 0.000 px      ← 왜곡을 뺀 상태
사진 → 카메라 → 오버레이 전체 사슬   최대 오차 1.27 px      ← 합성 고정물
```

즉 **이 게이트들이 증명한 것은 "OpenCV 와 three.js 의 핀홀 수식이 같다" 이지
"실제 렌즈로 찍은 화면 위에 겹쳐도 맞는다" 가 아니다.** 초록불인 까닭이
바로 그 어긋나게 만드는 항을 0 으로 두었기 때문이다.

실물 영상 위에 겹치는 순간 위 표의 680px·2064px 가 그대로 들어온다.
→ 단계 3(공간 HUD)의 완료 판정에 **실사진 기반 검사**를 하나 더 둔다.

## 5. 게이트가 중첩 스키마를 초록불로 통과시킨다 (반증)

`check-calib.sh` 안의 판정 코드를 그대로 꺼내(실파일 무변경) 세 입력에 돌렸다:

| 입력 | 게이트 출력 | exit |
|---|---|---|
| 브리프의 `extrinsics.labToCam{R,t}` | `labToCam 아직 없음 — 카메라 설치 후 (지금은 통과)` | **0** |
| 실제 `extrinsics.py` 스키마 | `외부 높이 1.82m · 하향 22.5° · 태그 4장 · RMS 0.803px` | 0 |
| 나쁜 RMS 5.0 (대조군) | `FAIL 외부 RMS 5.0 > 2.0` | 1 |

브리프 모양으로 쓰면 **정합이 있는데도 게이트는 "아직 없음"이라 말하고 초록불이 된다.**
게이트가 진짜 나쁜 값은 잡으므로(3행) 이건 게이트 결함이 아니라 **스키마를 발명한 대가**다.

## 6. 회귀 — 폰 설정이 또 되돌아갔다 (D64)

`status.json` 실측:

| 항목 | 잠금값 | 지금 | |
|---|---|---|---|
| `video_size` | 2560×1440 (보정 기준) | **1920×1080** | ❌ |
| `quality` | 90 | **49** | ❌ |
| `whitebalance` | fluorescent | **auto** | ❌ |
| `focusmode` | auto + `/focus` 1회 | continuous-video | ⚠ |
| `zoom` | 100 | 100 | ✅ |

`cam-lock.sh` 로 되잠갔다 — `2560×1440 · q90 · fluorescent · zoom 100 · 초점 수렴`.
**내부 파라미터가 다시 유효하다.**

> 곁가지: 잠금 직후 선명도가 169 였다(과거 기록은 950대). 라플라시안 분산은 장면 내용에
> 좌우되므로 — 지금 카메라는 체스보드가 아니라 방을 보고 있다 — 두 숫자를 직접 비교하지
> 않는다. 스크립트의 판정 기준도 절대값이 아니라 **수렴 여부**다.

## 7. 1080p 는 크롭이 아니라 순수 축소다 — **재측정이 필요 없다** (신규)

"1920 에 맞춰 내부 파라미터를 다시 재야 하나" 를 실측으로 갈랐다.
같은 장면을 두 해상도로 찍어 두 가설을 겨루게 했다.

| | 축소 가설 | 크롭 가설 |
|---|---|---|
| 밝기 상관(NCC) | **+0.9953** | +0.3194 |
| 엣지 상관 | **+0.7868** | +0.0358 |
| ORB 대응점으로 푼 배율 | — | — |

대응점 **395/400** 으로 푼 변환:

```text
배율 0.7502   (축소 가설 예측 0.7500 · 크롭 가설 예측 1.0000)
회전 +0.01°   이동 (-0.2, +0.2) px
```

메타데이터도 일치한다 — 두 해상도에서 `crop_x=50 crop_y=50 focal_length=5.4 zoom=100` 동일.

**결론: 시야가 같고 픽셀만 0.75 배다.**

| 결정 | 근거 |
|---|---|
| **2560×1440 내부 파라미터를 그대로 쓴다** | 35/35 코너 · RMS 0.4107px. 1080p 로 다시 재면 코너가 28/35 로 떨어진다 (`cam-lock.sh` 실측 주석) |
| **스케일 함수 하나만 둔다** | `fx·fy·cx·cy × (스트림폭 / 보정폭)`. `dist` 는 정규화 좌표라 **안 바뀐다** |
| **재측정하지 않는다** | 순수 축소라 선형 스케일이 근사가 아니라 **정확하다** |

→ §7 단계 0 의 절반(해상도)이 닫혔다. **남은 것은 회전 하나**다.

## 이 판정이 §7 순서에 하는 일

- 단계 0(회전·해상도 정합)이 **필수임이 숫자로 확정됐다** — 3번이 근거다
- 단계 1 의 "프레임 나이" 구현 방법이 바뀐다 — 2번
- 단계 2 앞에 `cam-lock.sh` 가 붙는다 — 6번
- 단계 3 의 완료 판정에 반경 조건이 붙는다 — 4번
- §10(객체 탐지)은 **관문을 통과했다** — 1번. 다만 순서상 여전히 뒤다

## 재현

```bash
python3 <scratch>/distort.py                 # 4번 — global-cam.json 만 읽는다
node    <scratch>/camprobe.mjs               # 1·2번 — 폰이 켜져 있어야 한다
node    <scratch>/rotprobe.mjs               # 3번 — 배포본을 연다
curl -s http://192.168.30.10:8080/status.json  # 6번
```

일회용 프로브라 `scripts/check/` 에 넣지 않았다. 상시 게이트로 승격할 것은
**3번(회전 어긋남)** 하나다 — 오버레이가 생기는 순간 회귀 감시가 필요하다.
