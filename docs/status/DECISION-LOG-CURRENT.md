## D85. **손으로 부르는 게이트는 안 도는 게이트다** — 실렌더를 전용 포트로 잠근다

**결정** — `.mjs` 실렌더 검증이 **자기 dev 서버를 자기 전용 포트에 띄우게** 고치고,
`check/*.sh` 로 감싸 `all.sh` 가 줍게 한다. `ar-render.sh`(82건 · 5188·5189) ·
`dash-render.sh`(113건 · 5187)를 신설했다. `fr5-render.sh`(2026-08-06)의 확장이다.
**하드웨어가 있어야 도는 것**(`fr5-cam-verify` 폰 · `tb-*` 터틀봇)은 그대로 손으로 둔다 —
넣으면 장비 없는 날마다 빨간불이 되고, 그게 게이트를 죽인다.

**왜** — `cam-web-verify.mjs` 가 **AR 겹침이 2176px 어긋난 것을 잡고 있었는데** 아무도
안 봤다. D82·D83 으로 실측 캘리브가 들어온 날부터 계속 빨간 채였고, 화면은 그럴듯했다.
게이트가 있었는데도 며칠을 살아남은 것이라, 원인은 코드가 아니라 **호출 경로**다.
2026-08-05 `/감사` P0 가 FR5 에서 낸 결론과 같다.

**전용 포트가 핵심이다** — 개발용(5174)에 붙으면 *고친 코드가 아니라 켜 둔 코드*를
판정한다. `--strictPort` 로 남의 서버에 붙는 길 자체를 막고, `.sh` 가 포트 점유를 먼저 본다.

**대가** — `all.sh` 가 54초 → **2분 51초**. 자동 판정 370건(단위 157 + 실렌더 213).
그만큼은 낼 값이다. `cv2` 가 없으면 **건너뛰지 않고 실패한다** — 없이 돌면 정합을 안 본 채
초록이 되는데, 그게 이 결정의 정반대다.

**초록불을 믿기 전에 빨간불을 봤다** — 일부러 버그를 심어 두 게이트 다 `exit 1` 을 확인했다.
AR 쪽은 **첫판에 초록이었다**(11초에 읽었는데 경고는 12초에 켜졌다). 게이트를 만들면
**그 게이트가 실제로 잡는지**를 따로 재야 한다.

## D84. **카메라가 믿을 만한가는 한 곳이 정한다** — 값은 공유, 그리는 것만 화면별

**결정** — 카메라 상태 판정(연결·해상도·설정 잠금·프레임 나이·정합)과 끊김 감시를
`Shared/data/camera/{state,watch}.js` 로 올린다. **판정 함수가 문자열과 색(`tone`)까지 낸다.**
FR5(React)·AR(바닐라)은 받아서 배치만 한다. 대시보드는 datasource 경계가 열린 뒤 같은 것을 쓴다.

**왜 컴포넌트가 아니라 함수인가** — `Shared/view3d/` 는 React 금지이고 AR 은 바닐라다.
**셋을 다 먹이는 컴포넌트는 애초에 만들 수 없다.** 그리고 배치는 달라야 한다 — 300px PiP 와
전체화면 머리띠를 같게 만들면 못 쓴다. 갈라지면 안 되는 건 배치가 아니라 **"괜찮다"의 기준**이다.
재보니 이미 조각나 있었다: 끊김 감시는 FR5 에만, `verified` 판정은 AR 에만 있었고
둘을 합쳐도 브리프 §4.0 의 5요소가 안 채워졌다.

**"못 읽었다"와 "안 물어봤다"를 가른다** — `null` 은 경고, `undefined` 는 조용. 합성 고정물에는
잠글 폰이 없는데 `설정 확인 못 함` 을 띄우면 **아무도 못 고치는 경고가 상주**하고, 사람은
경고를 무시하는 법을 배운다. 그게 제1원칙을 더 크게 깬다. 같은 이유로 **초점은 판정하지
않는다** — 기기가 되돌려주는 값이 거짓말이고(D64), 판정 근거인 선명도는 화면이 못 잰다.
**못 재는 것을 재는 척하지 않는다.**

**안 움직이는 게 정상인 것에 움직임을 재지 않는다** — 감시를 AR 에 걸었더니 정지 사진인
합성 고정물이 12초 뒤 `멈춤` 이 됐다. `?feed=` 가 있을 때만 감시한다.

**기각** — ①`Vision/` 같은 주제 폴더로 카메라 코드를 몰기: 배포 단위가 조각나고 런타임이
셋(Python 도구·바닐라·React)이라 안 맞는다. ②상태 표시를 화면마다 짜기: 오늘 그 결과가
"조각나 있고 합쳐도 모자란" 상태였다.

## D83. **MJPEG 는 끊겨도 말이 없다** — 픽셀로 재고, 실패하면 주소를 보여준다

**결정** — 실영상 PiP 에 ①**정지 감지**(3초마다 32x18 캔버스로 옮겨 그려 3회 연속 같으면
죽은 것) ②**자동 재접속**(3→6→12→20→30초로 벌린다) ③**실패 상태에도 주소 표시**를 넣는다.
D79 의 "자동 재시도는 안 한다(능동 폴링 금지)" 를 **뒤집는다.**

**왜** — `load` 이벤트는 첫 프레임 때 한 번뿐이다(10초에 1회 실측). 서버가 연결을 닫아도
`<img>` 는 **마지막 프레임을 들고 조용히 서 있는다.** 이날 폰 앱이 다섯 번 재시작했는데
화면은 멀쩡해 보였다 — 안전 표시에서 **옛 화면이 지금 화면인 척하는 것**이 제일 나쁘다
(SAFETY-RULES 제1원칙). 이벤트가 없으니 픽셀 말고 잴 것이 없다. 장면이 안 움직여도
JPEG 잡음 때문에 프레임마다 값이 달라져, 완전 동일은 "새 프레임 없음" 이다.

**폴링 금지를 뒤집은 근거** — 그 규칙은 **낭비**를 막자는 것이지 복구를 막자는 게 아니다.
벽에 걸린 화면 앞에는 누를 사람이 없다. 간격을 벌려 죽은 주소에 매달리지 않게 했다.

**③ 이 오늘의 진짜 교훈이다.** 우분투 화면이 안 뜨는 원인을 찾느라 프록시·CORS·네트워크·
빌드를 다 뒤졌는데, **범인은 저장된 주소의 포트 오타(`:8000`)였다.** 화면에는 "영상 없음"
뿐이라 주소가 틀렸는지 망이 문제인지 구분할 수가 없었다. 못 왔으면 **어느 주소가** 안
왔는지 말해야 한다. 게이트에 검사를 박았다 (`fr5-cam-verify.mjs` 13/13).

**대가** — `crossOrigin="anonymous"` 가 필요하다(캔버스 오염 방지). CORS 를 안 주는
카메라면 **감시만 접고 영상은 계속 낸다** — 못 재는 것과 안 되는 것은 다르다.

**실측** — 멎은 스트림 12초에 감지·32초까지 경고 유지(깜빡임 0) · 살아있는 스트림 20초
거짓경보 0 · 복구 4초. 근거 `evidence/2026-08-07/global-cam-calibrated.md`.

**날짜**: 2026-08-07

## D82. **글로벌 카메라는 가로로 단다** — 세로는 팔이 프레임 밖으로 나간다

**결정** — 폰을 세로(9:16)에서 **가로(16:9)** 로 돌려 단다. D79 에서 CSS 로 90° 돌려
세워 보여주던 것을 없앤다.

**왜** — 세로로 달면 넓은 화각(73°)이 **세로로** 가고 가로에는 좁은 45.3° 만 남는다.
팔 작업 높이에서 담기는 폭이 **1.32~1.55m** 인데 FR5 도달 지름은 **1.84m** 다 —
팔을 옆으로 뻗으면 화면 밖으로 나가고, **안전구역이 조용히 안 그려진다.**
가로로 돌리자 같은 자리에서 **2.19~2.45m · 0.95mm/px** 로 전 범위가 들어왔다.

**세로를 유지하는 안 — 기각.** 66cm 를 더 물려야 하고 그러고도 해상도가 34% 나쁘다.

**덤이 더 크다** — CSS 90° 회전이 사라졌다. 돌아간 이미지에 오버레이를 얹으면 가운데만
맞고 모서리가 338~587px 어긋난다. **겹치기(공간 HUD)의 선행 조건이 거치 방향 하나로
닫혔다.** D79 의 "CSS 가 제일 싸다" 는 그때는 맞았다 — 오버레이가 없었으니까.

**함정** — 앱 설정으로 돌리면 주점 `cx·cy` 가 바뀌어 내부 파라미터를 손봐야 한다.
**거치대에서 물리적으로 돌린다.** 그러면 내부 파라미터가 그대로고 `extrinsics.py` 만 다시다.

**날짜**: 2026-08-07

## D81. **공유층은 랩 안 SQLite 다** — 클라우드는 랩 밖에서 봐야 할 때 얹는다

**결정** — D46 의 두 층 구조는 그대로 둔다. 다만 상위 층을 Supabase 에서 **랩 안 상주 기계의
SQLite** 로 바꾼다. 로봇 옆 브리지의 로컬 파일(`~/fr5-data/`)이 정본인 것도 그대로다.
D46 의 스키마 조항(`robotId`·펌웨어·tool/user·그리퍼 정체·`source`·서버 시계)은 **전부 산다** —
소급해 못 채우는 값들이라는 이유가 저장소를 바꿔도 안 변한다.

**왜** — D46 의 이유는 "인터넷이나 클라우드가 끊겼다고 티칭·실행이 멈추면 안 된다" 였다.
그 이유를 **열람까지** 밀면 클라우드가 상위 층일 근거가 없어진다 — 작업이 안 멈춰도 기록을
못 보면 반쪽이다. 그리고 팀은 이미 랩 안에서 브리지 주소 하나로 들어온다 (`TB-CONTRACT.md`).

**기각 철회** — D46 의 "SQLite 단독: 팀 공유가 안 된다" 는 SQLite 를 **각자 PC 에 두는**
경우다. 상주 기계 하나가 들고 HTTP 로 서빙하면 공유도 집계·필터도 된다. 파이썬 표준
라이브러리에 `sqlite3` 가 있어 새 의존성도 0 이다.

**호스트는 라즈베리파이5 로 정했다** (2026-08-07 실측 · `evidence/2026-08-07/pi5-log-node-bringup.md`).
전원 `0x0` · 브리지 HTTP 200 · **내장 RTC** · 랜선 없이 WiFi 무인 복구까지 통과. 파이4 대비
결정타는 내장 RTC — 조건③(시계 유지)을 파이4 는 외부 모듈로 받쳐야 한다. (원문: "4/5 는 실측 후.")

**조건 셋** — ①기록 DB 를 **SD카드에 두지 않는다** (쓰기 수명이 못 버틴다). ②**쓰는 주체는
프로세스 하나** — SQLite 는 네트워크 DB 가 아니다. 나머지는 HTTP 로 읽는다. ③**시계를 잃지
않아야 한다** — 정전 후 재부팅에 타임스탬프가 오염되면 기록 전체가 무의미해진다
(D48 §두 개의 시계). 내장 RTC 가 없는 기계면 외부 모듈로 받친다.

**Supabase 를 푸는 조건** — **"랩 밖에서 봐야 하는가" 가 예가 되는 순간.** 그때 상주 기계가
동기화 주체가 된다. 층이 하나 더 얹힐 뿐 구조는 안 바뀐다 — 그래서 지금 정하지 않아도
나중 비용이 같다 (`ARCHITECTURE.md` §확장성: 교체는 파일 한 개).

**날짜**: 2026-08-06

## D80. **관문이 한 대에 둘이면 포트도 가른다** — tb-bridge 는 5056, 정본은 `config.yaml`

tb-bridge 가 우분투에서 못 떴다. 로봇이 꺼져서가 아니라 **5055 가 이미 FR5 것**이어서다.
계약의 "FR5 `bridge/` 와 형제·무의존" 은 **코드 의존**을 말한 것이었는데, 두 관문이 같은 PC
한 대에 살 줄은 안 적었다. 자원은 안 나눠 놨던 것이다.

**① tb 를 5056 으로.** 옮기는 비용이 0 에 가까운 쪽을 옮긴다 — FR5 는 systemd·배포 스크립트·
D63 주소에 5055 가 박혔고, tb 는 아직 한 번도 못 떴다.
**② 포트 정본은 `config.yaml` 하나.** 거기 있던 `port:` 는 **아무도 안 읽는 죽은 필드**였다
(`main.py` 는 `robots`·`disk_min_free_gb` 만 읽고 포트는 uvicorn CLI 인자였다) — "값 하나만
바뀐다" 가 포트엔 거짓이었다. 기동 스크립트 둘이 `sed` 한 줄로 읽는다(셸에 yaml 파서 안 들인다).

**화면은 0줄 고쳤다** — `http.js` 가 `location.host` 만 쓰고 브리지가 같은 출처에서 서빙하니
(D29) 포트가 애초에 클라이언트에 없었다. 사본은 vite dev 프록시 하나뿐이고 `check/consts.sh`
가 잡는다 — 사본을 없애는 대신 **정본 하나 + 게이트**가 이 저장소의 관용이다.

5055 로 되돌린 A/B 에서 똑같이 나 **포트와 무관**하다. `evidence/2026-08-06/tb-connect-check.md`.

## D77. **드리프트 기준은 우리가 든다** — 컨트롤러 필드는 티치모드를 영구히 잠갔다

**주인님이 실기에서 부딪혔다.** 티치모드로 팔을 옮기고 나니 조그·이동이 전부
`지령·실측 괴리 31.52° > 5.0° (조건 8 대안)` 으로 거부됐다. 로봇도 선도 브리지도 정상이었다.

조건 9 는 컨트롤러의 `lastServoTarget` 과 실측을 비교하고 있었다. **두 군데가 동시에 틀렸다.**

**하나 — 그 필드는 우리 명령으로 안 채워진다.** `ServoJ`(8ms 서보 스트리밍) 전용인데
우리는 `MoveJ` 만 쓴다. 브리지 저널의 `moveJ-after` 는 기록된 **모든** 이동에서
`servoTarget=[0,0,0,0,0,0]` 이었다 (08-03 · 08-05). 전부 0 이면 건너뛰므로 **이 게이트는
우리 지령의 추종을 한 번도 검사한 적이 없다.** GAP-MATRIX 에 "건너뛴다" 로만 적혀 있던
것이 실은 **한 번도 안 돌았다** 였다.

**둘 — 티치모드가 채우면 우리가 못 푼다.** 티칭 진입 시점 자세가 그 필드에 남고, 사람이
팔을 5° 넘게 옮기면 그때부터 전 축이 잠긴다. `MoveJ` 가 그 값을 갱신하지 않으니 **우리
명령으로는 영영 못 지운다** — 손으로 옛 자세에 되돌리는 길밖에 없다. 티치모드의 목적
자체(자세를 잡고 거기서 움직인다)가 봉쇄된다.

그래서 **기준을 브리지가 든다**: 마지막으로 보낸 `MoveJ` 목표(`session.lastCommandedDeg`).
없으면 검사하지 않는다 — 아직 아무것도 안 보냈으면 추종을 논할 게 없다. 비우는 시점은
**드래그 티칭 감지 · 모드 전환 · ARM · 연결** 넷. 티칭 감지는 `read_fresh_state()` 한 곳에
둔다 — 펜던트가 직접 켠 경우까지 같은 자리에서 잡힌다.

**게이트를 빼는 변경이 아니다.** 한 번도 판정하지 않던 조건을 **처음 작동시키는** 변경이다.
비운 뒤 첫 명령은 조그 5° 상한이나 지점 이동 경로 전수 검사를 그대로 지나고, 그 명령이
곧 새 기준이 된다 — 구멍이 아니다.

**기각** — ⓐ 게이트 삭제: 조건을 빼는 근거는 "안 걸리더라" 가 아니어야 한다 (SAFETY-RULES)
ⓑ 상한 완화(5°→40°): 숫자만 밀 뿐 기준이 여전히 우리 것이 아니다 ⓒ 티칭 해제 때만 비우기:
펜던트가 켠 티칭은 우리 해제 경로를 안 지난다.

`ServoJ` 를 실제로 쓰게 되면 그때는 `lastServoTarget` 이 살아나므로 둘을 함께 본다.
계약은 `SAFETY-RULES.md` §드리프트 기준.

## D76. **벽이 정밀함을, 사람이 방향을 낸다** — 그리고 링이 맵의 어디인지는 모드가 정한다

답사가 실물과 안 맞는 **최대 항은 캘리브레이션이 아니라 `↺↻` 15°** 였다. 최선을 다해도
±7.5° 가 남고 12m 지점에서 157cm — 축척 오차(24cm)의 6배다. 그런데 각도는 이미 오고
있었다: 히트 포즈의 `orientation`(= 그 면의 법선)을 받아 놓고 `position` 만 쓰고 버렸다.

**법선은 yaw 를 90° 네 자리까지만 좁힌다** — 직사각형이라 넷이 다 유효하고 기하학은 못
고른다. 그 마지막 칸을 처음엔 사람 손에 남겼는데, **주인님이 실기에서 "구석이면 정면으로
걸어 들어갈 수가 없다" 고 지적한 게 열쇠였다**: **사람이 서서 보는 쪽**이 고른다
(`snapQuadrant`). 걸어 들어갈 면이 앞에 와야 하기 때문이다. 둘을 안 섞는다.

**같이 정한 것 — 링이 맵의 어느 자리인가는 모드가 정한다** (`PIVOT`): 평소 가운데 ·
답사 **들어가는 변의 가운데** · 촬영 모서리(`solveCorners` 가 첫 모서리를 원점으로 쓴다).
이동은 **`apply()` 에서** 한다 — 탭할 때 옮겨 두면 확대할 때마다 기준점이 밀린다.

**시간을 조건으로 바꿀 때는 도달 불가를 먼저 본다.** `WARMUP_MS` 는 틀린 것을 쟀지만
**반드시 만료된다.** "0.3m 이동" 으로 바꾸면 삼각대에서 영영 안 열린다 — 그 고정 카메라
시연이 같은 파일 머리말에 적힌 용도였다. 6초 유예 + 회귀 검사.

**기각** — ⓐ `plane-detection`: 크롬 플래그 뒤일 수 있고 히트 법선만으로 대부분 된다
ⓑ 손가락 드래그: 조준 광선이 `viewer` 에서 나가 손가락을 안 본다. 폰을 움직여 훑는 쪽이
시차까지 같이 번다 ⓒ `↺↻` 삭제: 자동이 틀렸을 때 빠져나갈 길이 없다 — 90° 로 남겼다.

수치·검사·실기 판정은 `evidence/2026-08-07/xr-calibration.md`.

## D75. 상한을 푸는 대신 **경로를 본다** — 지점 이동은 가는 길을 훑고 한 번에 간다

**주인님이 실기에서 부딪혔다.** 지점 두 개(`home`·`1`)를 찍고 이동을 눌렀더니
`관절 변화 … > 상한 5.0°` 로 거부됐다. **5° 밖의 지점은 영원히 못 간다** — Teach 의 핵심
기능이 구조적으로 막혀 있었다. `GOAL-teach-points` 가 "기존 moveJ 게이트 그대로" 라고 적은
것을 곧이곧대로 받아 조그용 상한(`JOINT_DELTA_CAP_DEG` · v3 tiny-MoveJ)에 태운 게 원인이다.

**상한을 올리지 않았다.** 그 5° 가 있는 **진짜 이유는 경로가 검사되지 않는 것**이다 —
작업영역 게이트는 **도착점만** 본다. 도착점이 안전해도 가는 길이 상판을 쓸 수 있다.
숫자만 30° 로 올리면 그 구멍이 그대로 열린다.

**그래서 근거를 없앴다.** 보내기 전에 현재→목표를 **관절 공간에서 5° 간격으로 보간**하고,
표본마다 `GetForwardKin` 으로 손끝을 구해 **작업영역 게이트를 전부 통과**시킨다. 하나라도
막히면 몇 번째가 왜인지 돌려주고 안 보낸다. 전부 통과하면 `moveJ` **한 번**으로 매끄럽게 간다.
간격을 5° 로 둔 것은 조그 상한과 **같은 근거**다 — 사람이 반응할 수 있는 크기.

- **표본은 움직이기 전에 전부 구한다** — 이동 중 xmlrpc 를 두드리지 않는다 (연결이 하나뿐이라
  움직이는 동안 두드리면 컨트롤러가 밀린다 · 그리퍼 조밀 폴링 사고와 같은 계열)
- **`delta_cap=None` 은 경로를 대신 검사했을 때만 쓴다.** 조그·일반 `moveJ` 는 5° 그대로다 —
  검증이 그 둘을 따로 확인한다 (상한을 전역으로 푼 게 아니라는 증거)
- **작업영역이 없는 프로필이면 지점 이동을 아예 안 연다.** 검사할 수단이 없는데 상한만 푸는 것이
  제일 위험하다
- 두 끝이 URDF 한계 안이면 사이도 전부 안이다(볼록) — 표본에서 한계를 다시 안 본다

**기각** — ⓐ*5°씩 잘게 나눠 순차 실행*: 새 상한이 0이라 안전하지만 조각마다 가감속이 새로
걸려 뚝뚝 끊기고 느리다. **사이클 타임 비교(F10)가 그 자리에서 썩는다** ⓑ*지점 전용 상한만
신설(30°)*: 빠르지만 경로가 여전히 안 보인다 — 근거를 안 없애고 예외만 만드는 모양이다
ⓒ*상한 상수를 올린다*: 조그까지 같이 커진다

**남는 위험** — **여전히 손끝만 본다.** 팔꿈치·상완은 경로에서도 판정 밖이다 (D73 천장 그대로).
그리고 **막힌 경로가 실제로 거부되는 것은 아직 못 봤다** — 표본 논리는 단위 7건으로만 확인했다.

| 필드 | 없으면 |
|---|---|
| `stamp`(profile·tool/user·펌웨어·속도 상한·그리퍼 힘·작업영역 판) | 다른 조건끼리 비교된다 |
| `fps` 고정 + 흔들리면 재표본 | 성긴 샘플이 더 빨라 보인다 |
| `startPose` | 출발이 달라 생긴 차이를 동작 차이로 읽는다 |
| `endReason`(`done`/`timeout`/`gateRefused`/`estop`/`collision`/`disconnect`) | 막혀 끊긴 run 이 "빠른 run" 으로 섞인다 |
| `dropped` | 빠진 구간만큼 짧아 보인다 |
| `purpose`(`measure` 차단 / `collect` 랜덤화) | 학습용과 측정용이 섞여 둘 다 못 쓴다 |

**`purpose` 가 핵심이다.** 모방학습은 "물체 위치를 매번 바꿔가며" 찍어야 하고(정책이 고정
궤적을 외우지 않게), F10 은 정반대로 조건을 묶어야 한다. 충돌이 아니라 **다른 종류의 녹화**다.

**⑤데이터 증강 금지의 이유를 정확히 적는다.** 시뮬레이터 기반 증강이 성립하는 것은
**바꾼 자세에 맞는 영상을 시뮬레이터가 다시 렌더하기 때문**이다. 우리는 렌더러가 없으므로
영상 짝이 없고 금지는 그대로다 — "증강은 원래 안 되는 것" 이 아니라 "**우리에겐 렌더러가
없어서** 안 되는 것" 이다. 이 구분이 있어야 나중에 시뮬레이터를 들일지 판단할 수 있다.

**기각** — *Optimize 를 이름만 "비교" 로 바꿔 유지*: 중복 화면이 그대로 남는다.
*Teach 와 Program 을 합치기*: 캡처 버튼과 승인 버튼이 한 화면에 있으면 손가락 거리 하나가
"저장" 과 "실기 연속 실행" 을 가른다. 회귀 범위도 붙어 목록 정렬 하나에 승인 게이트를
다시 검증해야 한다. **⛔관절 목표를 한계로 클립하기**(여러 스택의 관례): 우리는 **거부**한다.
말없이 자르면 사람이 시킨 것과 로봇이 한 것이 달라진다 — `urdf-loader` 가 정확히 그래서
`j6 = 300°` 가 잘린 값이 진짜 자세인 양 증거 문서에 적혔다 (GAP 기록). *시뮬레이터·GPU 도입*:
지금 필요가 없고 새 의존성은 계약을 오염시킨다 — 붙일 일이 생기면 `/스택가드` 먼저.

**날짜**: 2026-08-05

## D73. 작업영역은 로봇이 직접 짚어 얻는다 — 상판은 평면이 아니라 사각 기둥이다

**결정** — 조건 12 의 카테시안 절반을 채운다. 값은 **로봇에게 모서리를 짚게 해서** 얻고
(`runbook/WORKCELL-MEASURE.md`), 프로필 최상위 `workspace` 에 등재한다. 계약은 §작업영역.

**왜 자로 잰 숫자로 안 되나** — 자는 바닥 기준이고 게이트는 로봇 기준인데 **둘을 잇는 변환이
없다.** 로봇이 짚으면 변환이 필요 없다. 주인님이 재 주신 `85.8×58cm` 는 버리지 않고
**교차검증**에 썼다 — 짧은 변이 587.3(자 580 대비 +7.3), 각이 90.1° 로 맞아 **방법 자체가
검증**됐다. 그래서 긴 변의 62.7mm 부족이 오차가 아니라 **로봇이 못 간 것**으로 확정됐다.

**①상판은 사각 기둥이다.** `x·y` 가 상판 안일 때만 높이를 건다. 높이 평면 하나로 막으면
**상판 바깥에서 내려가는 정상 자세부터 거부**된다 — 실제로 짚는 동안 손끝이 상판 밖
346mm 아래에 있었다. 이건 짚어보기 전에는 안 보이던 것이다.

**②기구학을 새로 짜지 않는다.** 목표 관절을 로봇의 `GetForwardKin` 에 넣는다. DH 파라미터를
우리가 다시 적을 이유가 없고 툴·사용자 좌표계가 저절로 맞는다.

**③그 가정을 ARM 이 매번 대조한다.** 작업영역은 기구학이 스트림과 **같은 좌표계일 때만**
참이다. 같은 관절을 FK 에 넣어 5mm 넘게 어긋나면 ARM 을 거부한다. 실기 첫 판정은 **0.0mm**.
게이트가 있는 척하면서 아무것도 안 막는 상태가 제일 위험하다 (D64 계열).

**④못 가는 데까지 넓게 잡는다.** 긴 변은 짚은 795 가 아니라 **858** 로 등재했다. 못 가는
데를 막아도 손해가 없고, 팔꿈치를 반대로 접으면 갈 수도 있다.

**기각** — ⓐ자로 잰 값을 그대로 쓰기: 변환이 없다 ⓑ가우시안 스플랫·사진 재구성: 만드는 건
**모양**이지 로봇 좌표계 안의 **위치**가 아니다. 원점 문제가 그대로 남고, 점 구름이라 평면
방정식이 안 나와 판정 근거로 못 쓴다 ⓒ파이썬으로 FK 직접 구현: 검증할 것만 늘어난다

**남는 위험** — **손끝만 본다**(팔꿈치·상완은 판정 밖) · 벽 두 점이 수평 91mm 밖에 안 떨어져
**각도가 ±70mm 부정확**(그래서 여유 100mm) · **실기에서 거부되는 장면을 아직 못 봤다**
(mock 57/57 로만) · `toolCoordId` 를 브리지가 로봇에 **안 넣는다**(GAP).

## D72. 잠근 건 펜던트가 아니라 우리 ARM 이었다 — 모드 전환을 화면에 되돌려 놓는다

**결정** — `{ "cmd": "mode", "manual": bool }` 을 명령 허용목록에 더하고 토글을 **헤더 안전
바의 STOP 옆**에 둔다. 계약은 §모드 전환.

**왜** — 팀원이 "펜던트에서 수동·드래그가 잠겨서 로봇을 못 움직인다"고 했다. 원인을 찾아보니
`ARM` 시퀀스의 마지막 두 줄이었다 — `ExitDragTeach()` + `SetMode(0)`. **우리가 잠갔다.**
게다가 `DISARM` 은 서보만 내리고 모드를 안 되돌려서, 껐다 켜도 잠긴 채로 남는다.
**들어가는 문만 만들고 나오는 문을 안 만든 것**이다.

**①`ARMED` 에서도 받는다.** 처음엔 "ARMED 에서는 거부, DISARM 이 선행"으로 짰다가
주인님이 뒤집었다 — **드래그 티칭은 서보가 켜져 있어야 된다.** DISARM 을 강제하면 서보가
내려가 잠금을 푸는 길이 다시 막힌다. **규칙이 스스로를 막는 모양이었다.**

**②하드 룰 4 는 전환 금지가 아니라 기존 게이트가 지킨다.** `check_motion` 이 `mode != 0`
이면 거부하므로 수동 모드에서 우리 조그·moveJ 는 이미 안 나간다. 드래그 중에는
`_common_safety` 가 그리퍼까지 막는다. **방어선이 원래 거기 있었다** — 전환을 막는 것은
안전을 더하지 않고 복구 경로만 없앴다.

**③드래그 티칭 스위치는 웹에 넣지 않는다.** 팔을 푸는 것은 펜던트의 3위치 인에이블
스위치다 — 쥐면 풀리고 놓으면 잠긴다. 웹 버튼은 놓아도 풀린 채라 그 장치를 무력화한다.
모드 전환은 **권한만** 넘기는 것이라 이 논리에 걸리지 않는다.

**같이 막은 구멍** — `check_arm` 이 `inDragTeach` 를 안 봤다. 다른 명령은 전부 막는데 ARM 만
안 막아서 **사람이 팔을 잡고 있는데 ARM 을 누르면 손 안에서 팔이 굳었다** (조건 25).

**기각** — ⓐ펜던트에만 두기: 우리가 잠근 것을 우리가 못 푼다 ⓑARM 이 모드를 안 바꾸게:
자동 모드는 우리 명령의 전제다 ⓒDISARM 이 수동 복귀: 사람이 원한 적 없는 상태로 옮긴다

**남는 위험** — 되돌리기는 **사람 몫**이다(자동 복귀 타이머 없음). 잊으면 다음 사람의 조그가
`auto 모드가 아니다` 로 거부되지만, 토글이 헤더에 늘 있어 막히지는 않는다.

**검증** — 단위 56 · mock 53 · 실렌더 32(활성 토글 스크린샷) · 실기에서 펜던트 해제 확인.
