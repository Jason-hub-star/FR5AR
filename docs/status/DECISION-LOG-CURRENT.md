## D37. 증거는 날짜가 폴더다 — 파일명에 날짜를 두 번 쓰지 않는다

**결정** — `docs/evidence/` 는 **날짜 폴더 하나 깊이**로 둔다.
`evidence/YYYY-MM-DD/<주제>.md`. 파일명에서 날짜 접두사를 뺀다.
더 깊게(주제별 하위 폴더) 파지 않는다 — 증거는 **언제 쟀나**로 찾지 주제로 찾지 않는다.

**왜** — 23개가 루트에 평평하게 쌓여 있었다. 날짜가 파일명 앞에 있어 정렬은 됐지만
"오늘 뭘 확인했나"를 보려면 목록 전체를 훑어야 했다. 폴더가 되면 그게 `ls` 한 번이다.

**함께 고친 것** — 참조 79건을 일괄 치환했고(파일 29개), 규약을 세 곳에 박았다:
`docs/INDEX.md` §새 문서 추가 규칙 · `.claude/skills/마감/SKILL.md` §2 · `SESSION-START.md`.
**`scripts/check/docs.sh` 에 게이트를 넣었다** — `evidence/` 루트에 파일이 생기면 실패한다.
규약만 적으면 다음 세션이 다시 평평하게 만든다.

**함정** — `scripts/build/config.mjs` 가 evidence 경로를 **생성물 json 안에** 박아 넣는다.
경로를 바꾸면 `consts.sh` 가 빨개진다. `node scripts/build/config.mjs` 로 다시 굽는다.

**기각** — `evidence/<주제>/<날짜>.md`(주제 우선). 한 주제가 한 번만 측정되는 경우가 많아
폴더 하나에 파일 하나가 된다. 지금 23개 중 그런 게 대부분이다.

**눈금도 같이 바꿨다** (주인님 선택, D18 절차대로). `docs-weight.sh` 가 재던
"evidence 전체 파일 수 15/25" 는 **평평했을 때의 기준**이었고, 폴더가 생긴 뒤 26개로
하드 상한을 넘어 게이트가 빨개졌다. **증거는 지우지 않는 역사라 총량은 계속 는다** —
총량에 상한을 걸면 게이트가 "시간이 지났다"는 이유로 실패한다.
그래서 **날짜 폴더 하나당 8/14** 로 바꿨다. 진짜 냄새는 "하루에 열몇 개"다.

`.png` 는 세지 않는다 — **문서에 딸린 근거지 읽을거리가 아니다.** 세면 사진을 많이 붙인
성실한 기록이 벌을 받는다. 07-31 은 파일 18개지만 문서는 12개다.

## D39. FR5는 robot profile을 거쳐 읽기 전용으로 먼저 연결한다

**결정** — 같은 FR5라도 다른 개체가 배정될 수 있으므로 `192.168.57.2`를 로봇 정체성으로
하드코딩하지 않는다. `robotId`와 현장 endpoint를 분리하고, 모든 첫 연결은
`link/subnet → ARP/TCP → connect → version → state`의 observe-only 사전검증을 거친다.
서보·모드·드래그 티칭·모션 명령은 조종권·현장 확인·안전 게이트 뒤의 별도 승격이다.

**실측 근거** — 2026-07-31 물리 포트 “1” 연결이라는 설명과 달리 `.58.2`는 응답하지 않고
eth0 주소 `.57.2:8080`만 응답했다. 기존 Unity 읽기 전용 스모크로 macOS Arm64에서
C#SDK-V1.2.4의 version·6축·TCP readback이 성공했다. 명령 호출은 0건이다
(`evidence/2026-07-31/fr5-live-readback.md`).

**경계** — C# readback 성공은 Python SDK 성공이 아니다. 루트 `Backend/`는 되살리지 않고
`FR5/bridge/robot_adapter/`에서 Python read-only 관문을 먼저 확인하며, 실패하면 브리지만
Linux로 옮긴다. 실기 상세 계획은 `ref/FR5-IMPLEMENTATION-PLAN.md`가 맡는다.

## D41. 실기 어댑터는 검증된 C# SDK 를 dotnet 서브프로세스로 재사용한다

**결정** — `FR5/bridge/robot_adapter/` 의 실기 경로는 Python SDK 가 아니라, 2026-07-31
macOS Arm64 에서 실기 readback 에 성공한 **libfairino.dll(C#SDK-V1.2.4)** 을 작은 dotnet
콘솔 앱으로 감싸 JSON-lines(stdin/stdout)로 부린다. 명령 승격은 `POST /arm`
(`confirm:"현장확인"` 리터럴 강제) 한 곳이고, WS 명령은 TB 와 같은 hello 신원 바인딩을 쓴다.

**이유** — libfairino.dll 은 관리형(.NET) 어셈블리다 (`file`: Mono/.Net assembly,
의존: mscorlib·System.Net.Sockets — 네이티브 없음). 즉 이 맥에서 이미 실기로 검증된
프로토콜 구현이 그대로 있다. 반면 공식 Python SDK 는 리눅스 `.so` 에 묶여 macOS 미확인
블로커가 그대로다 (PROJECT-STATUS §블로커). 검증된 것을 재사용하는 쪽이 추측 구현보다 싸고 안전하다.

**경계** — SDK 호출명·시그니처는 Unity `LiveFairinoClient.cs` 의 실기 검증 코드에서만 가져온다
(RPC/CloseRPC · GetRobotRealTimeState(`jt_cur_pos`·`tl_cur_pos`) · RobotEnable(byte) ·
Mode(int) · DragTeachSwitch(byte) · MoveJ 11인자 · StopMotion — `STACK.md` §FR5 C# SDK 등재).
dll 은 저장소에 커밋하지 않고 경로 설정으로 참조한다 (배포 저장소가 공개다). Python SDK 가
Linux 브리지에서 검증되면 어댑터만 교체한다 — 계약·웹은 모른다.

## D42. 실기가 낸 값을 기본값으로 박는다 — URL 에만 남기지 않는다

**계기** — 배포본을 폰에서 열었더니 **로봇이 안 떴고 카메라가 480×640** 이었다.
버전은 맞았다. 기본값이 틀렸다.

**무엇이 틀렸나 둘**

1. **마커 번호.** 설정이 `#2` 인데 인쇄해 쓰는 시트는 **`#5`** 였다
   (`Shared/assets/marker/marker-test-sizes-bc5.png`). 번호가 다르면 검출기가 통째로 무시한다
2. **해상도.** AR.js 기본이 카메라 640×480 · 검출 320×240 이라 **인식률 58%** 다.
   D26·D27 에서 둘을 올려 **100%** 를 봤는데, 그 값을 `?src=1280&cv=960` **URL 에만** 남겼다

**결정** — 실기가 낸 값이 기본값이다.
`.env` 를 `FR5_MARKER_BARCODE=5` · `FR5_MARKER_MM=45` 로, `ar.js` 의 기본을
`src=1280` · `cv=960` 으로 바꿨다. 되돌리려면 `?src=640&cv=320`.

**왜** — **측정해서 알아낸 값을 URL 에만 두면, 주소를 모르는 사람에게는 그냥 안 되는 화면이다.**
팀원은 링크만 받는다. 기본값이 곧 그 사람이 보는 전부다.

**대가** — **fps 13~14** (GAP-MATRIX OPEN). 끊기는 쪽이 안 잡히는 쪽보다 낫다고 보고 골랐다.

**같이 고친 것** — `config.mjs` 의 `FR5_MARKER_MM` 하한이 **40** 이라 크기 시험 시트의
10~35mm 를 설정으로 못 박았다. ⚙ 슬라이더는 이미 10 이었다 —
**같은 값을 두 곳이 다르게 제한하면 한 곳은 반드시 거짓말을 한다.** 10 으로 맞췄다.

**AR 배포 대상은 새 프로젝트 `fr5ar`** (이관 E 단계). 기존 `web`(= `web-nine-rho-89`)은
팀이 보고 있는 **이관 전 데모**라 건드리지 않는다. 방식은 D24 와 같은 **산출물 업로드** —
`AR/vercel.json` 의 `buildCommand` 는 이관 전 유물이고, 모노레포 하위 폴더에서
`npm install` 이 `@fr5/shared` 를 못 푼다. 스크립트 `scripts/dev/deploy-ar.sh`.

**함정** — 산출물만 올리면 `AR/vercel.json` 이 안 따라간다.
**카메라 권한 헤더(`Permissions-Policy: camera=(self)`)가 빠지면 AR 이 통째로 죽는다.**
스크립트가 다시 쓴다. 배포본에서 헤더를 확인했다.

**날짜**: 2026-07-31

## D43. 실험실 좌표계는 오른손이다 — `planToScene` 의 거울 사상을 고친다

**결정** — 바닥 원점 좌표계(SR_23)는 **오른손**(X·Y 바닥, Z 위)이다.
`units.js` 의 `planToScene` 을 `[x, z, y]` → **`[x, z, -y]`**. 축 변환은 이 함수 한 곳만 (하드 룰 5).

**근거** — `[x, z, y]` 는 축 두 개를 맞바꾼 것이라 **행렬식 −1 인 거울 사상**이다. 씬이 실제의
좌우 반전인데 배치안만 보면 아무도 눈치채지 못한다. 카메라 영상에 겹치면 첫 프레임에 드러나고
**흡수 불가** — 뷰 행렬 행렬식이 −1 이라 회전으로 표현이 안 되고, 스케일 −1 로 우회하면
뒷면 컬링이 뒤집혀 벽이 사라진다. 오른손을 고른 건 취향이 아니라 ROS 맵(`mapToLab`)과
OpenCV `solvePnP` 가 **둘 다 오른손 전제**여서다.

**실측** — `scripts/map/check-camera.sh` 가 cv2 와 three.js 투영을 대조한다. 고치기 전에는
변환이 거울을 감지해 던졌고, 고친 뒤 주점이 (7,26)px 어긋난 조건에서 7 점 전부 **0.000px**.
사진에서 시작하는 전체 사슬도 격자 0.000px (`evidence/2026-08-02/cam-overlay.md`).

**경계** — `layout-view.js` 는 아직 이 함수를 안 쓰고 같은 매핑을 인라인으로 약 25 곳 한다.
배치안 3D 는 여전히 반전 상태다. 카메라를 먼저 증명(S3)한 뒤 바꾼다 — 순서를 바꾸면
정합 오차와 반전 버그가 섞인다.

**날짜**: 2026-08-02

## D45. FR5 착수 전 감사 4역할 — P0 코드 3건은 즉시 수리, P0·P1 문서는 계약에 선반영

**결정** — P3~P6·그리퍼·모방학습 착수 전에 다역할 감사(보안·정합성·기능갭·운영)를 돌리고,
발견을 셋으로 갈랐다. ①**지금 코드가 이미 안전규칙을 어기는 3건은 즉시 수리** —
`stop` 이 명령과 같은 잠금을 공유해 앞 명령이 행이면 정지가 막히던 것(SAFETY-RULES 제3원칙
위반), 모든 xmlrpc 호출 무타임아웃, `/arm` 완료 직전 조종권 미재확인(주인 없는 ARMED).
②**P0·P1 설계 공백은 계약에 먼저 반영**(위 §이동 지점·§그리퍼·§슬롯). ③나머지는 GAP OPEN.

**이유** — 신규 기능이 기존 게이트 구조를 그대로 베끼면 결함까지 상속한다. 특히 그리퍼는
사람 손 협착 위험이 있어 "정지가 막힐 수 있다"를 P3 전에 닫아야 했다.

**저장 경계도 여기서 정했다** — 지점·슬롯·기록·시연 데이터는 **배포 트리 밖 `~/fr5-data/`**.
배포가 `rsync --delete` 라 트리 안에 두면 다음 배포 한 줄에 팀의 티칭 데이터가 사라진다.
감사가 아니었으면 첫 P3 커밋 다음 배포에서 만났을 사고다.

**모방학습의 선** — PRD "자율 작업 계획 범위 밖"과 충돌하지 않도록 **시연 1건 → 궤적 1건
재생, 일반화 없음**으로 긋는다. 기술 지형은 `scratchpad/scout-imitation-tech.md` 정찰 참고.

**기각** — 로그인 도입(D41 유지: LAN·팀 신뢰). 대신 조종권 위장(이름만 대면 통과)은
세션 토큰으로 막는 것을 GAP OPEN 으로 남겼다 — 로그인 없이도 닫히는 구멍이다.

## D46. 저장소는 Supabase — 단 로컬 파일이 정본이고 클라우드는 상위 층이다

**결정** — 미정이던 저장소(파일/SQLite/Supabase)를 **Supabase** 로 정했다. 다만 한 층이
아니라 두 층이다: **로봇 옆 브리지의 로컬 파일(`~/fr5-data/`)이 정본**, Supabase 는 팀
공유·집계용 상위 저장소. 브리지가 로컬에 먼저 쓰고 뒤이어 올린다.

**이유** — 인터넷이나 클라우드가 끊겼다고 티칭·실행이 멈추면 안 된다. 로봇 작업의 가용성을
외부 서비스에 묶지 않는다. 반대로 팀이 여러 기기에서 배치안·기록을 보려면 공유 저장소가
필요하다 — 두 요구는 층을 나눠야 동시에 만족한다.

**브라우저는 Supabase 를 직접 부르지 않는다.** 브리지만 서버 키로 말한다. 로그인이 없는
구조(D41)에서 브라우저에 키를 주면 주소를 아는 누구나 남의 기록을 지울 수 있다 —
"조종권·게이트·stop 이 보호한다" 는 전제가 데이터에는 성립하지 않는다.

**스키마에 미리 박을 것** — 모든 행에 `robotId`·펌웨어·tool/user·그리퍼 정체·`source`
(사람/텔레오퍼레이션/정책)·서버 단조시계 타임스탬프. **소급해 채울 수 없는 값들**이고,
특히 `source` 와 타임스탬프는 모방학습이 붙을 때 필요해진다. 영상은 경로만 저장한다.

**기각** — 브라우저 직결(anon 키 + RLS): 로그인이 없어 RLS 가 구분할 주체가 없다.
SQLite 단독: 팀 공유가 안 된다. 파일 단독: 집계·필터가 화면 몫이 된다.

**날짜**: 2026-08-03

## D47. 모방학습을 정식 목표로 — 학습이 목적이자 수단이다. 서보 스트리밍 경로를 연다

**결정** — D45 가 그었던 선("시연 1건 → 궤적 1건 재생, 일반화 없음")을 **넓힌다.**
주인님 확인: 학습은 데모에서 보여줄 **목적 그 자체**이면서 작업을 수행하는 **수단**이다.
따라서 시연 수집 → 정책 학습 → 정책으로 작업 수행까지가 범위다. PRD §범위 밖의
"자율 작업 계획" 은 **"배운 적 없는 작업을 스스로 계획하는 것"** 으로 좁혀 다시 적었다.

**이 결정이 연 기술 관문 — `MoveJ` 로는 안 된다.** 학습된 정책은 초당 10~50회 목표를
뱉는데 `MoveJ` 는 점 대 점이라 매 명령마다 가감속이 새로 걸린다. 벤더링된 SDK 에
`ServoMoveStart` → `ServoJ`(기본 주기 8ms) → `ServoMoveEnd` 가 있다 (소스 확인, 실기 미검증).
**브리지에 서보 스트리밍 경로를 새로 만든다.**

**안전 규칙도 형태를 바꾼다** — "한 명령당 5°" 는 점 대 점 전제다. 8ms 프레임마다 5° 면
초당 625° 다. 스트리밍은 **각속도(≤30°/s)·경과시간 비례·프레임 결손 3회면 종료**로 판정한다
(`SAFETY-RULES.md` §서보 스트리밍 상한). `stop` 은 스트리밍 중에도 잠금을 안 기다린다.

**LeRobot 은 쓰되 로봇을 잡게 하지 않는다** — 학습·데이터셋·평가 루프를 직접 구현하면
논문 재현이 프로젝트 하나가 된다. 대신 LeRobot 의 `Robot` 어댑터가 **브리지에게 요청을
보내게** 한다. xmlrpc 는 연결이 하나뿐이라 우회로를 만들 수 없고, 그래야 게이트가 산다.

**새로 생긴 준비물** — 서보 경로 · 텔레오퍼레이션 입력(±1° 버튼으로는 30~50회 시연을
못 한다) · 손목 뎁스카메라와 hand-eye · 학습용 GPU. 전부 GAP 에 OPEN 으로 올렸다.

**날짜**: 2026-08-03

## D48. 카메라의 주인은 라즈베리파이다 — 무선 기본, 원본 깊이는 안 흘린다

**결정** — 뎁스카메라를 라즈베리파이 4에 물리고(전원도 파이가 댄다), **파이 위에 작은 서버를
올려 카메라 전용 관문**으로 삼는다. "장치 하나에 관문 하나" — tb-bridge·fr5-bridge 와 같은
패턴이다. 계약은 `API-CONTRACT.md` §카메라. GAP 의 "카메라 스트림을 어느 브리지가 소유하나"를
이것으로 닫는다.

**파이는 로봇에 명령하지 않는다.** 찍고·시각 찍고·저장할 뿐이고 실행 여부는 FR5 브리지의
안전 게이트가 정한다. 파이가 로봇 명령 포트에 직접 붙으면 "명령 주인은 한 명"이 깨지고,
xmlrpc 는 연결이 하나뿐이라 실제로 컨트롤러가 넘어간다.

**무선으로 충분하다 — 단 원본 깊이를 실시간으로 흘리지 않는 조건에서.** 640×480 깊이
16비트 30fps 는 약 150Mbps 라 파이 4 의 무선 실효 대역과 겹친다. 그래서 **파이가 로컬에
먼저 기록하고 나중에 동기화**하고, 실시간은 압축 컬러만 보낸다(수 Mbps). 유선은 선택지로
남긴다 — 이더넷 포트는 어차피 있다. 조건 둘: **5GHz 사용** · 파이를 금속 함체에 넣지 않기
(안테나 내장).

**추론은 파이에서 하지 않는다** — GPU 가 없다. 파이는 눈이고, 학습·추론은 GPU 쪽이다.

**실무 함정 둘** — ①**전원**: 파이가 카메라 전원을 대므로 파이 자체가 5V·3A 정품급이어야
한다. 부족하면 촬영 중 카메라가 끊겼다 붙는데, 증상이 무선 탓처럼 보여 진단을 헤맨다.
불안정하면 전원 공급형 USB 허브로 카메라만 따로 먹인다. USB 3.0(파란) 포트를 쓴다
②**두 개의 시계**: 촬영 시각을 파이가 직접 찍고(도착 시각 금지), 랜 안에서 NTP 동기,
짝짓기 기준은 FR5 브리지 시계 하나.

**기각** — 카메라를 우분투에 직결(파이의 전원 공급 역할이 사라지고 케이블이 로봇까지 길어진다) ·
파이를 손목에 장착(j6 가 ±175° 돌아 케이블 비틀림과 페이로드가 같이 나빠진다. 카메라만
손목, 파이는 팔 밑동).

**날짜**: 2026-08-03

## D49. FR5 화면 UX 규약 — 3D 고정 레이아웃 · 폰은 보기 전용 · 확인은 한 모양

**결정** — 시각 토큰(D38)은 정해져 있었지만 UX 는 비어 있었다. 패널 4개가 붙기 전에 셋을
정했다 (주인님과 상의, 2026-08-03).

**①레이아웃은 "3D 고정 + 오른쪽만 교체"** — 왼쪽 3D 쌍둥이와 아래 조그·그리퍼 조작대는
항상 있고, 탭은 오른쪽 영역만 바꾼다. Teach 는 로봇을 조그하며 쓰는 화면이라, 전체 탭
교체 방식이면 "자세를 만든다 → 캡처한다" 사이에 화면이 두 번 바뀌고 돌아올 때마다 목록이
리셋된다. 조작대는 **Live 패널의 소유물이 아니라 화면의 상시 요소**다.

**②폰은 보기 전용** — 상태·기록 확인과 STOP 만. 조그·캡처·승인은 PC 에서만 한다.
화면을 좁히는 게 아니라 **조작 컨트롤 자체를 폰에 내보내지 않는다** — 주머니 속 오터치가
로봇을 움직이는 경로를 구조로 없앤다. STOP 만 예외다: 위험을 줄이는 방향이라 어디서든 받는다.

**③확인 절차는 전부 같은 모양** — `[ ] <무슨 일이 일어나는지> ` 체크박스 + 실행 버튼.
ARM · 슬롯 승인 · 정책 실행 · 시연 삭제가 같은 형태다. 모양이 다르면 급할 때 틀린다.
**알려진 위험은 습관화**다(같은 동작이 반복되면 읽지 않고 누른다). 그래서 문구를 고정하지
않는다 — "확인했습니다" 대신 그 순간 실제로 일어나는 일을 문구가 말한다. 이 완화가
③의 조건이다.

**기각** — 전체 탭 교체(작업 흐름이 끊긴다) · 폰에서도 전 기능(오터치 위험 대비 이득이 작다) ·
위험도별 3단 확인(배울 것이 늘고, 우리 규모에서 단계 구분이 자의적이 된다).

**정본** — `docs/ref/FR5-IMPLEMENTATION-PLAN.md` §화면. 시각 토큰은 D38 이 그대로 이긴다.

**날짜**: 2026-08-03
