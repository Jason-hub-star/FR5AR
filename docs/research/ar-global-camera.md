# 글로벌 카메라 AR — 실제 맵 위에 배치안 겹치기

분류: **조사** · 2026-08-02 · SSOT 아님. 확정되면 `ref/API-CONTRACT.md` · `ref/STACK.md` 로 승격한다.

---

## 결론 먼저

1. **된다. 그리고 폰 AR 보다 쉽다.** 글로벌 카메라는 **고정**이므로 정합 문제가 *추적(tracking)* 이 아니라 **1회 캘리브레이션(calibration — 카메라 위치·화각을 한 번 측정해 저장하는 것)** 으로 바뀐다. 떨림 0, 드리프트 0, 아이폰 포함 전 브라우저 동작(그냥 영상 + 캔버스다. WebXR·getUserMedia 안 쓴다).
2. **상시 태그는 필요 없다.** AprilTag/ArUco 는 **캘리브레이션 자동화용**으로만 쓴다 — 한 번 풀고 나면 화면에서 태그를 치워도 정합이 유지된다. "태그 없으면 불안정"은 **폰 AR 얘기**고, 고정 카메라엔 해당 없다.
3. **새로 만들 좌표 변환은 딱 1개.** 실험실 바닥 원점(SR_23)이 이미 전 도메인 기준이고 `mapToLab` 도 계약에 있다. 추가되는 건 `labToCam`(카메라 외부 파라미터) 하나뿐이다.

## 왜 쉬워지나 — 좌표 사슬이 이미 다 깔려 있다

```
SLAM 맵(m, ROS)  --mapToLab-->  ┐
FR5 관절값 --FK--> arm.basePosMm ┤→  실험실 바닥 원점 (mm · Z-up)  --labToCam-->  영상 픽셀
배치안 schema.js (mm) ──────────┘        ↑ SR_23 · TB-CONTRACT §미래접점③        ↑ 이것만 새로 만든다
```

- 배치안(`Shared/data/layout/schema.js`)의 원점이 **로봇이 아니라 바닥의 한 점**이라는 결정(D17·SR_23)이 여기서 값을 한다. 로봇 원점이었으면 카메라 정합이 배치를 바꿀 때마다 깨진다.
- AR 은 **읽기 전용 소비자**(TB-CONTRACT §4) — 이 설계도 그 규칙을 안 깬다. 명령은 안 보낸다.
- 그릴 것(`Shared/view3d/lab/layout-view.js` = 대시보드 메인뷰 본체)은 **이미 three.js 그룹으로 분리**돼 있다 — `createLayoutView()` 가 `{ root, contents, armSlot, dispose }` 를 주고 대시보드는 `stage.scene.add(view.root)` 한 줄로 붙인다. AR 은 **부모만 바꿔 끼우면 된다.** React 를 안 쓴 게(D17) 여기서 두 번째로 값을 한다.

### 다만 `stage.js` 는 그대로 못 쓴다 (검증 2026-08-02)

`createStage()` 가 렌더러·**PerspectiveCamera(42°)**·OrbitControls·불투명 배경을 통째로 소유한다. 글로벌 카메라 화면은 셋 다 반대여야 한다.

| 필요한 것 | 지금 | 조치 |
|---|---|---|
| 배경 투명 (영상이 비쳐야 함) | `alpha:false` + `scene.background` 색 지정 | `{ alpha:true }` → 배경 `null` |
| 카메라를 캘리브레이션 값으로 고정 | 내부에서 42° 로 생성 | 화각·포즈를 **주입**받는 옵션 |
| 궤도 조작 없음 (실카메라는 못 돈다) | OrbitControls 항상 생성 | `{ controls:false }` |

**새 stage 파일을 만들지 말고 `createStage` 에 옵션 3개를 얹는다.** 두 벌이 되면 조명·톤매핑이 갈라져 두 화면 색이 달라진다.

## 수직 사다리 — 실제 맵 없이도 G2 까지 오늘 쌓을 수 있다

| 단계 | 하는 일 | 완료 판정 | 서버 | 실제 맵 |
|---|---|---|---|---|
| **G1** | 웹캠 **정지 사진 1장**을 `<img>` 로 띄우고 바닥 4점 클릭 → **호모그래피**(평면↔평면 대응 3×3 행렬) → 격자를 사진 위에 겹친다 | 격자가 실제 바닥선과 붙는다 | ❌ 불필요 | ❌ |
| **G2** | 같은 대응점 + 내부 파라미터 → **solvePnP**(점 대응으로 카메라의 3D 위치·자세를 푸는 것) → three.js `PerspectiveCamera` 를 그 포즈에 놓고 `layout-view.root` 를 사진 위에 렌더 | 실물 상자 모서리와 가상 벽 모서리가 겹친다 | ❌ | ❌ |
| **G3** | **AR 전환 버튼 + 바닥에서 솟아오르는 연출** | 버튼 누르면 빈 바닥에서 방·작업대·로봇이 자란다 | ❌ | ❌ |
| **G4** | 정지 사진을 **라이브 영상**으로 교체 (MJPEG 1엔드포인트) | 손을 흔들면 영상이 움직이는데 겹친 3D 는 제자리 | ✅ | ❌ |
| **G5** | 실시간 연계 — `/ws/state` 의 AMR pose(`mapToLab` 경유)·FR5 관절을 같은 씬에 | 실물 터틀봇 위에 가상 터틀봇이 붙어 움직인다 | ✅ | ✅ |
| **G6** | ArUco 자동 재캘리브레이션 · 오클루전(실물이 가상을 가림) | 카메라를 건드려도 1초 만에 다시 맞는다 | ✅ | ✅ |

**G1~G3 은 서버도 실제 맵도 없이 된다** — 정지 사진 1장이면 정합의 전부를 검증할 수 있다. 라이브 영상은 정합이 끝난 뒤 `<img>` 를 `<video>`/MJPEG 로 바꾸는 것뿐이다. 순서를 지키면 "카메라가 없어서·맵이 없어서 못 한다"가 안 나온다.

### 순서를 바꿀 수 없다 — 내부가 나쁘면 외부가 조용히 틀어진다

합성 검증(2026-08-02)에서 **내부 파라미터 fy 를 1.3% 틀리게** 넣었더니 카메라 높이가
**2.40m → 4.41m** 로 나왔다. 재투영 오차 88px 로 드러나긴 했지만, 임계값이 없었으면
그 값이 그대로 저장돼 "왜 3D 가 안 맞지"를 좌표계에서 찾게 만들었을 것이다.
참값 내부로 다시 풀면 **위치 오차 4mm · RMS 0.95px** 다.

→ 두 build 스크립트 모두 **오차 상한을 넘으면 쓰지 않고 멈춘다.** 값이 없는 편이 낫다.

**캘리브레이션 수학은 브라우저에 넣지 않는다.** 파이썬 스크립트 1개(`cv2.calibrateCamera` + `cv2.solvePnP`)로 오프라인 계산해 JSON 으로 떨군다. 웹은 **JSON 을 읽기만** 한다 — 1회성 계산을 런타임 코드로 만들 이유가 없다.

## 마커 판정 — 어디에 쓰고 어디에 안 쓰나

| 경로 | 마커 | 근거 |
|---|---|---|
| **글로벌 카메라 (신규)** | **캘리브레이션 때만.** 없어도 클릭 4점으로 됨 | 카메라가 고정이라 포즈가 안 변한다 |
| **폰 AR (기존)** | **필수 유지** | iOS 사파리는 2026년에도 `immersive-ar` 미지원 — WebXR 경로 자체가 없다 |

- **AprilTag 36h11 로 확정 (2026-08-02).** 같은 크기에서 ArUco 보다 원거리 검출이 낫고 로봇공학 표준인데, **설치된 OpenCV 4.13 에 `DICT_APRILTAG_36H11` 사전이 내장돼 있어 추가 의존성이 0 이다.** 생성·검출 모두 `cv2.aruco` 로 한다 — "AprilTag 를 쓰려면 별도 라이브러리"라는 통념은 지금 환경에 해당 없다.
  - 인쇄물: `Shared/assets/tag/` · 생성기: `scripts/map/make-tags.py` (되읽어 8/8 검출·치수 자가검증)
  - **선언 크기 = 검은 사각형 바깥 한 변**. 바깥 흰 여백은 정숙영역이지 크기가 아니다. solvePnP 에 넣는 값이 이것이다
  - 폰 AR 의 3×3 바코드(`Shared/assets/marker/`)와 **다른 물건이다.** 읽는 주체가 AR.js(브라우저) vs OpenCV(파이썬)로 갈린다
- **정밀도 순위**: 4 태그 동시 관측(멀티태그 융합) > 1 태그 > 클릭 4점. 여러 태그를 동시에 보면 개별 태그 오차가 평균화된다 (PhotonVision MultiTag 와 같은 원리).
- **경사(oblique) 설치가 포즈 추정에 유리하다.** 평면 타겟을 정면에서 보면 포즈 모호성(planar ambiguity)이 생긴다. AprilTag 오차의 주범도 거리보다 **카메라의 회전 불확실성**이라는 게 문헌 일치다.
- **마커리스 대안은 지금 추천 안 함**: 8th Wall(유일하게 iOS 에서 되던 WebAR SLAM)은 2026년 호스팅 종료, 엔진 바이너리만 무료 배포로 남았다. 우리가 짊어질 리스크가 아니다.

## 내일 맵 만들 때 — 실제 치수

### 카메라 커버리지 (수직 설치, HFOV 70°/VFOV 42° = "대각 78°" 웹캠 기준)

커버 가로 = 2·h·tan(35°) = **1.40·h** / 커버 세로 = 2·h·tan(21°) = **0.77·h**

| 설치 높이 h | 커버 영역 | **권장 맵 크기**(여백 12%) | 픽셀밀도(1080p) |
|---|---|---|---|
| 2.0 m | 2.80 × 1.54 m | **2.4 × 1.35 m** | 686 px/m |
| 2.2 m | 3.08 × 1.69 m | **2.7 × 1.5 m** | 623 px/m |
| **2.4 m** | 3.36 × 1.84 m | **3.0 × 1.6 m** ← 기본 권장 | 571 px/m |
| 2.6 m | 3.64 × 2.00 m | 3.2 × 1.75 m | 527 px/m |

**암산 규칙: 맵 가로 ≈ 1.25·h, 세로 ≈ 0.68·h.**

> **맵을 16:9 로 만들어라.** 센서 비율과 맞추면 화면이 꽉 찬다. 정사각형 맵은 좌우가 남고 위아래가 잘린다 — 세로가 항상 먼저 모자란다.

### 카메라 각도

| 설치 | 인식률·측위 | AR 연출 | 판정 |
|---|---|---|---|
| **수직(90°, 천장 정중앙)** | 최상. 왜곡 최소, 가림 없음 | **나쁨** — 위에서 보면 솟아오르는 게 안 보인다(납작) | 순수 관제용 |
| **하향 50~60° (긴 변 중앙 위)** | 양호. 먼 쪽 픽셀밀도 절반 | **최상** — 높이감이 살아 연출이 극적 | **1대라면 이것** |
| 하향 30° 이하 | 나쁨 — 원근 심함, 가림 많음 | 과함 | ✗ |

**권장: 맵 긴 변 중앙 위 높이 2.2~2.6 m, 하향각 50~60°.** 나중에 천장 수직 1대를 추가해 2대(연출용·관제용)로 간다.

> **모서리 대각선 배치를 쓰지 마라 (2026-08-02 계산으로 뒤집음).** 처음엔 대각선이 맞다고 봤는데, 3.0×1.6m·높이 2.4m 로 실제로 풀어 보니 최원거리 모서리가 **4.16m·부각 35°** 가 된다. 긴 변 중앙이면 **3.35m·부각 46°** 다. 눕힌 태그의 단축 방향 해상도가 **190 → 292 px/m (+54%)** — 카메라를 옮기는 것만으로 태그를 1.5배 키운 효과다. **공짜다.**

**렌즈는 광각(≥100°)을 피한다.** 커버는 넓어지지만 배럴 왜곡 때문에 가장자리에서 가상·실물이 어긋나고, 그건 언디스토트(왜곡 보정) 작업을 강제한다. **70~90° 가 스위트스팟.**

### 태그 배치

**크기는 화면 중앙이 아니라 "가장 먼 모서리의 칸당 픽셀"로 정한다.** 36h11 은 8칸이고, 바닥에 눕힌 태그는 카메라 부각만큼 단축돼서 중앙의 여유가 먼 구석에서 사라진다. 3.0×1.6m·2.4m·HFOV 70° 실계산:

| 카메라 배치 | 해상도 | 150mm | 220mm |
|---|---|---|---|
| 모서리 위 (비권장) | 1080p | **3.6 px/칸 — 아슬** | 5.2 px/칸 |
| 모서리 위 (비권장) | 1440p | 4.7 px/칸 | 7.9 px/칸 |
| **긴 변 중앙 위** | 1080p | **5.5 px/칸 — OK** | 8.0 px/칸 |
| **긴 변 중앙 위** | 1440p | 7.3 px/칸 | 12.2 px/칸 |

**5 px/칸이 안전선, 3 px/칸은 조명이 나쁘면 놓친다.**

- **A4 150mm 는 "긴 변 중앙 위 + 1080p 이상"에서만 쓴다.** 이 조건을 지키기로 하고 **A4 만 생성한다** (2026-08-03 · 인쇄 환경이 A4 뿐). 카메라를 모서리에 달아야 하면 태그를 키우는 대신 **맵을 2.0×1.1m 로 줄인다** (5.6px/칸). A3 가 생기면 `make-tags.py` 의 `SHEETS` 에 `(A3, 220)` 을 되돌린다.
- **id4 는 바닥 태그가 아니다.** 로봇이 얹힌 테이블 위(z≈900mm)에 올려놓고 정합이 높이에서도 맞는지 보는 **이동식 기준자**다 — 바닥 태그로 푼 카메라는 바닥에서만 검증됐는데 팔은 그 위에서 움직인다. 재고 나면 치운다.
- A4 상한이 150mm 인 이유는 종이 폭이 아니라 **정숙영역**이다 — 태그 1칸 폭(=크기/8)을 흰 여백으로 둬야 해서 `크기 × 1.25 ≤ 200mm` 가 걸린다. 여백을 깎아 태그를 키우면 임계화가 흔들려 오히려 손해다.
- 맵 **네 모서리에 4장**(id 0~3).
- 태그 위치를 **바닥 원점 기준 mm 로 자로 재서 적어둔다.** 이 값이 틀리면 그 오차가 그대로 정합 오차다 — 문헌에서도 멀티태그의 주 오차원은 검출이 아니라 **레이아웃 값의 부정확**이다.
- 무광 용지·100% 배율·딱딱한 판. (우리 실측: 검출을 결정하는 건 크기가 아니라 명도차 — `STACK.md` §마커)

### 맵 자체

- **벽 높이 ≥ 250mm.** TurtleBot3 Burger 전고가 192mm 이고 LDS-02(42mm 높이)가 맨 위 판에 얹히므로 스캔 평면은 **대략 170~180mm** 로 추정된다 — 그보다 낮은 벽은 **SLAM 에 아예 안 보인다.** ⚠ **공식 문서에 스캔 평면 높이 수치가 없다 (2026-08-02 웹 확인).** 내일 실물에 자를 대고 라이다 창 중심 높이를 재서 여기 값을 확정하라. 그전까지 250mm 는 추정에 여유를 얹은 값이다.
- 바닥은 **무광·단색·비반사**. 광택 바닥은 조명 반사로 태그 검출과 AMR 검출을 동시에 망친다.
- 맵 원점(바닥 한 점)을 **테이프로 물리적으로 표시**하고 X축 방향도 그린다. 이 한 점이 전 도메인 SSOT 다.

## "바닥에서 솟아오르는" 연출 — 구현은 한 줄에 가깝다

**클리핑 평면을 올린다.** `THREE.Plane(new Vector3(0,-1,0), h)` 의 상수를 0 → 방 높이로 애니메이션하면 **모든 메쉬가 동시에 바닥에서 자라난다.** `renderer.clippingPlanes = [plane]` 한 줄이면 끝 — 전역 클리핑이라 `localClippingEnabled` 플래그도, 재질 수정도 필요 없다. (`layout-view.js` 의 재질은 모듈 상수로 공유되므로 재질별 클리핑은 오히려 손대기 나쁘다.)

- `scale.y` 를 0→1 로 키우는 방식은 **쓰지 마라.** 문·유리·프레임이 세로로 늘어나 형상이 망가진다. 클리핑은 형상을 안 건드린다.
- 스태거 0.15s: 바닥 격자 → 벽 → 작업대 → 안전 범위 → 로봇. 한 번에 다 나오면 뭐가 뭔지 안 보인다.
- **G3 은 카메라 없이 대시보드 메인뷰에서 먼저 완성한다.** AR 위에서 연출을 만들면 정합 오차와 연출 버그가 섞여 원인을 못 가른다 (그리퍼 정합 때 쓴 것과 같은 원칙).

## 함정 5개 (미리 안 보면 반드시 밟는다)

| # | 함정 | 증상 | 대응 |
|---|---|---|---|
| 1 | **영상 지연 vs 상태 지연** | 가상 로봇이 실물보다 **앞서 간다** | 영상은 100~300ms 늦고 WS 상태는 즉시다. 상태를 영상 지연만큼 **버퍼링해 늦춰 재생**한다. 지연값은 실측해 설정 파일로 |
| 2 | **화각 불일치** | 중앙은 맞는데 가장자리가 벌어진다 | three.js 카메라 `fov`·종횡비·주점을 **실측 내부 파라미터**로 맞춘다. 스펙시트 값 그대로 쓰면 안 맞는다 |
| 3 | **렌즈 왜곡** | 직선이 휘고 모서리에서 어긋남 | 광각 회피 + 필요하면 영상 쪽 언디스토트 |
| 4 | **`markerSizeMm` 드리프트** | 겹친 로봇 크기가 통째로 틀림 | 현재 `Shared/data/config/marker-offset.json` 이 **45mm** 인데 인쇄 시트는 **170/240mm** 다. 실제 인쇄물과 대조할 것 |
| 5 | **오클루전 없음** | 실물 뒤에 있어야 할 가상 물체가 앞에 뜬다 | 고정 카메라라 정적 깊이맵을 한 번 구울 수 있다 — G5. 그전까지는 **반투명**으로 회피 |

## 계약에 먼저 들어가야 할 것 (하드 룰 1)

코드보다 `docs/ref/contract/API-CONTRACT.md` 가 먼저다.

```
GET   /api/camera/stream            MJPEG 실시간 영상 (글로벌 카메라)
GET   /api/camera/calib             → { intrinsics, labToCam, verifiedAt, rmsPx }
POST  /api/camera/calib             { points: [{imgPx, labMm}] } 또는 { auto: true }  → solvePnP
```
신규 설정: `Shared/data/config/global-cam.json` — 내부 파라미터 · `labToCam` · 영상 지연(ms) · 태그 레이아웃(mm).
**단위 변환은 여기 한 곳**(하드 룰 5). 태그 좌표도 mm·도.

**미결 — 카메라는 누구 소유인가.** 글로벌 카메라는 FR5 것도 터틀봇 것도 아닌 **실험실 것**이다. 지금 브리지가 둘로 갈려 있어 스트림 엔드포인트를 어디 둘지 정해야 한다. 새 최상위 폴더는 하드 룰 1 대상이므로 **G4 전에 결정**한다. (A1~A6 은 서버가 없어 이 결정을 안 기다린다 — 그래서 사다리를 이 순서로 짰다.)
