먼저 결론

이 세 가지가 나머지 선택을 다 결정합니다.

판정 1 — 방식

WebXR은 못 씁니다. 마커 방식이 유일한 답입니다.

iOS 사파리는 2026년 현재도 immersive-ar를 열어주지 않습니다. 안드로이드만 됩니다. 양쪽 다 되는 방법은 카메라 영상을 직접 받아 마커를 찾는 방식뿐입니다.

근거 — caniuse WebXR · Safari 미지원 지속
판정 2 — 자산

FR5 3D 모델이 이미 우리 손에 있습니다.

FR5UNITY/…/FAIRINO_FR5/fairino5_v6.urdf + STL 7개. 웹 로더가 STL을 그대로 읽습니다. 모델을 새로 구할 필요도, 형식을 바꿀 필요도 없습니다.

실측 — 58,482 삼각형 / 12 MB
판정 3 — 범위

오차 1~1.5cm. 그래서 용도가 정해집니다.

마커 정합은 ±5~15mm 어긋납니다. "여기쯤 지나갑니다"를 보여주기엔 충분하고, mm 단위 정렬 작업에는 못 씁니다. 안전 범위·궤적·지점 표시가 딱 맞는 용도입니다.

근거 — 마커 자세 추정 정확도 연구 (거리 0.5~1m에서 최적)

스택 한 장

층별로 이렇게 고릅니다.

폰 · 카메라 정합
AR.js @ar-js-org/ar.js 3.4.8 마커를 찾아 3D 좌표계를 실물에 붙입니다. iOS·안드로이드 양쪽 다 됩니다. 2026년 3월 릴리스로 지금도 관리되고 있습니다. 대안 — MindAR(이미지 추적, 2024년 이후 정체) · 8th Wall(2026-02 서비스 종료) · model-viewer(마커 추적 불가)
3D 렌더
three.js + urdf-loader 0.185.1 / 0.13.1 우리 URDF를 그대로 읽어 관절 단위로 움직입니다. robot.setJointValue(관절명, 각도) 한 줄로 자세가 바뀝니다. 화면 구성이 복잡해지면 react-three-fiber 9.6.1 + drei 10.7.7 추가. 처음엔 순수 three.js로 충분합니다.
궤적 계산
우리가 이미 가진 정기구학(FK) 저장된 지점은 관절 각도이고 MoveJ는 관절을 곧바로 보간합니다. 각도를 잘게 쪼개 FK를 돌리면 손끝이 그리는 선이 그대로 나옵니다. 역기구학(IK)이 없어도 됩니다. 브라우저에서 다시 계산해도 되고(three.js에서 URDF의 관절 트리를 그대로 이용), 서버에서 계산해 점 목록만 내려줘도 됩니다.
뒷단(서버)
Python FastAPI + 공식 Fairino SDK fastapi 0.140.13 로봇과는 제조사 공식 파이썬 라이브러리로 말하고, 브라우저와는 WebSocket으로 말합니다. 이미 있는 FairinoBridgeClient가 부르는 그 서버 자리입니다. 서버 실행은 uvicorn 0.52.0. 조사에서 본 meowiky/DP-fairino-robot-API가 이 형태의 최소 예시입니다.
실시간 통신
WebSocket 관절값을 초당 30~100번 내려보내고, 브라우저에서 명령을 올려보내야 하므로 양방향이 필요합니다. SSE는 한 방향뿐이라 탈락, WebRTC는 과합니다. 여러 사람이 동시에 볼 때는 서버가 접속 목록을 들고 있다가 한꺼번에 뿌리는 방식(브로드캐스트).
개발 환경
HTTPS 필수 — mkcert 또는 터널 브라우저는 안전한 연결이 아니면 카메라를 아예 안 열어줍니다. 폰으로 테스트하려면 http://192.168.x.x로는 안 됩니다. 사내망이면 mkcert로 인증서 발급, 밖에서도 봐야 하면 tailscale funnel이나 Cloudflare Tunnel.

② 브라우저에 로봇 그리기

우리 URDF를 그대로 읽힙니다.

urdf-loader는 기본 로더가 STL과 COLLADA를 지원합니다. 우리 파일이 정확히 STL이라 변환 없이 바로 뜹니다.

// 우리 파일 그대로 로드
const loader = new URDFLoader();
loader.packages = { '': '/assets/FAIRINO_FR5' };
loader.load('/assets/FAIRINO_FR5/fairino5_v6.urdf', robot => {
  scene.add(robot);

  // 관절 하나 움직이기 — 각도는 라디안
  robot.setJointValue('j2', -1.2);

  // 저장된 지점 하나를 그대로 적용
  ['j1','j2','j3','j4','j5','j6'].forEach((n, i) =>
    robot.setJointValue(n, deg2rad(point.jointsDeg[i]))
  );
});

12MB는 줄이는 게 좋습니다. 폰에서 매번 12MB를 받으면 첫 화면이 느립니다. @gltf-transform/cli 4.4.2로 GLB 변환 + 간소화를 걸면 1~2MB대로 떨어집니다. 다만 1단계에서는 STL 그대로 쓰고, 느리다고 느껴질 때 최적화하는 순서를 권합니다 — 미리 하면 형식이 하나 더 늘어 관리 지점만 늘어납니다.

③ 지나갈 길 계산하기

역기구학이 없어도 궤적은 그려집니다.

이게 이 계획에서 가장 중요한 기술 판단입니다. 우리 프로그램에는 역기구학(IK)이 구현돼 있지 않습니다. 보통 이런 기능은 IK가 필요하다고 생각하지만, 이 경우엔 필요 없습니다.

이유

저장된 지점이 이미 관절 각도이기 때문입니다.

우리 이동 지점은 손끝 위치가 아니라 6축 관절 각도로 저장됩니다. 그리고 MoveJ는 그 각도들을 곧장 보간합니다. 그러니 시작 각도 → 끝 각도를 100등분해 각 단계마다 정기구학(FK)을 돌리면 손끝이 지나가는 점 100개가 나옵니다. 그 점들을 이으면 그게 궤적입니다.

우리 자산 — DHStandard.cs · ForwardKinematics.cs · DH 파라미터 6축 전부 정의됨 
# 서버 쪽 의사코드 — IK 없이 궤적 만들기
def preview_path(p_from, p_to, steps=100):
    pts = []
    for k in range(steps + 1):
        t = k / steps
        # 관절 각도를 선형 보간 (MoveJ가 실제로 하는 것)
        q = [a + (b - a) * t for a, b in zip(p_from, p_to)]
        # 정기구학 → 손끝 위치
        pts.append(forward_kinematics(q))
    return pts   # 이 점 목록을 브라우저로 보내면 선이 됨

브라우저에서 그릴 때는 점 목록을 three.js의 선으로 만듭니다. 얇은 선(Line)은 굵기 조절이 안 되니, 보기 좋게 하려면 TubeGeometry(가는 관)로 만들고 반투명 재질을 씌우는 쪽이 낫습니다. 안전 범위는 반투명 원기둥 하나면 됩니다.

주의 — 이 궤적은 "예상"입니다. 실제 로봇은 가감속 곡선과 안전 제한 때문에 조금 다르게 움직일 수 있습니다. 화면에 "예상 경로"라고 명시하고, 실제 지나간 길은 로봇이 보내주는 실제 관절값으로 따로 그려 두 개를 비교하면 오히려 더 좋은 기능이 됩니다.

# FastAPI — 접속자 전원에게 관절값 뿌리기 (최소 형태)
from fastapi import FastAPI, WebSocket, WebSocketDisconnect

app = FastAPI()
clients: list[WebSocket] = []

@app.websocket("/ws/state")
async def state(ws: WebSocket):
    await ws.accept()
    clients.append(ws)
    try:
        while True:
            await ws.receive_text()      # 브라우저 → 서버 명령
    except WebSocketDisconnect:
        clients.remove(ws)

async def broadcast(payload: dict):      # 로봇 상태 폴링 루프에서 호출
    for ws in list(clients):
        try:    await ws.send_json(payload)
        except: clients.remove(ws)

이 구조가 그대로 "여럿이 같이 쓰기"의 바탕이 됩니다 — 상태는 전원에게 뿌리고, 명령은 지금 조종권을 가진 한 명의 것만 받아들이면 됩니다.

⑤ 개발 환경

카메라를 열려면 HTTPS가 반드시 필요합니다.

브라우저는 안전한 연결이 아니면 navigator.mediaDevices 자체를 주지 않습니다. 이걸 모르고 시작하면 첫날에 반나절을 날립니다.

상황되나방법
PC에서 http://localhost됨브라우저가 예외로 허용
폰에서 http://192.168.x.x안 됨— 여기서 대부분 막힙니다
폰에서 사내망 접속됨mkcert로 인증서 발급 → 폰에 인증서 설치
밖에서도 접속됨tailscale funnel 또는 Cloudflare Tunnel로 HTTPS 주소 발급

시연 당일을 생각하면 터널 방식이 안전합니다 — 회의실 와이파이가 사내망과 다를 수 있고, 심사위원 폰에 인증서를 깔게 할 수는 없기 때문입니다. QR코드 하나 띄워두면 각자 폰으로 열어봅니다.

먼저 알고 가면 좋은 것

실제로 막힐 지점 다섯.

HTTPS 없이는 카메라가 안 열린다

폰에서 IP 주소로 접속하면 카메라 요청이 아예 안 뜹니다. 코드 잘못인 줄 알고 헤매기 쉽습니다.

먼저 할 일 — 코드 짜기 전에 터널부터 세우고 폰에서 카메라가 켜지는지 확인

마커가 흔들리면 로봇도 흔들린다

마커 검출은 프레임마다 조금씩 튑니다. 그대로 쓰면 겹쳐진 로봇이 덜덜 떱니다.

해결 — 최근 몇 프레임 평균을 쓰거나, 마커를 놓쳐도 마지막 위치를 유지

단위가 두 번 어긋난다

URDF는 미터·라디안, 우리 저장 지점은 밀리미터·도(°)입니다. 그리고 로봇 좌표계와 3D 화면 좌표계의 축 방향이 다릅니다.

해결 — 변환을 한 곳에만 두고, 절대 여기저기서 하지 않기

마커 원점과 로봇 원점을 맞추는 작업이 있다

마커를 붙였다고 끝이 아닙니다. 마커가 로봇 원점에서 얼마나 떨어져 있는지 한 번은 재야 합니다.

해결 — 이 값을 설정 파일 하나로 빼두면 마커를 옮겨도 숫자만 고치면 됨

12MB 첫 로딩

폰에서 처음 열 때 로봇 모델을 다 받아야 화면이 뜹니다. 시연 중 몇 초 침묵이 생깁니다.

해결 — 로딩 표시를 넣고, 느리면 그때 GLB로 바꿔 1~2MB로

착수 순서

위험한 것부터 먼저 확인합니다.

기능을 순서대로 쌓지 않고, "안 되면 계획이 무너지는 것"부터 하루 안에 확인합니다. 아래 순서면 3일차에 계속할지 말지 판단이 섭니다.

판정 — 슬라이더를 움직이면 3D 로봇이 따라 움직인다
